# Architecture

This document describes how Tsuzuki is built. Decisions and their rationale live in [`adr/`](./adr). Keep this file in sync with the code: any structural change updates it in the same PR.

## 1. Overview

```mermaid
flowchart LR
    subgraph App[Expo app]
        UI[app/ + features/ + ui/]
        Core[src/core]
        Platform[src/platform]
    end
    UI --> Core
    UI --> Platform
    Core -->|CatalogProvider| Jikan[Jikan v4 compatible API<br/>Tenrai by default]
    Core -->|Repositories| SB[Supabase Auth + Postgres + RLS]
    Platform --> MMKV[(MMKV: cache, guest data)]
    Platform --> Secure[(Secure store: session)]
    SB --> EF[Edge Functions]
```

- The **catalog** (titles, search, discovery) comes from an external provider behind the `CatalogProvider` interface: today a Jikan v4 compatible API, Tenrai by default or a self-hosted Jikan by configuration (ADR-0013).
- **User data**: the library (favorites included) lives in Supabase for signed-in users, and in MMKV for guests; the preferences and the recent searches stay on the device for both (§6, §7).
- The app never talks to a provider or to Supabase outside `src/core/`.

Layer rules are defined in `CONTRIBUTING.md` §4 and enforced by ESLint; their tables live in `tools/eslint/layers.mjs` (`layerRules`, `LAYERS`, `LAYER_ZONES` and the network constants) and `tools/eslint/import-bans.mjs` (the banned import tables `BANNED`, `CANONICAL_PATHS` and `PLATFORM_CORE_TYPE_ONLY`).

- Only the root layout `app/_layout.tsx`, the composition root, wires the repository and catalog provider implementations (`src/core/repositories/supabase/`, `src/core/repositories/local/`, `src/core/catalog/jikan/`). Every other route, nested layouts included, and every feature goes through `src/core/hooks/`. Everything else in `src/core/` (domain, schemas, query, errors, i18n, hooks, and the interface files at the root of `repositories/` and `catalog/`) and in `test/core/` depends only on the repository and `CatalogProvider` interfaces, never on the implementation folders.

## 3. Catalog provider adapter

All catalog access goes through one interface, so the Jikan-compatible provider can be replaced or complemented (AniList, MangaUpdates) without touching screens.

```ts
// src/core/catalog/catalog-provider.ts
// MediaKind, MediaIdNamespace, MediaKey ({ namespace, kind, externalId }), the format and status types and
// their const arrays live in src/core/domain/media.ts. a key names whose ids it holds (namespace 'mal' for
// every jikan v4 compatible instance), never the server that returned it (ADR-0013)
import type {
  MediaFormat, MediaIdNamespace, MediaKey, MediaKind, MediaStatus, SearchableMediaFormat, SearchableMediaStatus,
} from '../domain/media';

export interface Genre {
  readonly id: number;                   // scoped to the provider's namespace (a mal genre id)
  readonly name: string;
}

export interface MediaSummary {
  readonly key: MediaKey;
  readonly title: string;
  readonly titleEnglish: string | null;
  readonly imageUrl: string | null;
  readonly format: MediaFormat;          // tv, movie, manga, manhwa, light_novel… or unknown
  readonly status: MediaStatus;          // ongoing, finished, upcoming, hiatus, discontinued
  readonly totalUnits: number | null;    // episodes or chapters, null when unknown
  readonly score: number | null;
  readonly year: number | null;
  readonly genres: readonly Genre[];
  readonly isAdult: boolean;             // set by the adapter with isAdultMedia (see §7)
}

export interface MediaDetail extends MediaSummary {
  readonly synopsis: string | null;
  readonly titleNative: string | null;
}

export const SEARCH_SORT_FIELDS = ['score', 'popularity', 'title', 'start_date'] as const;
export type SearchSortField = (typeof SEARCH_SORT_FIELDS)[number];
export const SORT_DIRECTIONS = ['asc', 'desc'] as const;
export type SortDirection = (typeof SORT_DIRECTIONS)[number];

export interface SearchParams {
  readonly kind: MediaKind;
  readonly query?: string;
  readonly formats?: readonly MediaFormat[];
  readonly genresIncluded?: readonly number[];
  readonly genresExcluded?: readonly number[];
  readonly status?: SearchableMediaStatus;  // ongoing, finished, upcoming (FR-03)
  readonly yearFrom?: number;               // four digits: started on or after Y-01-01, still running or not
  readonly minScore?: number;
  readonly sort?: { readonly field: SearchSortField; readonly direction: SortDirection };
  readonly page: number;                    // 1-based
}

export interface TopParams {
  readonly kind: MediaKind;
  readonly format?: SearchableMediaFormat;  // one format of the kind with a provider type (FR-05 chips); absent: every format
  readonly page: number;                    // 1-based
}

export interface Page<T> {
  readonly items: readonly T[];
  readonly page: number;
  readonly lastPage: number;
  readonly hasNextPage: boolean;
}

export interface CatalogProvider {
  readonly namespace: MediaIdNamespace;  // of every key it returns and accepts; part of every catalog query key
  readonly instanceId: string;           // short non-personal id (tenrai, jikan-self-hosted) for error reports; never a url, never in a key

  readonly searchGenresMax: number;      // most genre ids accepted in genresIncluded, and in genresExcluded

  getTop(params: TopParams, signal?: AbortSignal, options?: CatalogRequestOptions): Promise<Page<MediaSummary>>;

export type CatalogRequestPriority = 'foreground' | 'background';

  readonly priority?: CatalogRequestPriority; // foreground (default): what the user sees; background: a prefetch

```

- `MediaStatus` is the publication status of the title (MAL "On Hiatus" and "Discontinued" included); it never reuses the library status names (`current`, `planned`, `completed`, `paused`, `dropped`, §5).
- The format and status const arrays (`ANIME_FORMATS`, `MANGA_FORMATS`, `MEDIA_FORMATS`, `MEDIA_STATUSES`, `SEARCHABLE_MEDIA_STATUSES`, `SEARCH_SORT_FIELDS`, `SORT_DIRECTIONS`) are the single source for the adapters' `z.enum` schemas and the filter chips. An unrecognized provider type maps to `unknown`. The format chips use `SEARCHABLE_FORMATS_BY_KIND` (`SEARCHABLE_ANIME_FORMATS`, `SEARCHABLE_MANGA_FORMATS`, type `SearchableMediaFormat`): the kind's formats without `unknown` (the adapter fallback) and `oel`, which have no provider search type; `MEDIA_FORMATS_BY_KIND` keeps every format of each kind.
- Formats per kind: `SearchParams` stays one interface, not a union keyed on `kind`, and `formats` stays an array. An adapter rejects, with a `RangeError` before any request, a format of the other kind, a format without a search type, or more formats than it can send (the Jikan-compatible adapter: one); the filters state (`src/core/domain/search-filters.ts`, §6) only builds valid params: one searchable format of the current kind, cleared on a kind change. `TopParams.format` (C-08) follows the same rule: a format of the other kind or one without a provider type is a `RangeError` before any request; the Discover manga chips offer only `SEARCHABLE_MANGA_FORMATS`. It is a field of the params, not a request option, because it changes the result and the cache key (`queryKeys.top`, §6), which the request options never do.
- The interface file holds types only, no Zod: raw payloads are parsed inside each adapter.
- Request priority (C-06): the paged methods (`search`, `getTop`, `getCurrentSeason`) take an optional last `CatalogRequestOptions`. `priority: 'foreground'`, the default, is for what the user is looking at; `'background'` is for a prefetch (the next page of the search, top or season list shown, §6 "Catalog lists"), which never delays a foreground request in the provider's rate limiter, and which a foreground call of the same request joins and promotes (§6, "Rate limiting"). It is a scheduling hint only: the result, the errors and the cache key do not depend on it. `getDetail` and `getGenres` take no options: nothing prefetches them. An adapter that ignores it treats every request as foreground; the Jikan-compatible adapter passes it to its http client, and the failure monitor forwards it with the other arguments.
- Media identity (ADR-0013): a `MediaKey` is `{ namespace, kind, externalId }`. The namespace (`MEDIA_ID_NAMESPACES`, today only `mal`) says whose ids `externalId` holds, never which server returned them: Tenrai and a self-hosted Jikan both serve `mal` keys, so switching instance keeps the cache and the library rows. A provider returns keys in its `namespace` only and rejects any other namespace with a `RangeError` before any request. `instanceId` identifies the configured instance in error reports only.
- Search text limit: `searchQueryMaxLength` (a positive safe integer) is the longest search text the provider accepts, in UTF-16 code units after trimming; longer text, and text with a lone surrogate, is a `RangeError` before any request. It is on the interface because routes and features cannot import an adapter: the search field is capped with it, and `prepareSearchQuery` (`src/core/domain/search-query.ts`, §6) cuts and cleans the text with it, so a prepared query is always accepted. The Jikan-compatible adapter exposes `JIKAN_QUERY_MAX_LENGTH` (300, Tenrai's `q` maximum) for every instance.
- Genre limit: `searchGenresMax` (a positive safe integer) is the most genre ids `search` accepts in `genresIncluded`, and separately in `genresExcluded`, counted after normalization (deduplicated, `normalizeSearchParams`); more ids in either list is a `RangeError` before any request. It is on the interface for the same reason as the text limit: the filters sheet passes it to the genre cycle (`cycleGenre`, §6), which never fills a list beyond it, so the genre filters it builds are always accepted. The Jikan-compatible adapter exposes `JIKAN_GENRE_IDS_MAX` (25, Tenrai's maximum per list) for every instance.
- Image hosts (L-04): `imageHosts` lists the lowercase CDN hosts the provider's image URLs come from, the hosts its adapter keeps with `toAllowedImageUrl` (§9). It is on the interface because a library snapshot cover read back from storage is untrusted (the entry schema checks only `https://`, the length and storable text): the library list passes the cover of each entry of the provider's namespace through `toAllowedImageUrl(url, provider.imageHosts)` before rendering, and gives `null` for any other namespace (§6 "Library"). The Jikan-compatible adapter exposes `JIKAN_IMAGE_HOSTS` for every instance, so a configured base URL never widens it.
- Year filter: `yearFrom` Y (four digits, 1000..9999) means "from Y onwards": titles whose airing or publishing started on or after Y-01-01, still running or not; the end of airing is never bounded. Decided in C-05 from the recorded Tenrai probe (2026-10-14, `__fixtures__/tenrai/year-probe-*.json`): `start_date` bounds the start of airing and `end_date` its end, so One Piece (mal 21, airing since 1999-10-20) is missing from `start_date=1999-01-01&end_date=1999-12-31` and listed with `start_date=1999-01-01` alone. A year range ("aired entirely within Y") dropped titles still airing or spanning two years. "Started in Y" would need a forced start-date sort and a client-side cut at the first later year, which overrides the user's sort (FR-03) and breaks server pagination (FR-04, every page would have a variable size); dropping the filter would lose an FR-03 filter.

Adapter rules:

- Raw provider responses are parsed with Zod inside the adapter, then mapped to the normalized types. Nothing provider-specific (field names, GraphQL documents, query parameters, hosts) exists outside the adapter folder: lint rejects `jikan.moe` and `tenrai.org` literals outside `src/core/catalog/jikan/` (`tools/eslint/syntax-guards.mjs`), and the layer zones keep the implementation folders out of everything but `app/_layout.tsx` (§2).
- Every request goes through the provider's `CatalogHttpClient` (`getJson(url, signal?, options?)`, `src/core/catalog/http/`, §6), which rate limits, deduplicates and retries: one client, hence one rate limiter with that instance's own limits, per provider instance, used only by that adapter; the adapter never calls `fetch` itself and passes the caller's `AbortSignal` through, and the request priority of the paged methods. Adapters build deterministic https URLs (stable parameter order, from `normalizeSearchParams` for search), so equivalent requests share one dedup key, parse the body with Zod and map a parse failure to `CatalogResponseError`. The client is GET only: a POST provider (AniList GraphQL) would extend it with a dedup key that includes the body.
- The adapter never filters adult content in requests (ADR-0004).
- Contract suite: every adapter passes `describeCatalogProviderContract(harness)` (`test/core/catalog-provider-contract.ts`, written against the `CatalogProvider` interface only), run once per adapter and per instance: the Jikan-compatible adapter runs it for Tenrai and for a self-hosted instance. The harness creates the provider and serves the adapter's own payloads for the scenarios page, empty-page, detail, genres, adult-genre, adult-rating, server-error, rate-limited, malformed, hanging and foreign-image (a page whose covers are outside the adapter's image allowlist: another host, `http`), and supplies the adapter's predicate telling whether a request carries a content filter and its image hosts (`allowedImageHosts`; the Jikan-compatible harness passes `JIKAN_IMAGE_HOSTS`). Search text limit cases: `searchQueryMaxLength` is a positive safe integer; a query of exactly that many code units is sent (one request); one unit more rejects with a `RangeError` and sends no request. Genre limit cases, the same shape for `genresIncluded` and for `genresExcluded`: `searchGenresMax` is a positive safe integer; exactly that many distinct genre ids (1..max) are sent (one request); one distinct id more rejects with a `RangeError` and sends no request; max + 1 ids holding one duplicate (max distinct) are sent, since the limit counts after normalization. Cover cases (§9): on the page and detail scenarios every `imageUrl` is `null` or equal to `toAllowedImageUrl(imageUrl, allowedImageHosts)`, and at least one is not `null` (the payload has covers); on foreign-image every `imageUrl` is `null`.
- Adding a provider = a new folder next to `jikan/` (added to `CATALOG_ADAPTER_FOLDERS`, `tools/eslint/layers.mjs`), with its own namespace unless it decides a mapping to an existing one, its fixtures, and the contract suite.
- The provider and its instance are selected only in the composition root (`app/_layout.tsx`, §2); hooks and screens see the `CatalogProvider` interface.

Sustained failure reporting (`src/core/catalog/catalog-failure-monitor.ts`, ADR-0013, A-05 in ADR-0017): `monitorCatalogProvider(provider, { reporter, now?, isOnline? })` wraps any `CatalogProvider`, platform-agnostic, with the clock and the `ErrorReporter` injected, and returns its results and errors unchanged. It passes every call's arguments through unchanged (the request options included, so a prefetch stays background), and forwards the provider's fields as they are (`namespace`, `instanceId`, `searchQueryMaxLength`, `searchGenresMax`, `imageHosts`; a test asserts each).

- Counted kinds (`CATALOG_FAILURE_KINDS`, `src/core/errors/catalog-errors.ts`): `server_error` (HTTP 500 or above), `rate_limited` (429), `client_error` (any other non-2xx but 404), `timeout`, `malformed_response`, and `network` (a `CatalogNetworkError`, counted only while the injected `isOnline()` is true: the composition root passes `isDeviceOnline`, §6; without the option, network errors are never counted), as the provider surfaces them, after the http client's own retries.
- A failure shared by several callers is counted once: the http client rejects every caller of one request in flight (a foreground call that joined a background prefetch, §6) with the same error object, and the monitor keeps the counted errors in a `WeakSet`. Accepted exception: a malformed payload is parsed by each adapter call, which throws its own `CatalogResponseError`, so `malformed_response` is counted once per caller.
- Ignored, neither counted nor resetting the streak: a 404 (`isCatalogNotFoundError`, shared with the detail screen's not found state; a normal answer for a missing title: gaps in MAL ids, a stale library row, a deep link to a missing id), network errors while the device is offline (an offline device and a provider outage at the DNS or TCP level look the same), aborts, input `RangeError`s and unknown errors. A success clears the streak. Accepted trade-off: a self-hosted base URL with a wrong path answers only 404s, so the monitor never reports it.
- Sustained = 3 counted failures since the last success, each within 2 minutes of the latest one. Reaching the threshold reports the kind of the failure that reached it, at most once per kind per 30 minutes per instance, and clears the streak.
- The report is `captureError(new CatalogProviderFailureError(kind), { source: 'catalog', tags: { instance: instanceId, kind } })`: the instance id and the kind only, never a URL, query, status code or response text (§9).

Jikan-compatible adapter (`src/core/catalog/jikan/`, C-03, ADR-0013):

- One adapter for every Jikan v4 instance. Instances (`jikan-instances.ts`): `JikanInstance { id, baseUrl, rateLimit }`; `TENRAI_INSTANCE` (id `tenrai`, base `https://api.tenrai.org/v1`, `TENRAI_RATE_LIMIT`) is the default; `selfHostedJikanInstance(baseUrl)` (id `jikan-self-hosted`, `SELF_HOSTED_JIKAN_RATE_LIMIT`); `jikanInstanceFor(baseUrl | undefined)` gives Tenrai for `undefined` and a self-hosted instance for a URL. The composition root passes the optional `jikanBaseUrl` of the parsed app env (`EXPO_PUBLIC_JIKAN_BASE_URL`, §10). The instance id is a fixed constant, never derived from the URL.
- Factory: `createJikanCatalogProvider(instance, options?)` returns a `CatalogProvider` with namespace `mal`, `instanceId` the instance id, `searchQueryMaxLength` `JIKAN_QUERY_MAX_LENGTH`, `searchGenresMax` `JIKAN_GENRE_IDS_MAX` and `imageHosts` `JIKAN_IMAGE_HOSTS`, and builds its own catalog http client from `instance.rateLimit`; `options` are the client options without `rateLimit` (`retry`, `timeoutMs`, `random`, `now`, `wallClock`, for tests). Client errors pass through unchanged. The composition root creates it, wrapped in the failure monitor (§2).
- Endpoints (`jikan-urls.ts`), relative to the instance base URL: `search` → `/anime` or `/manga`; `getDetail` → `/{kind}/{externalId}`; `getTop` → `/top/{kind}`, with `type` from the search type table below when `format` is set (`/top/{kind}?type=…&page&limit`; probed on Tenrai in C-08: `/top/manga?type=manhwa` returns only Manhwa items), never a filter; `getCurrentSeason` → `/seasons/now`, parsed as anime, without the `continuing` parameter: Tenrai still lists titles airing from earlier seasons, and discovery keeps them (C-08), since a client-side cut by season and year would give pages of variable size and a wrong `lastPage` (the reason "started in Y" was rejected for the year filter); a self-hosted Jikan without `continuing` lists only the season's new titles, an accepted difference (C-10); `getGenres` → `/genres/{kind}`, every category, explicit genres included. Paginated requests end with `page` and `limit=25` (`JIKAN_PAGE_LIMIT`: the public Jikan maximum and Tenrai's default, so every Jikan v4 instance accepts it; Tenrai allows 100). URLs are built as strings, the search text with `encodeURIComponent`, never with `URL` / `URLSearchParams`, whose React Native polyfills are incomplete. Search params go through `normalizeSearchParams`, then are written in a fixed order, absent ones left out: `q`, `type`, `status`, `min_score`, `genres`, `genres_exclude`, `start_date`, `order_by`, `sort`, `page`, `limit`; `end_date` is never sent (year filter, above). No content filter is ever sent: no `sfw`, `sfw-strict`, `rating`, `unapproved` or `continuing`, though Tenrai supports `rating` (ADR-0004).
- Search values: status `ongoing` / `finished` / `upcoming` → `airing` / `complete` / `upcoming` for anime, `publishing` / `complete` / `upcoming` for manga; sort `popularity` → `order_by=members` (MAL `popularity` is a rank, 1 the most popular, so `members` keeps the meaning of `asc` / `desc`), the other sort fields by name; `minScore` rounded to two decimals; genre ids comma-separated. Jikan takes one `type` per search: `formats` holds at most one format, which needs a Jikan search type (`light_novel` → `lightnovel`, `one_shot` → `oneshot`, `doujinshi` → `doujin`, the others by name); `oel` and `unknown` have none and are not searchable. `yearFrom` Y → `start_date=Y-01-01` alone (`jikanStartDateFrom`, the only place reading a year as a date), never `end_date`: "from Y onwards" (see "Year filter" above; the year probe `year-probe-open.json` is the recorded evidence that `start_date` alone keeps titles still airing).
- Input guards: each method builds its URL before calling `getJson`, so invalid input throws a `RangeError` before any request; the message holds no value and never the search text. Rejected: an unknown kind, status or sort, a page that is not a positive safe integer, a detail key outside the `mal` namespace, an external id outside 1..`EXTERNAL_ID_MAX`, a genre id that is not a positive safe integer, more than 25 included or more than 25 excluded genre ids (Tenrai's maximum per list), a minimum score outside [0, 10], a `yearFrom` that is not a four-digit integer, several formats, a search or top format of the other kind or one without a search type, search text longer than 300 UTF-16 code units (Tenrai's `q` maximum), and search text with a lone surrogate (`encodeURIComponent` cannot encode it).
- Parsing (`jikan-schemas.ts`, `jikan-fields.ts`, from the published OpenAPI spec, checked against the recorded Tenrai responses; unknown keys stripped): the whole response fails with `CatalogResponseError` when an item's identity (`mal_id`, an integer in 1..`EXTERNAL_ID_MAX`), default title (the first non-blank `Default` entry of `titles[]`, else the deprecated `title`), status (one of the documented anime or manga statuses; `null` fails) or BR-06 inputs (§7) are wrong, or when the pagination (`last_visible_page`, `has_next_page`) is missing or malformed; the Zod issues are dropped, since they could quote provider text. Display fields never fail a response; a missing or invalid one becomes `null`: English and native titles (`titles[]`, then the deprecated field), synopsis (trimmed, blank is `null`), score (in (0, 10]; Jikan sends 0 or `null` for an unscored title), episode or chapter count (a positive integer within the Postgres `integer` bound of `media_total_units`), year (four digits: anime `year`, then `aired.prop.from.year`; manga `published.prop.from.year`) and cover (§9). A `null` or unrecognized `type` maps to the `unknown` format, and so do `CM` and `PV`; `TV Special` maps to `special`. An id repeated within a page keeps its first item, adult when any copy of the id is adult (BR-06 fails closed); the page's `page` is the requested page and `lastPage` at least 1. A detail response for another `mal_id` than the requested `externalId` fails.
- Genres: an item's `genres` are its `genres`, `explicit_genres`, `themes` and `demographics`, in that order, deduplicated by id (the first wins); `getGenres` deduplicates the same way, in the provider's order. The cover is the first allowed URL among `webp.large_image_url`, `jpg.large_image_url` and `jpg.image_url`.
- Recorded facts (Tenrai, 2026-10-14, `__fixtures__/tenrai/`): response `type` values are capitalized as documented ("TV", "ONA", "Movie", "Manhwa"…); `titles[].type` values include `Default`, `Japanese`, `English`, `Synonym` and language names; no `null` anime status was observed (a `null` still fails the response); every item of search, top, season and detail carries the four genre arrays and, for anime, the `rating` key, so the fail-closed BR-06 inputs (§7) hold; `pagination` has extra keys (`current_page`, `items`), which are stripped.

## 4. Repositories

```ts
// src/core/repositories/library-repository.ts (types only)
export interface LibraryRepository {
  list(): Promise<readonly LibraryEntry[]>;          // updatedAt desc, ties by key ascending
  get(key: MediaKey): Promise<LibraryEntry | null>;
  save(entry: LibraryEntry): Promise<LibraryEntry>;  // insert or replace; resolves to the stored entry
  remove(key: MediaKey): Promise<void>;              // no-op when missing
}

export interface GuestLibraryRepository extends LibraryRepository {
  removeUnchanged(entries: readonly LibraryEntry[]): Promise<void>; // after a successful merge (BR-08, A-04)
  clear(): Promise<void>;                            // the device purge (FR-25, A-06, ADR-0018), never the merge
}

export interface LibraryCallOptions { readonly signal?: AbortSignal }

export interface AccountLibraryRepository extends LibraryRepository {
  mergeGuestEntries(entries: readonly LibraryEntry[], options?: LibraryCallOptions): Promise<void>; // BR-08, FR-22 (A-04, ADR-0016)
}

export interface RemoteAccountLibraryRepository extends AccountLibraryRepository {
  replayWrites(writes: readonly LibraryQueuedWrite[]): Promise<readonly LibraryReplayOutcome[]>; // A-05, ADR-0017
}

export interface LibraryReplayRun {
  readonly status: 'done' | 'offline' | 'failed' | 'signed-out' | 'aborted';
  readonly confirmed: number;                        // writes the run removed from the queue
}

export interface OfflineAccountLibraryRepository extends AccountLibraryRepository {
  replayQueuedWrites(options?: LibraryCallOptions): Promise<LibraryReplayRun>;
  subscribeToQueuedWrites(listener: () => void): () => void; // a write stayed queued
  queuedWriteCount(): number;                        // writes not confirmed yet (A-06, ADR-0018)
  purgeDeviceData(): void;                           // closes this user's instances, deletes the copy and the queue
}
```

Three implementations: the account store in `supabase/` (`RemoteAccountLibraryRepository`, A-03), the offline account library in `local/` over it (`OfflineAccountLibraryRepository`, A-05: the device copy and the write queue of the signed-in user) and the guest store in `local/` (L-02). The active library is chosen from the session state by `SessionLibraryContextProvider` (see "Library switch" below): the guest store, or the offline account library of the user signed in; hooks do not know which one they use, and nothing but the offline account library calls the account store.

- Async, so one interface fits the device store and the network. Entries are whole domain `LibraryEntry` values (§5): callers build them with the L-01 rules and skip `save` when a rule returns the same reference (BR-09); there is no partial input type.
- No filter parameter: a library is small (hundreds of entries), so `list()` returns every entry and the hooks filter, group and sort with `select` over the one list query `['library', scope]` (L-04; the favorites tab of L-05 too, `favoritesOnly`, §6), the adult filter included (BR-06, `applyContentFilter`, §7), so a filter change never refetches. The Supabase implementation reads the rows page by page with `range` inside `list()` (see "Account store" below), ordered on `(updated_at desc, id_namespace, media_kind, external_id)`, a total order.
- Order: `updatedAt` descending, then the key ascending (namespace and kind in the order of `MEDIA_ID_NAMESPACES` and `MEDIA_KINDS`, the Postgres enum order, then `externalId`), defined on the returned values: the Supabase implementation sorts after normalizing the timestamps to milliseconds, since two rows apart by microseconds can become equal.
- Every returned entry has passed `libraryEntrySchema` (§5): within the database limits, timestamps in the `Date#toISOString` form, so `updatedAt` values compare as plain strings.
- `save` inserts the entry of `entry.key` or replaces it and resolves to the stored entry, which callers keep: the local implementation returns the entry normalized by the schema, the Supabase one the row with the server `createdAt` / `updatedAt` (§5). Replacing keeps the stored `createdAt` in both, since a client never writes `created_at`. An entry the schema rejects (database limits, BR-07) rejects with a `RangeError` whose message holds no value, and nothing is written; the UI validates user input first (`isValidScore`, `isValidNotes`, `isValidProgress`), so this is a programming error, not a user-facing one.
- Concurrency: the interface does not order concurrent calls; the library hooks serialize every repository call of one key through the library writer's per-key queue (L-03, §6 "Writes"): writes, and reads too, which first start the key's pending coalesced change, so a read never returns a state older than a write. Calls of different keys stay independent. Storage and network failures reject the promise, never swallowed: the guest store with the storage's error, the account store with a `LibraryRemoteError` (below). The offline account library is the exception for a write it keeps queued (offline, `network`, `signed-out`): the call resolves with the queued state, and the change is replayed later (see "Offline account library" below).
- One repository instance holds one owner's library for its whole life: the account store is created for one user id and never follows a later session (see "Account store", the session guard).
- `removeUnchanged` and `clear` exist only on `GuestLibraryRepository`: the account library is removed from the server by account deletion only (`AuthRepository.deleteAccount`, A-06), and from the device by `OfflineAccountLibraryRepository.purgeDeviceData` (see "Offline account library" below). `clear` is the device purge of a sign out or an account deletion (FR-25, ADR-0018), never the merge.
- Guest merge (BR-08, FR-22, A-04, ADR-0016): `AccountLibraryRepository.mergeGuestEntries(entries)` has the database apply the BR-08 rule (stated by `guestMergeDecision`, `src/core/domain/guest-merge.ts`) at the write, through the function `merge_guest_library_entries`, each entry with its own `updatedAt` capped at the server's now (§5, "Account store" below); `mergeGuestLibrary` (`src/core/hooks/guest-merge.ts`, run by the library switch below) reads `guest.list()`, passes those entries to `mergeGuestEntries`, and only once it resolved, and while the session is still the one it ran for, removes exactly them from the device with `removeUnchanged`, so a failed or interrupted merge loses nothing and can be retried. The local store only ever holds entries the database accepts (`save` validates, reads parse), so the merge cannot fail on a constraint.
- Personal data: entries hold notes and titles; implementations never log them and never put them, or a key, in an error message or a report tag.

Guest store (`src/core/repositories/local/library-repository.ts`, L-02): `createLocalLibraryRepository(storage, { reporter })` returns a `GuestLibraryRepository` over the core `StorageAdapter` (MMKV on mobile) and the `ErrorReporter`. The composition root creates it at module level over the app storage and gives it to the library switch (§2, "Root layout"; "Library switch" below), which merges it into the account at sign in (A-04).

- One key, `guest-library` (`GUEST_LIBRARY_STORAGE_KEY`), holding a JSON envelope `{ "version": 1, "entries": [...] }` of entries in the domain shape.
- No in-memory cache: the storage is the single source of truth. Each method reads, changes and writes synchronously inside the call, with no `await` between the read and the write, so calls never interleave and apply in call order.
- Every read parses the stored content, which is untrusted: invalid JSON or an invalid envelope (an unknown version included) reads as an empty library; an entry `libraryEntrySchema` rejects is dropped; of entries with the same key, the most recent `updatedAt` is kept (the first stored on a tie). Each kind of problem is reported through the reporter with a `LibraryStorageError` (`src/core/errors/library-errors.ts`; `reason` a `LibraryStorageReason`: `invalid-json`, `invalid-envelope`, `invalid-entries`, `duplicate-keys`; `{ source: 'library-storage', tags: { reason } }`), at most once per repository instance and reason, and never thrown on read: the stored content, a title, notes or a key never appear in the message or the tags. The next write replaces the stored document with the entries read plus the change: a damaged store loses what could not be read (accepted: it could not be merged either). This holds for the merge too (A-04): `list()` leaves such an entry out, so the merge never sends it, and the write of the `removeUnchanged` that follows a successful merge deletes it with the merged entries; the envelope versions below keep a newer version from writing, under this key, entries an older reader rejects.
- `save` validates with `libraryEntrySchema` before writing and stores the normalized entry; `remove` of a missing key writes nothing; `clear` deletes the key. A failed storage write rejects the promise.
- `removeUnchanged(entries)` (A-04, ADR-0016), in the same single synchronous read, change and write: removes each stored entry equal field by field to one of `entries` (`isSameLibraryEntry`: the key, the snapshot and every other field, `createdAt` and `updatedAt` included), so an entry changed or added since the merge listed the store stays and the next merge sends it; writes nothing when no stored entry matches, and deletes the key when no entry remains.
- Envelope versions: a later version must stay readable by the version 1 reader, or use a new key. An older bundle can run on newer data (an EAS update rolled back, or expo-updates returning to the embedded bundle after a failed launch, §10): its reader would read a newer version as empty and replace it on the next write, losing the guest's only copy. The same holds for the entries: an older reader drops an entry its `libraryEntrySchema` rejects and the next write deletes it, so the guest entry schema may only be widened in a way older readers accept; a change that adds an enum value older readers do not know (a new `MediaIdNamespace` such as `anilist`, a format or a status) or tightens a check needs a new envelope version under a new key, with a migration from the old one.
- Cost: each call parses the whole document and each write serializes it, linear in the library size; fine for hundreds of entries, and `+1` taps are coalesced into one write (BR-09, §6).

Account store (`src/core/repositories/supabase/library-repository.ts`, A-03, FR-23): `createSupabaseLibraryRepository(client: SupabaseClient<Database>, { userId, reporter }: SupabaseLibraryRepositoryOptions)` returns the `RemoteAccountLibraryRepository` of one signed-in user over the app's Supabase client (§8): `userId` is the `AuthSession.userId` it is created for, `reporter` the `ErrorReporter`. The composition root gives it as `remoteFor` to the offline account library factory (§2 "Root layout", "Offline account library" below), whose `accountLibraryFor` the library switch calls once per user id. No `clear`: the account library is removed from the server by account deletion only, through the foreign key cascades (A-06, §5). The store, its guest merge (`mergeGuestEntries`, `library-merge.ts`, A-04, ADR-0016) and its replay (`replayWrites`, `library-replay.ts`, A-05, ADR-0017) share the request helpers of `library-requests.ts`: `createLibraryRequests(client, { userId, reporter })` returns `fail` (map and report a failure), `run` (an error thrown that is not already a `LibraryRemoteError` becomes `unknown`), `send` (one request behind the session guard and the timeout, its error response rejected) and `readAllRows` (the paged read), with the constants `LIBRARY_PAGE_SIZE`, `LIBRARY_REQUEST_TIMEOUT_MS`, `LIBRARY_TABLE` and `LIBRARY_CONFLICT_TARGET`.

- Rows (`library-row.ts`, next to the implementation: column names are the Supabase implementation's concern, and the value rules it reuses already live in `src/core/schemas/library-entry.ts`). `LIBRARY_ROW_COLUMNS` is the explicit select list, never `*`: `id_namespace, media_kind, external_id, media_title, media_image_url, media_format, media_total_units, media_is_adult, status, progress, score, notes, is_favorite, started_at, finished_at, created_at, updated_at` (no `id`, no `user_id`). `parseLibraryRow(row: unknown): LibraryEntry | null` requires an object holding every selected column, maps it to the domain shape (`key` from `id_namespace`, `media_kind`, `external_id`; `media` from the `media_*` columns; the rest by name) and parses that with `libraryEntrySchema`, the only value check, so the account side accepts exactly what the guest side does; `timestampSchema` turns the `+00:00` microsecond timestamps of PostgREST into the `toISOString` form (§5). `toLibraryRowPayload(entry)` (`LibraryRowPayload`) is the inverse for writes, typed from `TablesInsert<'library_entries'>`: every writable column (§5 "Grants"), never `id`, `user_id`, `created_at` or `updated_at`, and always `id_namespace` (no default, ADR-0013) and `media_is_adult` from the snapshot (no default, BR-06, §5). The merge sends it with the entry's `updatedAt` as `updated_at`, which only the merge function writes (A-04).
- `list()`: pages of `LIBRARY_PAGE_SIZE` (1000, the `max_rows` of `supabase/config.toml` and of the hosted projects' defaults) read with `.select(LIBRARY_ROW_COLUMNS, { count: 'exact' })`, `.eq('user_id', userId)` on top of RLS, `.order()` on `updated_at` descending, then `id_namespace`, `media_kind`, `external_id` ascending, and `.range(offset, offset + LIBRARY_PAGE_SIZE - 1)`. The offset advances by the rows received, never by the page size, and reading stops at a page without rows or once the offset reaches the count of that response: a project whose `max_rows` is below the page size returns shorter pages, which are never taken for the end, so the list is never truncated. The rows are then parsed, deduplicated by key keeping the most recent `updatedAt` (a row updated on another device between two pages can be read twice), and sorted in the interface order after the timestamp normalization (`compareLibraryEntries('updated')`, `src/core/domain/library-view.ts`), since two rows apart by microseconds can become equal. Accepted: a row moved the other way between two pages, or a row deleted on another device between two pages (which shifts the later rows back by one), makes the read miss a row until the next refetch; it needs more than one page (over 1000 entries) and a write on another device during the read; keyset paging would remove it if libraries grow that large, and the list is always revalidated (§6).
- A row `parseLibraryRow` rejects (a value a newer app version wrote, such as a format or a status this version does not know) is left out of `list()`, never deleted or rewritten, and reported (`invalid-row`, below); `get` of its key rejects with `LibraryRemoteError('invalid-row')`, so the detail shows its read error and the user cannot overwrite a newer version's row by adding the media again. Unlike the guest store, which drops what it cannot read on its next write (above), nothing is lost: the row stays on the server for the newer version. The guest merge is the exception (A-04, below): the database compares the times only, whatever the row's other values, so a guest entry newer than such a row replaces its values, as BR-08 wants the most recent copy to win.
- `get(key)`: the same columns, `.eq()` on `user_id`, `id_namespace`, `media_kind` and `external_id`, `.maybeSingle()`: no row is `null`.
- `save(entry)`: validates with `libraryEntrySchema` first (a `RangeError` with no value and nothing sent, like the guest store), then `.upsert(toLibraryRowPayload(entry), { onConflict: 'user_id,id_namespace,media_kind,external_id' }).select(LIBRARY_ROW_COLUMNS).single()`, and resolves to the returned row, parsed: the server `createdAt` (kept on a replace, since the payload never holds `created_at`) and `updatedAt` (set by the trigger). `user_id` takes its `auth.uid()` default on insert, which the conflict target matches. A returned row the schema rejects rejects with `invalid-row` (the write happened; the writer then refetches the entry).
- `remove(key)`: `.delete()` with `.eq()` on `user_id` and the key, no returned row; a missing key is a no-op.
- Session guard: before every request (`send`), reads and writes, each page of `list()` and each merge and replay call included, the repository reads `client.auth.getSession()` and goes on only when it holds a session whose user id is `userId`; with no session or another user's, the call rejects with `LibraryRemoteError('signed-out')` and sends nothing. A session read that fails (an error result or a thrown error, such as a token refresh failing offline) rejects with `network`, never `signed-out` (A-05: it is transient, so a write stays queued and a read falls back to the device copy), and sends nothing. The guard runs under the request's timeout (below): supabase-js reads the session storage behind a lock, with no timeout of its own, so a session read that does not answer in time rejects with `network`, and nothing is sent (A-04). A stalled token refresh, which supabase-js runs one at a time with no timeout of its own and which every later session read waits for, is released by the client's own fetch bound (`SUPABASE_FETCH_TIMEOUT_MS`, 30 s, §8). Reason: after a switch the old writer flushes its pending changes to the repository they were made for (§6 "Writes"); without the guard, user A's change would be sent as anon after sign out (refused by the grants), or into user B's library after A → B through an email link (accepted by RLS, since the request would carry B's token). Accepted residual window: supabase-js reads the token again for the request itself, so a session change landing between the guard and that read still sends the request with the new token; RLS keeps it inside the token's own library, and the window is one session storage read. Cost: one more session read (the secure store on mobile) per request.
- Timeout: each request carries an `AbortSignal` (`.abortSignal()`) aborted after `LIBRARY_REQUEST_TIMEOUT_MS` (15 s), per page for `list()` and per merge or replay call; its one timer (a plain controller and timer: React Native polyfills `AbortController` without `AbortSignal.timeout`) covers the session guard's read and the request. React Native's fetch has no timeout of its own, and a stalled request would keep the library loading and block the writer's queue of its key (and the `flushAll` of a switch). A timeout rejects with `network`; an aborted write may still have been applied, which the writer's refetch after the failure then shows.
- Errors: every rejection but the save validation's `RangeError` is a `LibraryRemoteError` (`src/core/errors/library-errors.ts`) with a `reason` from `LIBRARY_REMOTE_REASONS`, mapped by `toLibraryRemoteError` (`library-error-mapper.ts`) from the PostgREST response: `network`, no response (status 0: a lost connection, the timeout), a gateway status 502, 503 or 504, a 408 or 429 (try again later, never reported, so a replay batch backs off instead of being split, A-05), or a session read error (A-05); `signed-out`, the session guard (no session, another user's), a 401 response (an expired or invalid token), an answer row of another user from a merge or replay call (A-04, A-05), or a replay call the function refuses for its caller (`42501`: no user, or not `expected_user_id`, A-05); `rejected`, any other 4xx response (a check, not-null, unique or privilege refusal, an RLS refusal, an unknown column or enum value, an input the merge function refuses with `22023`): `save` and the merge validate first and their payloads name granted columns only (and `updated_at` for the merge function), so this is a programming error or a schema drift (an older binary against a newer database); `invalid-row`, a row `parseLibraryRow` rejects; `unknown`, anything else (another 5xx, an error thrown by the client, a response without its row, a merge or replay answer that does not parse or does not hold each key of its call exactly once). The message is fixed per reason; no `cause`, no server text: a PostgREST message or detail can quote the row (a `23505` detail holds the user id and the media key). The screens show one neutral read error and the write error, and do not branch on the reason in A-03.
- Reporting, through the injected `ErrorReporter` like the auth repository: `{ source: 'library-remote', tags: { operation, code?, status? } }` (`libraryReportContext`), `operation` one of `list`, `get`, `save`, `remove`, `merge`, `replay` (`LibraryOperation`); `code` the Postgres or PostgREST error code only when it matches `^(?:[0-9A-Z]{5}|PGRST[0-9]{3})$` (a SQLSTATE such as `23514`, or `PGRST204`); `status` the HTTP status when a response came. `rejected` and `unknown` are reported each time, `invalid-row` at most once per repository instance (whatever the number of rows, never a count, a key or a value); `network` and `signed-out` are expected and never reported.
- `mergeGuestEntries(entries, { signal? })` (`library-merge.ts`, A-04; design and alternatives in ADR-0016): the signal is checked before each batch, and once aborted the merge rejects with `signed-out` and sends no further batch (A-05; a batch already sent completes). Every entry is validated with `libraryEntrySchema` first, an invalid one or two of one key rejecting with a `RangeError` without a value and nothing sent, and an empty list resolves without a request. Then batches of `GUEST_MERGE_BATCH_SIZE` (100, at most the function's `max_entries`), one after the other, each one `client.rpc('merge_guest_library_entries', { entries })` through `send` (the session guard and the timeout), each entry `toLibraryRowPayload(entry)` plus its `updatedAt` as `updated_at`, never `user_id`, `id` or `created_at`: the database takes the user from the token, caps each time at its `now()` and applies the newest-wins rule to the row as it is at the write, a batch written whole or not at all (§5 "Guest merge"). The answer, one row per entry (the key, `user_id`, `outcome` `written` or `kept`), is parsed with Zod: a row of another user (the residual window above) rejects with `signed-out`, not reported, and confirms nothing; an answer that does not parse, or does not hold each key of the batch exactly once, rejects with `unknown`, reported. A failed batch stops the merge; the batches before it stay written, and a call again with the same entries completes the merge to the same final entries (a written entry now carries the same time and is kept). A merged entry keeps its own `updatedAt`, capped at the server's now; an inserted one takes the merge time as `createdAt`, which can be later than its `updatedAt`.
- `replayWrites(writes)` (`library-replay.ts`, A-05, ADR-0017): at most `LIBRARY_REPLAY_BATCH_SIZE` (100, the function's `max_writes`) queued writes, each validated with `libraryQueuedWriteSchema` and no key twice, else a `RangeError` without a value and nothing sent; an empty list resolves `[]` without a request. Then one `client.rpc('replay_library_writes', { expected_user_id: userId, writes })` through `send`: a save as `toLibraryRowPayload(entry)` plus `op: 'save'` and its `updatedAt` as `updated_at`, a removal as `op: 'remove'`, the key columns and its `removedAt` as `updated_at`; never `user_id`, `id` or `created_at`. The user id is sent only as the function's guard. The answer (the key, `user_id`, `outcome` `written` or `kept`) is parsed with Zod: a `42501` refusal or a row of another user rejects with `signed-out`, not reported, so the device queue is kept and no write is taken for refused; an answer that does not parse or does not hold each key exactly once rejects with `unknown`, reported. Resolves with the outcomes in input order.

Offline account library (`src/core/repositories/local/account-*.ts`, A-05, FR-23, ADR-0017): `createOfflineAccountLibraries({ storage, remoteFor, isOnline, reporter, now? })` returns `(userId) => OfflineAccountLibraryRepository`, a new instance per call over `remoteFor(userId)` (the account store), the app `StorageAdapter`, `isDeviceOnline` (§6) and the reporter. It is the library the switch gives a signed-in user, so the account library reads and writes offline (SPEC "Offline").

- Per-user documents, keyed by the user id (checked as a UUID before any key is built, a `RangeError` without a value otherwise): `account-library-copy.<userId>`, the device copy of the last server state seen (the guest store's version 1 envelope and rules), and `account-library-queue.<userId>`, the write queue (`{ "version": 1, "nextSeq": n, "writes": [{ "seq", "write" }] }`, at most one `LibraryQueuedWrite` per key, the latest, each with a seq that never decreases). Both are untrusted and parsed with Zod on every read: an invalid element is dropped, an invalid queue document reads as an empty queue, an invalid copy document as no copy (never an empty one, which would answer `null` offline for entries the account holds); each problem is reported once per reason and document per factory (`LibraryStorageError`, `{ source: 'library-storage', tags: { reason, document } }`, `document` `account-copy` or `account-queue`), never thrown. Each operation reads, changes and writes synchronously inside the call, like the guest store. The copy is created only by a successful `list()` (complete); a per-key update changes an existing copy and never creates one.
- What the instances of one user share (the keys with a direct attempt in flight, the keys being replayed, the run in flight, the writes refused in this process, the queue listeners) lives in the factory, never in a module global. Instances of different users share nothing: user B's instance never reads or sends user A's queue or copy, and A's queue stays for A's next sign in.
- Write-ahead (`save`, `remove`): the input is validated first (`libraryEntrySchema`, the media key schema: a `RangeError`, nothing queued). The write is timed `queuedWriteTime(changeTime, knownUpdatedAt)` (the change time is a save's `updatedAt` or a removal's `now()`; the known time is the key's queued write's, else its copy entry's: a change is never timed at or before the state it was computed from), a save keeps `createdAt` from the copy, else from the earlier queued save, and the write replaces its key's queued write in the persisted queue before any request, so it survives the app being killed. Offline, or while a replay run is sending that key, the call resolves at once with the queued state and the queue listeners are notified. Otherwise a direct attempt with the regular request (`remote.save` / `remote.remove`, at the server time): a success removes the queued write if its seq is unchanged, updates the copy and resolves with the stored entry; `network`, `signed-out` or `unknown` (a 5xx, a thrown error: the server may have committed it) keeps it queued for this user (the key's attempt released first, then the listeners notified) and resolves with the queued state, an error that is not a `LibraryRemoteError` reported with source `library-replay`; only `rejected` or `invalid-row` removes it (the server refused it, or wrote it) and rejects, so the user sees the write error and the entry refetches, as before A-05.
- Reads (read your writes): `get` answers the key's queued write first (its entry, or `null` for a removal); `list()` overlays the queue on the server state (`overlayQueuedWrites`). Online, a success refreshes the copy (`list()` replaces it, `get` updates an existing one), keeping the state of a key confirmed while the read was in flight; `network` falls back to the copy. Offline, the copy overlaid with the queue; without a copy document, the read rejects with `network` (a first sign in offline shows the library's error state).
- Replay run (`replayQueuedWrites({ signal? })`): single flight per user (a call joins the run in flight unless it was aborted); offline it ends `offline` at once. It sends the replayable writes (no direct attempt of their key in flight, not refused in this process) by ascending seq, in batches of `LIBRARY_REPLAY_BATCH_SIZE` taken from the queue as it stands, one `remote.replayWrites` call each. Each confirmed write (`written` or `kept`) leaves the queue if its seq is unchanged, and a `written` one sets the copy. Retry policy: `network` and `unknown` are retried after each of `LIBRARY_REPLAY_RETRY_DELAYS_MS` (2 s, 10 s, 30 s; cut by the signal), then the run ends `failed`, the queue kept for the next trigger; `signed-out` ends the run at once, the queue kept, nothing reported. Refused writes: a `rejected` batch of several writes is sent again one write per call, and a write rejected alone stays queued but is not replayed again in this process (until the next launch, or a newer change of its key); the account store reports each `rejected` call. Any other error ends the run `failed`, reported with the source `library-replay`. `confirmed` counts the writes the run removed from the queue. A run interrupted and run again reaches the same final state.
- Count and purge (A-06, ADR-0018), for the sign out and the account deletion (§8): `queuedWriteCount()` is the number of writes in this user's queue now, whatever their state (waiting, being sent, refused in this process), read synchronously from the device, 0 once purged. `purgeDeviceData()` closes the coordination every instance of this user shares and drops it from the factory, then deletes both documents, synchronously, so no write of another instance lands between the closing and the deletion. From then on no instance created before, this one included, reads or writes either document or sends a request: `list`, `get`, `save`, `remove` and `mergeGuestEntries` reject `signed-out` (a late flush of a retired writer is refused, never queued), `replayQueuedWrites` resolves `{ status: 'signed-out', confirmed: 0 }` with nothing sent, the queue listeners are dropped. A call in flight ends without touching the documents: a direct write whose answer comes back after the purge rejects `signed-out` (the request already sent completes on the server, its outcome is not stored), and a replay run sends no further batch and ends `signed-out`, at once when it waits in its retry delay. The next instance of that user starts afresh (an empty queue, no copy); a second call on a closed instance does nothing, so it never deletes a later instance's documents. A storage failure still tries both deletions, then throws the first error, the coordination staying closed; the device purge reports it and goes on (§8 "Sign out purge").

Library switch (`src/core/hooks/SessionLibraryContextProvider.tsx`, A-03, A-04, A-05): `SessionLibraryContextProvider({ guest, accountRepositoryFor, reporter, subscribeToForeground?, children })`, with `guest: GuestLibraryRepository`, `accountRepositoryFor: (userId: string) => OfflineAccountLibraryRepository`, both stable (module level in the composition root), `reporter: ErrorReporter` and the optional foreground seam (`ForegroundSubscription`, `src/core/hooks/foreground.ts`; `src/platform/app-state.ts` on mobile), reads `useAuthSession()` and renders `LibraryContextProvider` with the repository of the session state:

- `signed-out`: `guest`.
- `signed-in`: `accountRepositoryFor(session.userId)`, memoized on the user id (`useMemo`): a token refresh keeps the instance (the session state keeps its object, §8), and another user, or the same user signed in again after a sign out, gets a new one. Each new instance first gets the guest library merged into it (below): `PENDING_LIBRARY_REPOSITORY` while the merge checks or runs and after a failure until a retry succeeds, the account instance once its merge succeeded (nothing to merge, or merged).
- `loading`: `PENDING_LIBRARY_REPOSITORY`, a module constant whose calls never settle, so the library screens show their loading state until the session is known: never the guest library to a signed-in user, nor an empty library. No write ever reaches it (library actions are enabled once an entry is loaded, which never happens there); its scope's queries are removed at the switch (§6 "Writes"), after which its writer and its never-settling calls are unreachable and collected.
- Never mixed, not even for one frame: the repository, its writer and its cache scope change in the same render (`LibraryContextProvider` builds them together), and every library query key holds the scope (§6 "Query keys"), so the first frame after a switch reads keys of the new scope only, which have no data yet (the loading state).
- Guest merge (A-04, BR-08, FR-22, ADR-0016): the merge phase (`checking`, `merging`, `failed`, `done`) is state held with the account instance it is about and derived for any other, so the first render of a new instance is already `checking` and the account library never shows, nor takes a write, before its merge succeeded. The run starts in an effect, once per account instance and once per retry; `retry` moves `failed` back to `checking` and is ignored in any other phase. A failed merge is also retried automatically when the device reconnects (`onlineManager`, A-05). It calls `mergeGuestLibrary({ guest, account, settleWrites, isCurrent, signal, onMerging })` (`src/core/hooks/guest-merge.ts`) → `'empty' | 'merged' | 'stale'`; `signal` is the run's `AbortController` signal, aborted a microtask after the commit that retires its account instance (only when that instance is no longer the committed one, so a StrictMode cleanup aborts nothing) and passed to `mergeGuestEntries`, which then sends no further batch (A-05): `settleWrites()` waits for the previous run of the provider (runs never overlap: a stale run of the same user signed in again still passes the session guard, and its later batches could write back an entry deleted meanwhile) and for the pending writes of the retired libraries (below), then `guest.list()`; an empty store ends `empty` without an account call; else `onMerging` moves to `merging`, `account.mergeGuestEntries(entries)`, then `guest.removeUnchanged(entries)`. `isCurrent` compares the run's instance with the committed one (a ref set in a layout effect, null once unmounted), checked once the writes settled, once the guest store was read and once the merge resolved: a stale run changes no state and removes nothing, and the next session's merge sends the entries (a merged entry merged again is kept, or written again at a later capped time when the device clock was ahead, BR-08). Pending writes: `LibraryContextProvider` reports each retired value to `onRetired` with its writer's `flushAll()` (§6 "Writes"); the switch keeps every flush not settled yet, but a retired pending library's, which never settles, and `settleWrites` waits for those reported when the run starts, so a `+1` still in its coalescing window at sign in reaches the guest store before the merge reads it. A failure of any step concludes `failed`: the library stays the pending one until a retry succeeds, so no Add or `+1` is ever computed on an account library lacking a guest entry (that write would make the account copy newer, and the next merge would keep it and remove the guest copy), the guest store whole; failures that are not a `LibraryRemoteError` (a guest store failure, a `RangeError`; the account store reports its own) are reported with `{ source: 'guest-merge' }`, stale runs included. `useGuestMerge()` (`GuestMergeContext`, `guest-merge-context.ts`) gives `{ status, retry }`, `status` one of `GUEST_MERGE_STATUSES`: `checking`, `merging`, `failed`, or `idle` signed out, while the session loads and once the merge concluded without failure.
- Replay driver (A-05, ADR-0017): inside its `LibraryContextProvider`, the switch renders `LibraryReplayDriver({ account, reporter, subscribeToForeground })` with the account instance once its merge is `done` (null otherwise). While that instance is the live library, the driver starts a replay run when it becomes live, on reconnect (`onlineManager`), on a return to the foreground and when the instance notifies a queued write; the triggers of one synchronous step start one run. After a run with `confirmed > 0` (kept writes included), it invalidates the live scope (`['library', scope]`), so the views read the server state. Its runs are aborted once the instance is no longer live (sign out, another user, unmount); a run that rejects is reported with the source `library-replay`. Never before the merge, never for a retired instance.
- Background flush (A-05): `LibraryContextProvider` subscribes once to `subscribeToForeground`, and going to the background flushes the current writer (`flushAll`), so a coalesced `+1` reaches the guest store or the account library's write-ahead queue before the app can be killed.
- The guest library stays on the device while a user is signed in until a merge into that user's account succeeds, which removes the merged entries from it. A sign out clears it once the merge concluded (`idle`), and keeps it while the merge is `checking`, `merging` or `failed`, so it shows again after sign out, whole, and the next sign in merges it (A-06, §8 "Sign out purge").
- Session libraries (A-06, ADR-0018): the switch also gives `SessionLibraryContext` (`useSessionLibrary()`, one memoized value) the account instance of the user signed in, whatever the merge phase (`null` signed out or while the session loads), and the guest repository: the sign out and the account deletion sync, count and purge that instance, even while the library shown is the pending one.

Implemented by `createSupabaseAuthRepository(client, { confirmationRedirectUrl, passwordResetRedirectUrl, reporter, oauth? })` in `src/core/repositories/supabase/auth-repository.ts`, with `oauth: { browser: OAuthBrowser; providers: readonly OAuthProvider[]; redirectUrl: string }` (without it, `oauthProviders` is `[]`); the redirect URLs are given by the composition root, so a web app passes https ones.

- Every rejection but `deleteAccount`'s (below) is an `AuthError` (`src/core/errors/auth-errors.ts`) with a `reason` from `AUTH_ERROR_REASONS`: `invalid-credentials`, `invalid-email`, `email-not-confirmed`, `weak-password`, `same-password`, `rate-limited`, `captcha-failed`, `link-invalid` (expired, used, or no matching verifier on this device), `oauth-failed` (a failed or mismatched OAuth redirect, a failed OAuth exchange, A-02), `network`, `unknown`. The message is fixed per reason; no email, password, code, token or server text, no `cause`. Supabase errors map by `code`: `invalid_credentials`, `email_not_confirmed`, `weak_password` and `same_password` to their reason; `over_email_send_rate_limit`, `over_request_rate_limit` and any 429 to `rate-limited`; `captcha_failed` to `captcha-failed`; `email_address_invalid` (GoTrue's address check, which differs from `z.email()`) to `invalid-email`, not reported; `flow_state_not_found`, `flow_state_expired`, `bad_code_verifier` and a missing verifier (`isAuthPKCECodeVerifierMissingError`) to `link-invalid`; a retryable fetch error (`isAuthRetryableFetchError`, a lost connection or a 5xx) to `network`; anything else to `unknown`. `completeEmailLink` rejects every failure as `link-invalid`: supabase-js deletes the flow's verifier on every failed exchange (a lost connection, a 5xx or a 429 included), so the link can never be retried; a cause the mapping reads as `unknown` is still reported with operation `complete-email-link`.
- `unknown` is the only reason reported, through the injected `ErrorReporter`: `{ source: 'auth', tags: { operation, code } }`, with the operation name (`sign-up`, `sign-in`…) and the Supabase error code only when it matches `^[a-z0-9_]{1,64}$` (a server-defined identifier such as `email_address_not_authorized`, which tells a misconfigured project apart). The other reasons are expected user errors, never reported.
- No account enumeration: `signUp`, `resendConfirmation` and `requestPasswordReset` resolve the same way whether or not an account exists, and the implementation never reads `user.identities` to tell them apart.
- `onAuthStateChange` maps every supabase-js event to `{ userId }` or `null`; the user id is parsed with Zod (a uuid), a session without one reads as signed out and is reported as `unknown`. The supabase-js callback is synchronous and only maps and forwards the session; listeners set state, async work belongs to the hooks.
- `signInWithProvider` (A-02, ADR-0015) resolves the session, or `null` when the user closed the browser or declined consent; it rejects with `oauth-failed`, `network` (the exchange lost the connection; a new tap starts a new flow), `rate-limited` (the exchange was rate limited) or `unknown` (a provider outside `oauthProviders`, a browser session that cannot start). The browser step is mobile-only and injected as an `OAuthBrowser` from `src/platform/` (A-09), like the storage adapters.
- `deleteAccount()` (A-06, FR-24, ADR-0018; `requestAccountDeletion(client, reporter)` in `src/core/repositories/supabase/account-deletion.ts`) rejects with an `AccountDeletionError` (`src/core/errors/account-deletion-errors.ts`, a fixed message per reason, no cause), not an `AuthError`. No session on the device: `session-expired`, nothing sent; a session read that fails or does not answer within `ACCOUNT_DELETION_TIMEOUT_MS` (20 s): `network`, nothing sent. Otherwise one `client.functions.invoke('delete-account', { method: 'POST', timeout: ACCOUNT_DELETION_TIMEOUT_MS })`, with no body and no user id (supabase-js adds the access token, from which the function takes the user, §8 "Account deletion"); the answer is parsed with Zod as `{ deleted: true }`. No answer (`FunctionsFetchError`: a fetch error, the timeout) or a 408, 429, 502, 503 or 504 is `network` (the outcome may be unknown); a 401 is `session-expired`, by its status alone, since the gateway answers a request without a valid JWT with its own body; anything else is `unknown` (another status, a relay error, a 2xx that does not parse, a thrown error), the only reason reported: the `AccountDeletionError`, never the supabase error, with `{ source: 'auth', tags: { operation: 'delete-account', status?, code? } }`, `code` the body's `error` only when it is one of the function's fixed codes. Those codes are copied as a client constant (`FUNCTION_ERROR_CODES`), since `src/core/` cannot import `supabase/functions/`: keep both lists in sync (A-10). Reading that body is bounded by the same timeout. `offline` is the hook's (§8). It neither purges nor signs out: `useDeleteAccount` does.

## 5. Data model (Supabase)

The migrations in `supabase/migrations/` are the source of truth; this excerpt shows the design.

```sql
create type public.media_kind as enum ('anime', 'manga');
create type public.media_id_namespace as enum ('mal');  -- whose ids external_id holds (ADR-0013)
create type public.library_status as enum ('current', 'planned', 'completed', 'paused', 'dropped');

-- profiles: one row per auth user
create table public.profiles (
  id uuid primary key references auth.users on delete cascade,
  preferences jsonb not null default '{}'::jsonb,  -- unused: the preferences stay on the device (§7, A-03)
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  constraint profiles_preferences_object_check check (jsonb_typeof(preferences) = 'object'),
  constraint profiles_preferences_size_check check (octet_length(preferences::text) <= 4096)
);

create table public.library_entries (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null default auth.uid() references auth.users on delete cascade,
  id_namespace public.media_id_namespace not null,  -- no default: every write names its namespace
  media_kind public.media_kind not null,
  external_id integer not null,  -- the integer type caps it at EXTERNAL_ID_MAX (src/core/domain/media.ts)
  -- per-user snapshot of the media, refreshed from the detail screen with the next library action (ADR-0009, §2)
  media_title text not null,
  media_image_url text,
  media_format text not null,
  media_total_units integer,
  media_is_adult boolean not null,  -- no default: every write sets it from the snapshot (BR-06)
  status public.library_status not null default 'planned',
  progress integer not null default 0,
  score smallint,
  notes text,
  is_favorite boolean not null default false,
  started_at date,
  finished_at date,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  constraint library_entries_external_id_check check (external_id > 0),
  constraint library_entries_media_title_check check (char_length(media_title) between 1 and 500),
  constraint library_entries_media_image_url_check
    check (media_image_url like 'https://%' and char_length(media_image_url) <= 2048),
  constraint library_entries_media_format_check check (char_length(media_format) between 1 and 32),
  constraint library_entries_media_total_units_check check (media_total_units > 0),
  constraint library_entries_progress_check check (progress >= 0),           -- BR-01 floor only
  constraint library_entries_score_check check (score between 1 and 10),     -- BR-07
  constraint library_entries_notes_check check (char_length(notes) <= 2000), -- BR-07
  constraint library_entries_user_media_key unique (user_id, id_namespace, media_kind, external_id)
);

create index library_entries_user_status_idx on public.library_entries (user_id, status);
create index library_entries_user_updated_idx on public.library_entries (user_id, updated_at desc);
create index library_entries_user_favorite_idx on public.library_entries (user_id) where is_favorite;

-- progress history for future statistics, written by trigger only
create table public.progress_events (
  id bigint generated always as identity primary key,
  entry_id uuid not null references public.library_entries on delete cascade,
  user_id uuid not null references auth.users on delete cascade,
  from_progress integer not null,
  to_progress integer not null,
  created_at timestamptz not null default now()
);

create index progress_events_entry_idx on public.progress_events (entry_id);
create index progress_events_user_created_idx on public.progress_events (user_id, created_at desc);
```

- The media snapshot is stored **per user** in `library_entries` instead of a shared `media` table: a shared table writable by clients would let any user alter titles or image URLs seen by everyone.
- Media identity (ADR-0013): a user has at most one entry per `(id_namespace, media_kind, external_id)`, the `MediaKey` of §3. `id_namespace` names whose ids `external_id` holds (today only `mal`), never the server that returned them, so switching catalog instance keeps every row. It has no default. The migration `*_media_id_namespace.sql` renamed `mal_id` to `external_id` (its column grants and check follow; the check is now `library_entries_external_id_check`), added `id_namespace` (a temporary default `'mal'` filled any existing row, then was dropped) and rebuilt `library_entries_user_media_key`. It ran before any user data existed and before any binary read or wrote `library_entries` (A-03), so it needed no data migration and no compatibility step (§10). An AniList adapter adds its own namespace (`anilist`) with a new enum value, unless the AniList item decides a mapping to MAL ids.
- `media_is_adult` has no default either (migration `*_library_media_is_adult_no_default.sql`, A-03): a default `false` failed open, so an insert that forgot it would show an adult title with the setting off (BR-06). Every insert names it, like `id_namespace` (an insert without it fails with `23502`); the account store always sends it from the snapshot (§4). Dropping a default changes no existing row, so it needs no data migration and no compatibility step (§10).
- `profiles` has no `username` in v1: no requirement uses it, and a unique username would let callers probe which names exist.
- The only progress check in the database is `progress >= 0`. There is no `progress <= media_total_units` check: BR-01's upper bound is enforced in the domain on user edits, and a snapshot refresh must never fail when the provider total drops below the saved progress. The UI shows progress above total gracefully.
- `updated_at` is set by triggers. `profiles`: `private.set_updated_at`, `before update`, always `now()`. `library_entries` (migration `*_guest_merge_client_time.sql`, A-04, ADR-0016): `private.set_library_entry_updated_at`, `before insert or update`: an update leaving `updated_at` unchanged gets `now()`, and a value set explicitly, on update or insert, is kept, capped at `now()` (`least`). `authenticated` has no insert or update grant on `created_at` and `updated_at` (see "Grants"), so a client can neither set nor change them (a statement naming them fails with `42501`): on insert both take their `now()` default, and every update gets `now()`. Only a role holding the column privilege sets `updated_at`: the owner of the guest merge and replay functions (below) and the trusted server roles (`service_role`, in Edge Functions only). So for a signed-in user the stored timestamps are the server's, except the `updated_at` of a merged guest entry or a replayed offline save (A-05), which keeps the time of its change on the device capped at the call's `now()` (its `created_at` is the time of the insert, so it can be later); the Supabase repository returns them (§4).
- Library rules (L-01, `src/core/domain/library-entry.ts` and `library-progress.ts`): pure functions over a `LibraryEntry` (`MediaKey`, snapshot, status, progress, score, notes, favorite flag, `startedAt` / `finishedAt` calendar days, ISO `createdAt` / `updatedAt`) and a `LibraryWriteContext` (`now`, the ISO timestamp; `today`, the local calendar day). BR-09: every change returns a new entry with `updatedAt = now`, a no-op returns the same reference, so callers skip the write; the guest store keeps these client timestamps, which the BR-08 merge compares and keeps on merged entries; for signed-in users the database sets both timestamps itself (see the `updated_at` note above). BR-01: an integer in 0..total when the total is known, else 0..`PROGRESS_MAX` (`POSTGRES_INTEGER_MAX`); an invalid manual value throws a `RangeError`, an unchanged value is a no-op even above a dropped total, and `+1` is a no-op at or above the total. BR-02: any progress change on a `planned` entry makes it `current` and sets `startedAt` when empty. BR-03: reaching the known total sets `completed` and `finishedAt` (from any status); decreasing keeps the status, the user reverts with `setStatus`. BR-04: `setStatus(completed)` sets the progress to the known total and `finishedAt`; `setStatus(current)` sets `startedAt` when empty; other transitions keep progress and dates; an explicit status never triggers BR-02 or BR-03. BR-05: `favoriteMedia` adds a missing media as a planned favorite; unfavoriting keeps the entry. BR-07 (L-03, `library-details.ts`): `setScore(entry, score | null, ctx)` and `setNotes(entry, notes | null, ctx)` throw a `RangeError` without the value on an invalid input (`isValidScore`, `isValidNotes`, checked first: the UI validates before, so this is a programming error), an unchanged value is a no-op; `notesFromInput(text)` turns the notes editor text into notes: blank text (as `String#trim` sees it) is `null`, any other text is kept exactly as typed, untrimmed. Snapshot (ADR-0009, L-03, `library-snapshot.ts`): `refreshMediaSnapshot(entry, snapshot, ctx)` is the BR-09 write of a fresher snapshot (the same reference when `isSameMediaSnapshot`, field by field), and never touches the status, the progress or the dates: a total dropped below the progress keeps the progress (`canIncrementProgress` then disables `+1`), and a total that drops to the progress does not complete the entry (BR-03 applies to progress changes only); `withMediaSnapshot(entry, snapshot)` is the same view without a write (`updatedAt` kept), for display. Coalesced `+1` taps (BR-09, §6) write the last optimistic entry.
- `progress_events` rows are written by an `after update of progress` trigger on `library_entries`, only when the progress value changes. There is no insert trigger: logging an insert would invent history. The guest merge (A-04, ADR-0016) inserts without an event, and a merge replace, an update, logs one event when it changes the progress, dated at the merge (`created_at` is `now()`, not the guest time): a progress change the user made on the device. The schema v1 migration comment ("logging an insert or a guest merge would invent history") predates that design and assumed a merge that never logs.
- A `profiles` row is created by a trigger on `auth.users` insert, which never reads `raw_user_meta_data` (user-controlled at sign-up). `profiles` has no insert or delete policy.
- Every foreign key to `auth.users` cascades, so deleting the auth user removes the profile, the library entries and the progress events (account deletion, A-06, ADR-0018: no migration was needed). pgTAP `080-account-deletion` checks it (`delete from auth.users`, what the admin delete runs, removes one user's profile, entries and events and none of another user's) and guards it for later tables: every foreign key of the `public` and `private` schemas cascades on delete (`confdeltype = 'c'`), profiles, library entries and progress events reference `auth.users`, and every `user_id` column of a public table references `auth.users`, so a table holding user data without the cascade fails CI.
- Library entry schemas (L-02, `src/core/schemas/`), the single boundary of every stored entry: the guest store parses with them on read and validates with them on save (§4), and the account store's `parseLibraryRow` (A-03, §4) maps a row to the same shape and parses it with them, so both sides accept exactly what the database accepts.
  - Limits (`src/core/domain/database-limits.ts`): `MEDIA_TITLE_MAX_LENGTH` (500) and `MEDIA_IMAGE_URL_MAX_LENGTH` (2048; `IMAGE_URL_MAX_LENGTH` of `image-url.ts` is this constant) mirror `library_entries_media_title_check` and `library_entries_media_image_url_check`. Postgres `char_length` counts code points, not UTF-16 units, so lengths are measured with `codePointLength(text)`; `isStorableText(text)` rejects what a Postgres `text` column cannot hold (U+0000, a lone surrogate), and `toStorableText(text)` removes NUL and replaces each lone surrogate with U+FFFD. BR-07 (`src/core/domain/library-entry.ts`): `SCORE_MIN` (1), `SCORE_MAX` (10), `NOTES_MAX_LENGTH` (2000 code points); `isValidScore(score)` (null or an integer in 1..10) and `isValidNotes(notes)` (null or storable text of at most 2000 code points) feed the entry schema, guard `setScore` / `setNotes` (L-03, "Library rules" above) and validate the notes sheet text (the score sheet offers valid scores only, §2 "Media detail").
  - `libraryMediaSnapshotSchema`: title of 1..`MEDIA_TITLE_MAX_LENGTH` code points; `imageUrl` `null` or starting with `https://` and at most `MEDIA_IMAGE_URL_MAX_LENGTH` characters; both storable text; `format` one of `MEDIA_FORMATS`; `totalUnits` `null` or an integer in 1..`POSTGRES_INTEGER_MAX`; `isAdult` a required boolean.
  - `libraryEntrySchema`: key with `namespace` in `MEDIA_ID_NAMESPACES`, `kind` in `MEDIA_KINDS`, `externalId` an integer in 1..`EXTERNAL_ID_MAX`; `status` in `LIBRARY_STATUSES`; `progress` an integer in 0..`PROGRESS_MAX`, never bounded by `totalUnits`, like the database (above); `score` per `isValidScore`; `notes` per `isValidNotes`; `isFavorite` a boolean; `startedAt` / `finishedAt` `calendarDateSchema` or `null`; `createdAt` / `updatedAt` `timestampSchema`. Both schemas produce the domain types.
  - Timestamps (`src/core/schemas/timestamp.ts`): `timestampSchema` accepts an RFC 3339 timestamp with an offset (`Z`, `±HH:MM`, `±HHMM` or `±HH`; uppercase `T`; no fraction or 1 to 9 digits; a real calendar date and time) and normalizes it to the `Date#toISOString` form `YYYY-MM-DDTHH:mm:ss.sssZ`: UTC, the fraction truncated to milliseconds, never rounded, so two timestamps keep their order or become equal; a result whose year is outside 0001..9999 is rejected (Postgres has no year 0). Supabase returns `+00:00` with microseconds and `libraryWriteContextAt` gives `toISOString`, so after normalization every `updatedAt` has one fixed-width format and the BR-08 comparison is a plain string comparison. `calendarDateSchema`: `YYYY-MM-DD`, a real date in the years 0001..9999.
  - Snapshot (FR-10, ADR-0009): `toLibraryMediaSnapshot(summary: MediaSummary)` builds the snapshot written with an entry, from a search or Discover row or the detail (`MediaDetail` extends `MediaSummary`). The title, which the Jikan-compatible adapter does not bound, is made storable with `toStorableText`, then cut to `MEDIA_TITLE_MAX_LENGTH` code points, never splitting a surrogate pair; `isAdult` is always copied from `summary.isAdult` (BR-06; the column has no default, see above); the result is then validated with `libraryMediaSnapshotSchema`, and anything else invalid (a title empty after cleaning included) throws a `LibrarySnapshotError` (`src/core/errors/library-errors.ts`, a `RangeError` with a fixed message, L-05), which the detail's library section tells apart from a read failure (§2 "Media detail") (the adapters already guarantee the image URL and the total, §3, §9).
- Guest merge (BR-08, A-04, ADR-0016, migration `*_guest_merge_client_time.sql`): the only path on which a client-supplied time is honored. `public.merge_guest_library_entries(entries jsonb)` (see "Functions") validates the whole input, then writes each element through `private.write_client_library_entry(entry jsonb)`, the rule of a client write carrying the time of its change: the user `auth.uid()`, the time `least(entry updated_at, now())`, an insert, or on a conflict on the key an update of the values and the time only `where stored.updated_at < excluded.updated_at` (an equal or newer stored copy is kept), so the database applies last-write-wins between the guest change and the row as it is at the write, and a device clock ahead of the server is capped at the `now()` of the writing call (a retry after a failed batch caps it again at its own later `now()`, so within the skew it can replace an account change made between the two calls, ADR-0016). The microsecond `updated_at` compared with a millisecond guest time agrees with the client's comparison of the truncated value (`timestampSchema`). A merged row keeps the guest time, so with guest data on two devices the most recent change wins whatever the order of the sign ins. One call is one transaction: a batch is written whole or not at all. The guest store removes the merged entries only after the merge succeeded (§4, §8).
- Replay of offline writes (BR-08, FR-23, A-05, ADR-0017, migration `*_replay_library_writes.sql`). Rule (B1, as extended by ADR-0017): a client-supplied modification time is honored only by the guest merge and by the replay of writes the server has not confirmed, both through `private.write_client_library_entry` (and, for removals, `private.remove_client_library_entry`), capped at the server's `now()`; every regular online write goes through PostgREST and keeps the server time from the trigger, and `authenticated` still has no privilege on `updated_at` (pgTAP `030` and `060`). A replayed save follows the merge rule above. A replayed removal deletes the stored entry of its key only when its `updated_at` is strictly earlier than the removal's time capped at `now()`, keeps an equal or newer one, and answers `written` when the account has no entry of the key (the absence holds). No tombstone: a removal that reached the server, followed by the replay of an older save from another device (or the merge of an older guest entry), inserts the entry again (accepted, ADR-0017). A replay that replaces the progress logs one `progress_events` row, dated at the replay, like the merge.

### Functions

Every function sets `search_path = ''`, uses fully qualified names, and has `execute` revoked from `public`, `anon` and `authenticated`. All but two live in schema `private`, which the API does not expose and on which `anon` and `authenticated` have no usage: they are called by a trigger or by the functions below. `private.log_progress_event` and `private.handle_new_user` are `security definer`: clients have no insert grant or policy on `progress_events`, and the auth server's role has no grant on `profiles`. `private.set_updated_at` (`profiles`), `private.set_library_entry_updated_at` (`library_entries`), `private.write_client_library_entry` (the rule of a client write carrying its time: the guest merge and the replayed saves) and `private.remove_client_library_entry` (A-05: the rule of a replayed removal) are `security invoker`, the last two executable by their owner only. `private.remove_client_library_entry(entry jsonb) returns boolean` applies the same checks as the write rule (`auth.uid()` else `42501`; `updated_at` of the RFC 3339 form before any cast, finite, not before the year 1; the key complete; else `22023` with fixed messages), deletes the caller's row of the key only `where stored.updated_at < least(time, now())`, filtering on `auth.uid()` itself since it runs under definer rights, and returns `true` when it deleted the row or the caller has none, `false` when a row as recent or newer is kept.

The API calls exactly two functions. The first is `public.merge_guest_library_entries(entries jsonb)` (A-04, ADR-0016), `security definer` (owner `postgres`: it writes `updated_at`, which no API role may), `execute` granted back to `authenticated` only after the revoke (`service_role` keeps Supabase's default). Definer rights bypass RLS, so it scopes itself: the user is `auth.uid()` only (`42501` without one), in every write and in the conflict key, never an input. The input is validated whole before any write, each failure `22023` with a fixed message holding no value: a JSON array of at most 100 elements (`max_entries`; the client's `GUEST_MERGE_BATCH_SIZE` must not exceed it), each an object of exactly the 15 writable columns and `updated_at` (never `user_id`, `id` or `created_at`), `updated_at` a string of the RFC 3339 form the client sends, checked before any cast (migration `*_guest_merge_time_format.sql`; `private.write_client_library_entry` checks it too, with a lower bound of the year 1), no key twice. It returns one row per element, in input order: `(id_namespace, media_kind, external_id, user_id, outcome)`, `outcome` `written` or `kept`.

The second is `public.replay_library_writes(expected_user_id uuid, writes jsonb)` (A-05, ADR-0017), with the same mode, owner, grants and self-scoping: the user is `auth.uid()` only (`42501` without one), and `expected_user_id` is a guard, never a source: `42501` when `auth.uid()` is distinct from it, so the writes queued for one user never land in another account when the token changed after the client's session guard. The input is validated whole before any write, each failure `22023` with a fixed message holding no value: a JSON array of at most 100 elements (`max_writes`, equal to the client's `LIBRARY_REPLAY_BATCH_SIZE`; each names the other in a comment), each an object whose `op` is the string `save` or `remove`; a save holds exactly `op`, the 15 writable columns and `updated_at`, a removal exactly `op`, the media key columns and `updated_at` (never `user_id`, `id` or `created_at`); `updated_at` a string of the RFC 3339 form, checked before any cast, then not before the year 1 for the whole batch up front; no key twice, compared as the table types them. Then each element in input order goes through `private.write_client_library_entry` (a save) or `private.remove_client_library_entry` (a removal), in the call's single transaction. It returns one row per write, in input order: `(id_namespace, media_kind, external_id, user_id, outcome)`, `outcome` `written` or `kept`. A value that passes the form but not the cast, the types or the constraints (an impossible time, an uncastable key, a null key column of a save) fails the whole call with the cast or constraint code, which can quote the caller's own input to the caller only; the client schema rejects those first (`docs/BACKLOG.md` R-04).

### Row Level Security

One policy per command, `to authenticated` only:

```sql
alter table public.profiles enable row level security;
alter table public.library_entries enable row level security;
alter table public.progress_events enable row level security;

-- no insert or delete policy: created by trigger, removed by cascade
create policy profiles_select_own on public.profiles
  for select to authenticated using (id = (select auth.uid()));
create policy profiles_update_own on public.profiles
  for update to authenticated using (id = (select auth.uid())) with check (id = (select auth.uid()));

create policy library_entries_select_own on public.library_entries
  for select to authenticated using (user_id = (select auth.uid()));
create policy library_entries_insert_own on public.library_entries
  for insert to authenticated with check (user_id = (select auth.uid()));
create policy library_entries_update_own on public.library_entries
  for update to authenticated using (user_id = (select auth.uid())) with check (user_id = (select auth.uid()));
create policy library_entries_delete_own on public.library_entries
  for delete to authenticated using (user_id = (select auth.uid()));

-- read only: rows are written by the progress trigger
create policy progress_events_select_own on public.progress_events
  for select to authenticated using (user_id = (select auth.uid()));
```

### Grants

Least privilege, fail closed:

- `anon` has no grant on any table, sequence or function of the schemas `public` and `private` (extension objects aside), and no policy. The Supabase-managed schemas (`graphql_public`, `extensions`) keep their platform grants.
- Default privileges for role `postgres` in schema `public` revoke tables, sequences and functions from `anon` and `authenticated`, so a future object without explicit grants is unreachable instead of exposed.
- Per-schema default privileges cannot remove the global `PUBLIC` execute on new functions, so every function needs its own `revoke execute`; the pgTAP guard `010-privileges` fails when one is missing.
- Functions: `authenticated` executes exactly `public.merge_guest_library_entries(jsonb)` (A-04, ADR-0016) and `public.replay_library_writes(uuid, jsonb)` (A-05, ADR-0017), `anon` and `public` none; `010-privileges` fails on any other function an API role may execute. Both write `updated_at` as definer; no API role holds a privilege on it.
- `service_role` keeps the Supabase defaults (Edge Functions only).

| Table | `authenticated` |
| --- | --- |

| Rate limiting | Catalog http client (`src/core/catalog/http/`): one `createCatalogHttpClient({ rateLimit, retry?, timeoutMs?, random?, now?, wallClock? })` per provider instance, with its own limiter and dedup map, shared by every request of that provider (no singleton: the adapter factory creates its own client from its instance's policy, and the composition root, which owns the provider, never builds a client itself). `getJson(url, signal?, options?: { priority? })` resolves the parsed JSON as `unknown`; per call, in this order: a non-https URL is rejected with a `RangeError` before any token or fetch; in-flight dedup by URL; the retry loop, where every attempt, retries included, takes a token (`acquire`; `acquireBackground` while the request is background, below), then calls `globalThis.fetch` (read at call time) with `Accept: application/json` and a per-attempt timeout covering headers and body (`REQUEST_TIMEOUT_MS`, 10 s; the fetch and the body read are raced against the attempt signal with `raceAbort`, so the timeout and the caller abort also end a transfer that ignores its signal); a status other than 2xx is a `CatalogHttpError` and its body is never read: the attempt's `AbortController` is aborted once the attempt settles (`finally`), which releases the connection on undici and in browsers (the future web app; React Native's XHR-based fetch buffers the body anyway) and is a no-op for an attempt whose body was already read. Limiter (`createRateLimiter(policy, { now? })` → `{ acquire(signal?), acquireBackground(signal?), pauseFor(ms) }`, `RateLimitPolicy = { buckets: { capacity, refillIntervalMs }[] }`): token buckets in their integer virtual-scheduling form (GCRA); a request is granted when every bucket allows it, and a bucket grants at most `capacity + floor(W / refillIntervalMs)` requests in any window W, background grants included. Priorities (C-06, FR-04): two FIFO queues. `acquire` joins the foreground queue; `acquireBackground` returns `BackgroundAcquire = { readonly granted: Promise<void>; promote(): void }` and joins the background queue. The foreground head is always served first. The background head is served only when the foreground queue is empty, no pause is running and every bucket keeps one token after the grant: its background ready time is `tat - (capacity - 2) * interval` for a capacity of 2 or more, one interval after the foreground ready time `tat - (capacity - 1) * interval`; a bucket of capacity 1 keeps no reserve (`tat`, the foreground time). So a granted prefetch never takes the token the next foreground request would use: with `TENRAI_RATE_LIMIT`, a prefetch waits for a full bucket, and a page opened right after it is still sent at once. A background waiter can wait indefinitely under sustained foreground traffic; its caller aborts it when it is no longer wanted. `promote()` moves a still-queued background waiter to the tail of the foreground queue (a no-op once granted or aborted). Still at most one timer, for the head that drains next (the foreground head, else the background head at its background ready time), and none when idle; a queued waiter of either queue whose signal aborts leaves without taking a token (`granted` rejects with `CatalogAbortedError`). `pauseFor` holds both queues, capped at `MAX_PAUSE_MS` (60 s). Background requests in the http client: a background call joins an in-flight request of the same URL (no extra token); otherwise it starts one whose attempts, retries included, take their token with `acquireBackground` while the request is background. A foreground call joining a URL in flight as background promotes it: the attempt still waiting for its token is promoted (`promote()`), and later attempts use `acquire`; a promoted request is never demoted, even when its foreground callers leave and only the prefetch remains (harmless: one request at most). Otherwise a background request is identical to a foreground one: same retry policy, timeouts, pauses (its 429 pauses everyone), dedup and abort handling. Clock (approved design change in C-03, after the C-02 review): the limiter, its pauses and the retry deadline read a monotonic clock, `performance.now()` by default (the injected `now`, which must never decrease, read on each call so fake timers apply), so a wall clock change (NTP step, manual change) never refills a bucket, shortens a pause, moves the deadline or stalls the queue; `Date.now` (`wallClock`) only resolves an HTTP-date `Retry-After`. The C-02 clamp of a backward wall clock jump was removed. Jikan-compatible instances (`src/core/catalog/jikan/jikan-rate-limit.ts`, ADR-0013), one policy per instance: Tenrai (`TENRAI_RATE_LIMIT`), one bucket of 2 tokens refilled one per 750 ms, from its documented 4 req/s and 120 req/min per IP: at most 3 requests in any 1 s window (a 4th needs 1.5 s) and 82 in any 60 s window, 80 per minute sustained, 25 % and 32 % under the limits. A self-hosted Jikan (`SELF_HOSTED_JIKAN_RATE_LIMIT`, formerly `JIKAN_RATE_LIMIT`): a bucket of 2 tokens refilled one per 750 ms and one of 10 tokens refilled one per 1.5 s, from the public Jikan's documented 3 req/s and 60 req/min, the conservative default for an instance whose limits are unknown: at most 3 requests in any 1 s window and 50 in any 60 s window (51 need 61.5 s), 40 per minute sustained, bursts of 2 then one per 750 ms until the 10-token bucket is spent. Reading limits as capacity = refill rate (3 per second, 60 per minute) would allow 6 requests in one second and 120 in one minute. The limiter is per device, while Tenrai counts per IP: every device behind one NAT (carrier-grade NAT on mobile networks, shared Wi-Fi) shares its limits, which no device can see. A 429 pauses the limiter for its `Retry-After` (below), sustained 429s are reported by the failure monitor (§3), and the mitigations beyond that are a shared server-side cache ("Dedicated backend", §11) or a self-hosted instance. Dedup (`in-flight-dedup.ts`): identical in-flight requests (key: the exact URL, GET only, per client) share one operation with its own `AbortController` and a caller count; a caller whose signal aborts rejects at once with `CatalogAbortedError` and detaches; when the last caller aborts, the shared operation (token wait, backoff or fetch) is aborted and dropped, so a later caller starts fresh. Nothing is cached, failures included. Retries (`DEFAULT_RETRY_POLICY`, `retry-policy.ts`): at most 4 attempts (3 retries) on 429, 5xx, network errors and attempt timeouts; never on other 4xx, malformed JSON or aborts. Delay = max(`Retry-After`, backoff); backoff with equal jitter `d/2 + random·d/2`, `d` = 1 s·2^(n−1) capped at 8 s for retry n (0.5–1 s, 1–2 s, 2–4 s); `Retry-After` honoured up to 10 s (a longer one is not retried: the `CatalogHttpError` surfaces with its `retryAfterMs`), parsed by `parseRetryAfter` as delta-seconds or an IMF-fixdate (strict regex + `Date.UTC`, not `Date.parse`, compared with `wallClock`), anything else ignored; no retry is scheduled more than 20 s after the call started (its first token wait included), or, for a request started in the background, after its first token grant (its background wait is not on the user's clock, even once promoted); a scheduled retry then queues for its token at the tail of its priority's queue like any request, so under a backlog it is sent later. Every 429, and every 503 with `Retry-After`, pauses the whole limiter (`pauseFor`) for the `Retry-After`, or the backoff without one, so every queued request waits, not only the retried one; the pause applies even when that request is not retried (last attempt, `Retry-After` over 10 s). Worst case before an error surfaces: about 30 s plus the token wait. ## 7. Adult content filter

- Providers are always queried without content filters (ADR-0004).
- The BR-06 classifier `isAdultMedia({ kind, genreNames, isRxRated })` lives in `src/core/domain/content-filter.ts`: a title is adult when its genres include Hentai or Erotica (`ADULT_GENRE_NAMES`, compared trimmed and lowercased), or the anime rating is Rx. Adapters call it to set `isAdult`; no adapter reimplements the rule.
- The Jikan-compatible adapter (every instance, §3) passes the names of all four genre arrays, `genres`, `explicit_genres`, `themes` and `demographics` (MAL lists Hentai and Erotica under `explicit_genres`), and reads an anime rating as Rx when it starts with `Rx`, trimmed and case-insensitive (`Rx - Hentai`). It fails closed: a missing or malformed genre array, or a missing anime `rating` key, fails the whole response with `CatalogResponseError` instead of yielding a non-adult item; a `null` rating is an unrated anime.
- `applyContentFilter(items, showAdult)` in the same file is generic over `{ isAdult: boolean }` (catalog items and library snapshots) and returns `{ items, hiddenCount }`; it is applied in hook `select`. Default `showAdult = false` (`DEFAULT_SHOW_ADULT`).
- The setting (L-06, FR-32) is the adult content preference: stored on the device under `preferences.showAdult` (`'true'` / `'false'`, anything else read as `false`), held by the composition root and read with `usePreferences().showAdult` by search (results, filters sheet), Discover, the media detail and the library list (§2). It is turned on in the settings screen after a confirmation sheet, with no age verification: showing adult content is at the user's own risk; turning it off needs no confirmation (`AdultContentSetting`, §2). It stays on the device for guests and signed-in users alike, like the theme and language preferences, and is not synced to `profiles.preferences` (A-03): SPEC does not require it (FR-23 is the library), theme and language are device choices, and a synced value would add a server-written input to the BR-06 setting. `profiles.preferences` stays unused; a later sync would parse it with the same fail-closed rule (`showAdult` false unless exactly `true`).
- A filtered page can contain fewer items than the provider page size; the UI shows a subtle note instead of refetching.
- The media detail screen shows a translated hidden state, with nothing of the media, for an adult title while the setting is off (`useMediaDetail` `select`, §2 "Media detail", §6), with an "Open settings" action (navigation only).
- The library list hides adult entries by their snapshot's `isAdult` (`buildLibraryView` in the `useLibraryList` `select`, after the status and kind filters) and shows the hidden note when `hiddenCount` is above 0 (§2 "Library screen", §6 "Library"); a setting change lays the list out again (`keepLibraryLayout` keeps the last layout only for the same setting).
- App store rating: 17+ (App Store) / PEGI 18 equivalent (Play). The adult content toggle is shown on every platform (L-06); its iOS exposure is checked against the current App Store Review Guidelines (1.1.4) before release (R-05).

  - Accepted limitations: the links open only on the device that requested them; all variants share the scheme, so with two installed Android may ask which app opens a link (the wrong one fails as `link-invalid`); mail link scanners that follow links consume the token; verified https links need a domain (deferred).
- OAuth sign-in (A-02, ADR-0015), through `signInWithProvider` (§4):
  - Flow, all inside the user's tap: `signInWithOAuth({ provider, options: { redirectTo: 'tsuzuki://auth/oauth-callback', skipBrowserRedirect: true } })` builds the authorize URL locally, stores the verifier in its flow slot and returns `{ url, flowId }`; the injected `OAuthBrowser` opens `url` in a browser auth session (ASWebAuthenticationSession on iOS, Custom Tabs on Android) and resolves with the redirect or `closed`; the redirect is parsed with Zod in core: it must start with the redirect URL followed by `?` or `#`, its params are read from the query and the fragment (a param repeated within one part fails; only `error`, `error_code` and `error_description` may appear in both, since GoTrue may copy them into the fragment, and the query value wins, as in supabase-js; `code`, `sb_flow_id` or any other key in both fails), `error` / `error_code` win over a code (`error=access_denied` without an `error_code`, the user's own decline, resolves `null`; any other error fails, including an `access_denied` that Supabase sends with an `error_code` when it refuses on its side, such as disabled sign ups), `error_description` is never read, the code and `sb_flow_id` follow the bounds of `parseAuthLinkParams`, and the flow id must equal the one `signInWithOAuth` returned. Only then `exchangeCodeForSession(code, { flowId })`. Plain string rules, not the React Native `URL` polyfill (§9).
  - Route `auth/oauth-callback`: Android also hands the redirect to expo-router. The screen never reads or exchanges its params and writes nothing; on mount it goes back once (`router.back()`) when the screen below is sign in or sign up (`OAUTH_SOURCE_ROUTES`, `src/features/auth/auth-routes.ts`), whose hook awaits the result; `canGoBack()` alone is not enough, since a cold deep link gets the tabs below it (`unstable_settings`); otherwise (a cold start after the process was killed in the browser, or a stray link) it shows "sign in did not finish" with Sign in (`router.dismissTo('/auth/sign-in')`). On iOS the session captures the redirect, so only a stray link shows the route. An interrupted flow leaves its verifier in the 5-slot ring, evicted by later flows.
  - Buttons: sign in and sign up show "Continue with Google" / "Continue with Apple", plain text buttons, one per entry of `oauthProviders`, in that order, hidden while it is empty (every A-02 build: the composition root passes no `oauth` option until A-09, with the browser dependency, the provider setup, `EXPO_PUBLIC_AUTH_PROVIDERS` and the branded buttons). While a flow runs, the provider buttons are disabled. Success returns with `router.dismissTo('/settings')`, like the email sign in; `null` leaves the screen as it was, with no error.
  - Errors, translated with `authErrorKey` in an inline error: `oauth-failed` "sign in did not finish, try again", `network` the offline message, `rate-limited` the "too many attempts" one, `unknown` the generic one. A failed exchange consumes the verifier: a retry is a new tap and a new flow. A cause the mapping reads as `unknown` is reported with operation `oauth-sign-in`, whatever reason is returned. No captcha (Supabase does not protect `/authorize`).
  - Accounts: Supabase links the provider identity to an existing account with the same verified email; an unconfirmed email account with that email is not taken over. The app keeps the user id only (Apple's private relay email and first sign-in name are not read).
- Session state: `AuthContextProvider({ repository, captcha })` (`src/core/hooks/`) subscribes to `onAuthStateChange` in an effect and holds an `AuthSessionState` (`loading` until the first call, then `signed-out` with `session: null` or `signed-in` with `{ userId }`), keeping the same object when the user id is unchanged (token refreshes cause no re-render). `useAuthSession()` reads it.
- Auth hooks (`src/core/hooks/use-auth-mutations.ts`): one TanStack `useMutation` per action. Before `signUp`, `signIn`, `requestPasswordReset` and `resendConfirmation`, the hook asks the `CaptchaTokenProvider` for a token for its `CaptchaAction` and passes `{ captchaToken }` only when it is not null. Every auth mutation sets `networkMode: 'always'` (an offline call fails at once with `network`, never paused) and `gcTime: 0`, and the persister never dehydrates mutations (`shouldDehydrateMutation: () => false`, `src/core/query/persister.ts`): mutation variables hold passwords, and TanStack would otherwise persist a paused mutation, variables included, to MMKV now that `onlineManager` follows the device connectivity (A-05). Screens translate an error with `authErrorKey(error)` (`src/features/auth/auth-error-keys.ts`; anything that is not an `AuthError` reads as `unknown`).
- Token refresh: supabase-js starts its auto refresh timer outside the browser; the composition root binds it to the app foreground (`subscribeToForeground`, `src/platform/app-state.ts`, AppState `active`) through `setAutoRefresh` (`startAutoRefresh` / `stopAutoRefresh`), the supabase-js React Native guidance: no refresh timer runs in the background, and returning to the foreground restarts it, which refreshes a token close to expiry.
- Captcha (ADR-0014): the seam above, `noCaptcha` until a provider is wired (A-08: hCaptcha or Turnstile, a WebView widget implementing `CaptchaTokenProvider`, its site key in the app env as `EXPO_PUBLIC_CAPTCHA_SITE_KEY`). A cancelled or failed challenge rejects with `captcha-failed`.
- Session storage: `src/platform/secure-session.ts` implements `SessionStorage` over `expo-secure-store`, with `keychainAccessible: WHEN_UNLOCKED_THIS_DEVICE_ONLY` (readable only while unlocked, never migrated to another device). A value is split by code point into chunks of at most 2048 UTF-8 bytes (at most 32 chunks, otherwise a `RangeError`) stored under `<key>.<generation>.<index>`, with the generation (0 or 1) the stored header does not point to; then the header `<generation>:<count>` is written last under `<key>` and parsed with Zod; then the chunks no header points to are deleted. The header write is the single switch from the whole old value to the whole new value: a failed or interrupted write leaves the old value readable, never a mix of old and new chunks. A failed chunk deletion is reported through the `ErrorReporter` and not thrown (the value is already whole); the next write or removal deletes the leftovers. A read fails closed (`null`) when the header is missing or invalid or a chunk is missing; a removal deletes the header first. A header in the F-09 format (a bare chunk count, chunks under `<key>.<index>`) is invalid: that session fails closed (the user signs in again) and its chunks are deleted by the next write or removal. Keys are limited to `[A-Za-z0-9_-]`: the dot is reserved for the chunk suffixes, so a key cannot collide with another key's chunk. Calls are serialized per key with a promise queue (`getItem`, `setItem` and `removeItem` on one key run one after another, other keys are independent): an overwrite spans several writes and supabase-js takes no lock, so without the queue a read during an overwrite could see mixed chunks, treat the session as invalid and remove it (silent sign-out). A failed call does not block the next one on its key. The `expo-secure-store` config plugin keeps the secure-store data out of Android auto backup (`configureAndroidBackup`) and requests no Face ID permission.
- App foreground (A-05, ADR-0017): `subscribeToForeground` (`src/platform/app-state.ts`, the core type `ForegroundSubscription`) is passed by the composition root to `SessionLibraryContextProvider`. Going to the background flushes the live library writer (`flushAll`: the coalesced `+1` writes reach the guest store, or the account library's write-ahead queue, before the app can be killed); a return to the foreground starts a replay run of the account library's queued writes (§4 "Library switch"), next to the token auto refresh below.
- MMKV (`src/platform/storage.ts`, one unencrypted instance) holds the preferences, the persisted query cache, the recent searches, the guest library (notes included) and, per signed-in user id, the account library's device copy and write queue (`account-library-copy.<userId>`, `account-library-queue.<userId>`, notes included, A-05), never the session: `src/core/repositories/supabase/session-isolation.test.ts` proves that sign-in, an authenticated persisted query, a token refresh and sign-out write no token to the `StorageAdapter`, and that a new client restores the session from `SessionStorage` alone. A sign out or an account deletion deletes the signed-out user's two documents, the recent searches, the persisted cache and, once the guest merge concluded, the guest library (A-06, "Sign out purge" below). Leaving MMKV unencrypted is reviewed in R-04.
- Guest mode (FR-20) uses the `local` repositories: the guest library is the `GuestLibraryRepository` of `src/core/repositories/local/library-repository.ts`, on the device only (§4).
- Library and session (A-03, FR-23): signed in, the library hooks read and write the account library (the offline account library over `createSupabaseLibraryRepository`, one instance per user id, A-05), once the guest library was merged into it (A-04, below); signed out, the guest library; while the session state is `loading`, or while the merge checks or runs, or after it failed until a retry succeeds, neither, and the library screens show their loading state, the merge in progress or its failure with Try again (§4 "Library switch"). The two are never shown together, not even for one frame (§6 "Query keys", "Writes"). The guest library is merged into the account at sign in: its merged entries leave the device once the merge succeeded, the rest stays there; a sign out clears it once the merge concluded and keeps it, shown again, while the merge has not (A-06, "Sign out purge" below). The preferences stay on the device in both states; the recent searches stay across a sign in and are purged at sign out (§6, §7). Offline (A-05, ADR-0017), the account library reads from its per-user device copy with the queued writes applied, and its writes are queued on the device and replayed on reconnect, on foreground and when a write stays queued (§4 "Offline account library"); library queries are still never persisted (§6). A signed-in cold start offline with no device copy yet (a first sign in offline) shows the library read error with its retry.
- Guest merge (A-04, BR-08, FR-22, ADR-0016): each time a signed-in session starts in the app process (a launch with a stored session, a sign in, another user; a token refresh starts nothing) and on Try again after a failure, `SessionLibraryContextProvider` runs `mergeGuestLibrary`: it waits for the pending writes of the retired libraries, reads `guest.list()`, merges every entry with `mergeGuestEntries` (most recent `updatedAt` wins, each entry keeping its own time capped at the server's now, through the database function `merge_guest_library_entries`, §4 "Account store", §5), then removes exactly those entries from the device with `guest.removeUnchanged`, only after the merge succeeded and while the session is still the one it ran for. The library is pending meanwhile, so no library action writes during a merge. After a failure the library stays pending, with the error and Try again, until a retry succeeds; the guest store stays whole, and Try again, a reconnect (A-05), the next launch or the next sign in tries again; a merge whose session ended removes nothing and sends no further batch (its signal is aborted, A-05). The status is `useGuestMerge()`.
- Sign out (A-01, A-06, FR-25, ADR-0018): `useSignOut()` (`src/core/hooks/use-sign-out.ts`), a mutation with the auth mutation options taking `{ discardUnsynced? }` and resolving `{ status: 'signed-out' }` or `{ status: 'unsynced', count }`, in this order:
  1. The session's account instance (`useSessionLibrary().account`) is taken as the call starts. None (signed out, or the session loading): `signOut()` only, nothing purged.
  2. Sync, both within `SIGN_OUT_SYNC_TIMEOUT_MS` (10 s): the live library writer's `flushAll()`, so a coalesced `+1` still in its window is sent under the session it was made in, then the account's `replayQueuedWrites({ signal })`, whatever the merge status (each write carries the time of its change, so BR-08 does not depend on the order with the merge). A run joined from the replay driver may sit in its 30 s backoff: at the budget the signal aborts and the sign out stops waiting. A step that rejects is reported (`{ source: 'sign-out', tags: { step } }`) and the sign out goes on: the count tells what remains.
  3. Writes still queued (`queuedWriteCount()`) and no `discardUnsynced`: `{ status: 'unsynced', count }` and nothing else. `AccountSection` asks (§2): Cancel keeps the user signed in with nothing touched; the confirm calls again with `discardUnsynced: true`, which tries the sync again, skips the count and purges what remains. Keeping the queue on the device instead would leave notes at rest on a device that may be handed over.
  4. The guest merge status is read before the session ends (it reads `idle` once signed out): the guest library is kept while the merge is `checking`, `merging` or `failed` (`keepsGuestLibrary`, `device-purge.ts`), since those entries are guest data the account has not confirmed: they show again as the guest library, and the next sign in merges them. Once `idle`, the merge concluded and the guest store holds nothing the account lacks (BR-08): it is cleared.
  5. `signOut()`, local scope: this device's session is revoked and removed, other devices stay signed in. When the server revocation fails (offline) with a valid access token, supabase-js still removes the local session and the repository resolves: the device is signed out, and the unrevoked refresh token is no longer stored anywhere on it. With an expired access token, supabase-js must refresh it first; offline that fails, the session stays and `signOut` rejects with `network`: the mutation rejects, nothing is purged and the user stays signed in (and retries online). The repository resolves only once the session is gone from the device; supabase-js removes every PKCE verifier with it.
  6. The device purge (below), then `{ status: 'signed-out' }`. Sign out shows a loading label while it runs.

  The library then switches back to the guest library and the account library's queries are removed with its scope (§6 "Writes"); a retired writer's late flush is refused by the closed account library (`signed-out`), never queued or sent (§4 "Offline account library").
- Sign out purge (A-06, FR-24, FR-25, ADR-0018 "Device purge"): `purgeDeviceUserData` (`src/core/hooks/device-purge.ts`), bound by `useDevicePurge()` to the query client, the recent searches, the session's guest library and `DevicePurgeContextProvider`, shared by the sign out and the account deletion. Each step is independent: a failure is reported as a `DevicePurgeError` of its step (`{ source: 'device-purge', tags: { step } }`, a fixed message, no cause, since a storage error could quote stored content), the next steps still run, and the purge never rejects. In order:
  1. `account-library`: `purgeDeviceData()` of the session's account instance: that user's device copy and write queue, the queued writes included (asked first at sign out; the account is gone at deletion), every older instance of that user closed (§4 "Offline account library").
  2. `guest-library`: `GuestLibraryRepository.clear()`, unless kept by the rule of the sign out's step 4.
  3. `recent-searches`: `RecentSearchesRepository.clear()`.
  4. `query-cache`: `queryClient.removeQueries()`: every query, the catalog ones included; mutations untouched (the running sign out lives there), so never `queryClient.clear()`.
  5. `persisted-cache`: the persister's `removeClient`, after step 4, so the stored `query-cache` document is gone when the purge returns (§6 "Persistent cache").
  6. The purge generation +1, last, so a screen keyed with it (the search tab) remounts on the purged state: its text, filters, page, results and recent searches list.

  Why every query, the catalog's too: a list of the user-scoped keys would have to follow every new key, and the catalog queries a user opened (details, Discover pages, genres) show what they looked at; removing every query is simpler and robust, and catalog data refetches. Kept on purpose: the preferences (theme, language, adult content), device settings used in guest mode too; the expo-image cover cache, public CDN images keyed by their URL, with no user id or library data and never listed by the app, so at most it tells someone reading the app sandbox which covers were displayed; other users' per-user documents, whose queued writes wait for their own next sign in; the guest library while its merge has not concluded. Nothing to clear in Sentry: no user context is ever set. An involuntary session end (a refresh token expired or revoked, the account deleted from another device) purges nothing, as before (ADR-0017): it does not go through `useSignOut`, and that user's copy and queue wait on the device for their next sign in, or until the app data is cleared (ADR-0018 "Residuals"; A-10 tracks a purge when the auth server reports the user gone).
- Account deletion (A-06, FR-24, ADR-0018): `useDeleteAccount()` (`src/core/hooks/use-delete-account.ts`), a mutation with the auth mutation options, run only by the confirmed second tap of `DeleteAccountScreen` (§2; the route reads no param, so a link opens the screen at most):
  1. The session's account instance is taken as the call starts. None: `session-expired`, nothing sent.
  2. `isDeviceOnline()` false: `offline`, nothing sent.
  3. `deleteAccount()` (§4): a rejection rejects the mutation; nothing is purged and the user stays signed in, the screen showing the translated reason.
  4. The device purge above, the queued writes included (discarded on purpose: the account is gone), the guest library by the same rule.
  5. `signOut()` ends the session locally. A rejection is reported (`{ source: 'account-deletion', tags: { step: 'sign-out', reason } }`), not shown, and the mutation still resolves: the next token refresh fails and ends the session.

  The purge comes before the local sign out, so the device data is gone even if the sign out fails or the app is killed in between. Server side, the `delete-account` Edge Function (`supabase/functions/delete-account/`, security model in §9) answers POST only, reads `Authorization: Bearer <token>` (nothing else of the request), has the auth server check the token with `auth.getUser(token)`, then hard deletes that user with `auth.admin.deleteUser(id)` and the service role key of its env; the foreign keys remove every row of the user (§5). A user removed between the check and the deletion (a concurrent call) answers `{"deleted":true}` too; a later call with the deleted user's token is refused (401, `session-expired`). Confirmation is two deliberate taps without re-authentication (owner decision), the same flow for email, Google and Apple accounts. Residuals (ADR-0018): an answer lost after the server deleted the account shows `network` and keeps the device signed in with its data until an explicit sign out (a retry answers `session-expired`); after a failed local sign out, the session stays until the next token refresh fails, the data already purged. Revoking Apple tokens (App Store guideline 5.1.1(v)) is A-09's, before Apple sign-in ships.

## 9. Security

Baseline: OWASP MASVS L1. Rules are in `CONTRIBUTING.md` §7. Summary:

| Threat | Mitigation |
| --- | --- |
| Reading or writing another user's data | RLS on every table + pgTAP tests in CI. The account library store (A-03, §4) also filters every request on its own user id, and checks before every call that the client's session is still that user's, so a change left pending by user A at a switch is never sent as anon or into user B's library (one session read of residual window, accepted, RLS still bounding it to the token's own rows). The guest merge (A-04, ADR-0016) goes through the same store: the guard before each of its calls, no user id in the request (the database function takes it from the token, next row), and the `user_id` of every answered row checked (a row of another user, the residual window, confirms nothing and rejects with `signed-out`, so the entries stay on the device); a run whose session ended (sign out, another user) changes no state and removes nothing from the device, and the next session's merge sends the entries to that session's own account. Offline writes (A-05, ADR-0017): the device copy and the write queue are kept per user id (checked as a UUID), and the instances of different users share nothing, so user B's instance never reads or sends user A's queued writes; the replay goes through the same store and guard, sends the store's user id as the function's `expected_user_id` guard (a switched token is refused with `42501`, read as `signed-out`, the queue kept), and checks the `user_id` of every answered row. Library query keys hold a per-writer scope, so one library's entries never show under another, and the previous library's queries are removed at the switch (§6 "Writes") |
| Privileged database function and client-chosen times | Two functions exposed to the API, `public.merge_guest_library_entries(jsonb)` (A-04, ADR-0016, §5 "Functions") and `public.replay_library_writes(uuid, jsonb)` (A-05, ADR-0017), with the same guards; the replay adds `expected_user_id`, a guard never a source (`42501` when `auth.uid()` is distinct from it), bounds a call to 100 writes, accepts per element exactly the keys of its `op` and checks the time form and the year-1 bound before any write, and its removals go through `private.remove_client_library_entry`, which filters on `auth.uid()` itself (pgTAP `070`, `071`). The merge function: `security definer` because it writes `updated_at`, which no API role may; `search_path = ''` and fully qualified names; `execute` revoked from `public`, `anon` and `authenticated`, then granted to `authenticated` only. Definer rights bypass RLS, so it scopes itself: the user is `auth.uid()` only (`42501` without one), never an input (an element naming `user_id`, `id` or `created_at` is refused), and every write and its conflict key hold `auth.uid()`, so a call reaches the caller's own rows only; the input is bounded (100 entries) and validated whole before any write, validation errors carry fixed messages with no value (a cast or constraint error can quote the caller's own input back to the caller only; the client keeps the code alone). A client-supplied time is honored on these two paths only (B1, extended to the replay by ADR-0017), capped at the server's `now()` of the writing call, so a clock ahead never pins a row in the future; every other API write gets the server time (`anon` and `authenticated` hold no privilege on `updated_at`). pgTAP: `010-privileges` (the only two functions an API role may execute, empty `search_path` everywhere), `050-guest-merge` (cross-user, `anon`, no user, validation, cap), `030` and `060` (a client cannot set `updated_at`). Accepted: a user can backdate only their own rows (an insert with a past time, or a delete then a merge), and a device clock behind only penalizes that user's own data; trusted server roles (`service_role`, `postgres`) can set a past time, as they can write any row; a later grant of `updated_at` to `authenticated` would let every write set its time, which `030` and `060` catch |
| Leaked privileged key | Only the anon key ships in the app; service role only in Edge Function secrets: today the `delete-account` function's env only (`SUPABASE_SERVICE_ROLE_KEY`, provided by the platform, never set by hand or stored in the repository), held by an admin client that keeps no session, never in a request, a response body, a header or a log (A-06, ADR-0018); gitleaks in CI |
| Token theft on device | Session in Keychain/Keystore via secure-store |
| Malicious provider payload | Zod parsing at the adapter boundary (§3: identity, default title, status and BR-06 inputs fail the whole response with `CatalogResponseError`, display fields fall back to `null` or `unknown`), rendering as text only. Image URLs (`toAllowedImageUrl`, `src/core/catalog/image-url.ts`) are kept only when https, at most 2048 characters (`IMAGE_URL_MAX_LENGTH`, the database check on `media_image_url`), with a host exactly in the provider allowlist (`JIKAN_IMAGE_HOSTS`: `cdn.myanimelist.net`, for every Jikan-compatible instance, so a configured base URL never widens it), no userinfo, port, fragment, backslash or whitespace, and a path and query from a safe character set (unreserved characters, `/` and percent escapes, a `%` only followed by two hex digits; `=` and `&` in the query); anything else gives `null` (no cover). The checks are plain string rules, not a URL parser: React Native's `URL` polyfill lacks `hostname`, so Jest and the device would read a URL differently. Covers render only through the ui `CoverImage` with the item's `imageUrl` as given (`expo-image` and FlashList are imported only in `src/ui/`, §2); the contract suite proves every adapter returns allowlisted urls or `null` (§3) and the search row and detail content tests that the image source is exactly the item's url. Library snapshot covers read back from storage are untrusted too: the library list re-checks them with `toAllowedImageUrl` and the provider's `imageHosts` before rendering, display only (§3 "Image hosts", §6 "Library"). Catalog errors never carry the query or provider text: Zod issues are dropped and the adapter's `RangeError` messages hold no value |
| Malicious deep link | Size limits first (`app/+native-intent.tsx`, `redirectSystemPath`): expo-router calls it for the initial link and every link received while the app runs, before it parses the link, and a link longer than `INCOMING_LINK_MAX_LENGTH` (2048) or holding more than `INCOMING_LINK_MAX_PERCENT_ESCAPES` (32) percent-encoded bytes (`src/core/schemas/incoming-link.ts`) opens Discover instead, which bounds the decode cost of a crafted link for the quadratic decoder of query-string 7 (decode-uri-component 0.2, GHSA-qr28-fpjm-wq7f, ignored in `pnpm-workspace.yaml` until expo-router ships a compatible query-string); other links pass unchanged. Route params validated with Zod at the route boundary (`mediaRouteParamsSchema`: exact namespace and kind, bounded decimal id, arrays rejected); invalid params and unmatched links show a translated error; a valid link only reads the catalog (`getDetail` through `useMediaDetail`) and the library entry (`useLibraryEntry`), and an id the provider does not have (404) shows the translated not found state; no write triggered by a link: library writes happen only on user taps, and the ADR-0009 snapshot refresh is shown on view but persisted only with the next library action on the detail screen (§2 "Deep links and route params"). Auth email links (ADR-0014, §8): params parsed with `parseAuthLinkParams` (bounded code and flow id, arrays rejected, `error_description` never shown); PKCE, so a code is useless without the verifier stored on the requesting device, which also blocks login CSRF and a hijacked `tsuzuki://` scheme; no tokens in any URL (no implicit flow, `detectSessionInUrl: false`); the code is exchanged only when the user taps Continue or submits a valid new password, never on open. OAuth redirect (ADR-0015, §8): parsed with Zod in core (prefix of the redirect URL, bounded code and flow id, repeated params rejected, `error_description` never read); only the URL returned by the browser session the user's tap opened is exchanged, and only when its flow id is the one that call started, so a code injected by another app or page fails before or at the exchange (PKCE); the `auth/oauth-callback` route never reads its params and writes nothing |
| Account takeover | Email confirmation required; password policy (10 code points, letters and digits, mirrored client side, §8) on every project; Supabase per-IP auth rate limits and the per-email `max_frequency`; no account enumeration by sign up, resend or reset (one narrow exception: a second email within 60 s for an existing account is rate limited, ADR-0014); sign out revokes the device's session; `secure_password_change` on. Captcha: provider-agnostic seam (`CaptchaTokenProvider`) on sign up, sign in, reset and resend, disabled (`noCaptcha`) until a provider is wired (A-08); until then bots are bounded by the rate limits only. OAuth (ADR-0015): PKCE with the flow id bound to the call, which blocks login CSRF (a session the user did not start) and code injection; no tokens in any URL; the provider page runs in a browser auth session, so the app never sees the provider password; Supabase links a provider identity only to an account with the same verified email, never taking over an unconfirmed one; `/authorize` has no captcha, only the per-IP rate limits |
| Library data at rest offline | The account library's device copy and write queue (A-05, ADR-0017) hold titles and notes in the unencrypted MMKV instance, like the guest library and the persisted cache: reviewed with the MMKV encryption in R-04. A sign out or an account deletion deletes the signed-out user's copy and queue, after a sync and, for writes still unsynced, the user's confirmation, and closes every instance of that user, so no late write recreates them (A-06, ADR-0018, §4, §8); the guest library goes too once its merge concluded. Accepted: an involuntary session end (a refresh token expired or revoked, the account deleted from another device) purges nothing, so that user's documents stay until their next sign in and sign out or until the app data is cleared (A-10). Per user id, parsed with Zod on every read (an invalid element dropped, a damaged document reported with its reason and document only, never thrown); never logged, never in an error or a report tag; TanStack mutations are never persisted, so no write variables reach the query cache document. A replay depends on the session and the queue only, never on a link parameter |
| Account deletion (A-06, ADR-0018) | The `delete-account` Edge Function acts only on the user of the caller's own token. The gateway (`verify_jwt = true`) refuses a request without a valid project JWT; the function answers POST only, reads nothing of the request but `Authorization`, exactly `Bearer <token>` with three base64url segments of at most 8192 characters (anything else 401, no call made), and has the auth server check the token with `auth.getUser(token)`, never a local decode: the anon key, another project's token or a deleted user's token is refused (401), while a timeout, a rate limit or an unreachable auth server answers 503 without deleting. The user id comes only from that verified user and must be a UUID; the body and the query are never read, so a request cannot name another user. Every answer is a fixed JSON from one table, with `Cache-Control: no-store`: no error text, id, token or key, so a supabase message (which can hold an email) never leaves the function. No CORS header: a web page's preflight gets no answer, and the bearer token is never a cookie, so no cross-site request carries it (the future web app decides a restricted CORS in its own ADR). No logging: the platform logs the status only. The client sends no body and no user id and reports only `unknown`, with the status and a fixed code; the screen reads no param and deletes only on the second deliberate tap, so a link never deletes anything. pgTAP `080-account-deletion` pins the cascades. Accepted risk (owner decision): anyone holding the unlocked device with the app signed in can delete the account, irreversibly; mitigated only by the device lock, the session readable only while unlocked (`WHEN_UNLOCKED_THIS_DEVICE_ONLY`), the dedicated screen and the double confirmation. A stolen access token (valid up to an hour) can delete it too, like any other account write. Apple token revocation is deferred to A-09: no Apple identity can exist while the provider is disabled |
| Credentials at rest | Passwords live only in form state and in the request: auth mutations are never paused or persisted (`networkMode: 'always'`, `gcTime: 0`, no mutation dehydrated, §8), never logged or reported; the session and the PKCE verifiers are in the secure store only (`SessionStorage`) |
| Vulnerable dependency | Dependabot alerts, recurring dependency update (M-01), `pnpm audit` (high blocks CI), CodeQL |
| Personal data in logs | No PII logging; `no-console` outside `src/platform/sentry.ts`; Sentry errors only (no tracing, no replay), `sendDefaultPii: false`, disabled in development and without a DSN; `beforeSend` and `beforeBreadcrumb` scrub emails, JWTs, bearer tokens and API keys, auth and cookie headers, request bodies and `request.env`, user fields and notes (structured fields, JSON/JS keys quoted or unquoted with either quote style: `"notes": ...`, `'notes': ...`, `notes: ...`, and free-text `notes=` up to `&` or end of line), and formatted phone numbers (international `+` forms and national numbers in separated groups; dotted digit groups are also replaced, a harmless over-scrub); `ErrorContext` carries non-personal tags only; recent searches and the guest library stay on the device and are never logged or reported (a damaged guest store is reported as a `LibraryStorageError` with its reason only, §4), and search queries are not persisted in the query cache (§6); catalog errors (`src/core/errors/catalog-errors.ts`) carry no URL, query string or search text, no underlying error message and no `cause`, since search text is user input and errors reach Sentry; the catalog failure monitor (§3) reports the instance id (a fixed constant, never the configured URL) and the failure kind only, never a URL, query, status code or response text; auth errors (`AuthError`, §4) carry a reason only, and only `unknown` is reported, with the operation and the Supabase error code, never an email, password, code, token or server message; account library errors (`LibraryRemoteError`, §4) carry a reason only, never the PostgREST message or detail, which can quote the row (user id, media key), and only `rejected`, `unknown` and `invalid-row` are reported, with the operation, the error code and the HTTP status; the guest merge's other failures are reported with `{ source: 'guest-merge' }` and no tag, and the repository errors they carry hold no entry, key or user id (A-04); account deletion errors (`AccountDeletionError`) carry a reason only, and only `unknown` is reported, with the operation, the HTTP status and one of the function's fixed codes; device purge failures carry their step only, never the storage error (A-06); the app state holds the user id, never the email; EU data region (ADR-0012). Accepted limitations: native crash events do not pass through the JS `beforeSend`; they are covered server side by the Sentry project's Data Scrubber, default scrubbers and IP address storage prevention ("Environment setup (owner)"). Unseparated digit runs are not treated as phone numbers, which would also match ids and timestamps |
| Misconfigured or cleartext backend | Env validated with Zod at build time and again at startup; every env URL is `https:` (the optional catalog base URL `EXPO_PUBLIC_JIKAN_BASE_URL` also has no userinfo, query or fragment), no cleartext exception in the native config; the catalog base URL is build-time only, never switchable remotely (ADR-0013); the catalog http client rejects a non-https URL with a `RangeError` before taking a token or calling `fetch` |
| Third-party catalog provider | The provider sees the IP address and User-Agent of every device and the search text it is sent; Tenrai logs IPs and User-Agents for up to 90 days (its privacy policy). No user id, token, email or library data is sent to it. The privacy policy (R-05) names the provider and this logging; a self-hosted instance or a shared server-side cache (§11) removes the third party |

- `APP_VARIANT` is set in the `env` of each build profile in `eas.json`, and in `.env.local` for `expo start`. The other variables (`EXPO_PUBLIC_SUPABASE_URL`, `EXPO_PUBLIC_SUPABASE_ANON_KEY`, `SENTRY_DSN`, the optional `EXPO_PUBLIC_JIKAN_BASE_URL`, and the secret `SENTRY_AUTH_TOKEN` for `preview` and `production`) live in the EAS environment of the same name; the `development` profile sets `SENTRY_DISABLE_AUTO_UPLOAD=true`. `app.config.ts` validates them with `src/core/schemas/app-env.ts` and passes them in `extra.env`: always on the EAS build worker (`EAS_BUILD=true`), and elsewhere only when `EXPO_PUBLIC_SUPABASE_URL`, `EXPO_PUBLIC_SUPABASE_ANON_KEY`, `SENTRY_DSN` or `EXPO_PUBLIC_JIKAN_BASE_URL` is set (a partial or invalid local env still fails: the catalog URL alone fails on the missing Supabase values). Without any of them, `extra.env` is left out and the app fails closed at startup. `APP_VARIANT` is read on its own: a valid value selects the app id and name even without the other variables, an invalid one fails, a missing one falls back to `development`. The Expo CLI compiles `app.config.ts` but loads its imports with plain Node, which strips TypeScript types (Node >= 22.18) yet resolves no extensionless `.ts` import, so `app.config.ts` first loads `tools/expo/resolve-ts-imports.cjs`, a `node:module` resolve hook (no new dependency). It retries a relative import from a TypeScript file (or the app config) with `.ts` only when the error is a module-not-found (`ERR_MODULE_NOT_FOUND` / `MODULE_NOT_FOUND`), rethrows the original error when the retry fails, and forces the `module-typescript` format only for the app config's import graph.
- The EAS CLI (`eas build` in `eas-preview.yml` and `release.yml`, `eas credentials`) also evaluates `app.config.ts` locally, with `EXPO_NO_DOTENV=1` (`.env.local` is ignored) and the profile `env` from `eas.json` only (`APP_VARIANT`), not the EAS environment: the config then picks the variant, hence the app id that selects the credentials, without validating the other variables, which the build worker validates. Because the config reads `APP_VARIANT` on its own, `eas credentials` and a local `eas build` need no env set up. The `EXPO_PUBLIC_*` and `SENTRY_DSN` values of the EAS environment are created with `plaintext` visibility (a `secret` value is readable only inside the cloud build), and the Expo robot token must have access to them. `SENTRY_AUTH_TOKEN` is a `secret` EAS variable, read only by the cloud build.
- Catalog instance (ADR-0013): `EXPO_PUBLIC_JIKAN_BASE_URL` is an optional `plaintext` EAS variable, validated as `jikanBaseUrl` by `src/core/schemas/app-env.ts` (https only, a host, an optional port and path, no query, fragment or userinfo; a trailing slash is stripped; empty counts as absent) and re-parsed at startup. Unset, the app uses Tenrai; set, a self-hosted Jikan at that URL. It is per variant and holds no secret. Switching needs only the EAS value plus a build, or an update published with its environment (`pnpm update:publish <variant>`) when only JavaScript changes, so no store release.
- Versions: `eas.json` sets `cli.appVersionSource: "remote"` and the `production` profile `autoIncrement: true`, so EAS owns the Android `versionCode` (incremented on every production build); the version name stays in `app.config.ts`, written by release-please.
- `pnpm-workspace.yaml` `allowBuilds` denies the `@sentry/cli` install script: the binary comes from its optional platform packages, the script is only a fallback download.
- Every env URL is `https:`. The local `supabase start` stack (Docker) is used only by `pnpm test:rls` and `pnpm db:types`; development builds use the staging project.
- `expo-updates` runs with `runtimeVersion: { policy: 'appVersion' }`; updates are published by hand with `pnpm update:publish <variant>` (`tools/expo/eas-update.mjs`), from a commit carrying the app version of the target binaries. The script runs `eas update --channel <variant> --environment <variant>` and rejects a missing or unknown variant and a `--channel` or `--environment` argument that differs from it, and rejects `--branch` and `--auto`, which would bypass the channel's branch. Off the EAS build worker, `app.config.ts` leaves `extra.env` out when no Supabase or Sentry value is set, so an update exported without its EAS environment would fail closed at startup on every device that downloads it. Running `eas update` or `expo export` directly is not allowed.
- EAS build quota: the Expo account is on the "EAS Free" plan; the current build limits are on expo.dev → Billing. To save builds, `eas-preview.yml` runs only for pushes to `dev` that touch the app, native config, dependency and migration paths listed in the workflow (`paths`), or on manual dispatch; within a run the staging migrations always apply and the preview build runs only when a build path changed.
- Database migrations are applied before the build of the same commit and must stay compatible with the binaries already installed (add columns and tables first, remove them in a later release).

### Branching model

| Branch | Role | Receives | Merge method |
| --- | --- | --- | --- |
| `dev` | Development/integration, deployed to staging; every PR targets it explicitly (`--base dev`) | PRs from `feat/*`, `fix/*`, `chore/*`, `docs/*`, `test/*`; back-merges from `main` | Squash; merge commit for back-merges from `main` only |
| `main` | Production, always releasable, GitHub default branch | Release PRs from `dev`, hotfix PRs, the release-please PR | Merge commit for release PRs; squash for hotfix and release-please PRs |
| `hotfix/*` | Urgent production fix | Branched from `main`, merged into `main`, then `main` merged back into `dev` | Squash into `main` |
| `release-please--branches--main--components--tsuzuki` | Release PR `chore(main): release X.Y.Z` (version + changelog). release-please puts the component in the branch name even with a single package and `include-component-in-tag: false` | Opened and updated by release-please on `main` | Squash into `main` |

```mermaid
flowchart LR
    PR[PR to dev] --> P[PR policy<br/>base branch + title + commits]
    P --> Q[lint + typecheck + tooling tests]
    Q --> T[unit + component tests + coverage]
    T --> S[RLS tests + gitleaks + audit + CodeQL]
    S --> D[merge dev]
    D --> ST[staging migrations<br/>+ EAS preview build]
    ST --> R[release PR<br/>dev to main]
    R --> RP[release-please PR<br/>on main]
    RP --> TAG[tag vX.Y.Z<br/>+ GitHub release]
    TAG --> PROD[prod migrations<br/>+ production build<br/>submit gated off]
    TAG --> BM[main merged back<br/>into dev]
```

- Both `dev` and `main` are protected by the `protect-main-dev` ruleset: PR only, no direct push, no force push. Required status checks and code scanning results are added by the owner once F-04 is merged into `dev` (see "CI workflows and required checks" and "Repository settings (owner)").
- A release PR from `dev` to `main` also requires the owner's approval and the E2E suite (from R-01). Until then, the owner runs `pnpm test:e2e` locally before merging a release PR.
- JS-only fixes can ship with EAS Update on the matching runtime version; native changes require a store build.

### CI workflows and required checks

- All workflows run on `ubuntu-24.04` and use `pull_request`, never `pull_request_target`.
- `permissions: {}` at workflow level; each job grants only what it needs.
- Checkout with `persist-credentials: false`; concurrency groups; a timeout on every job.
- Third-party actions are pinned by full commit SHA with a version comment.
- Jobs that install dependencies use the local composite action `.github/actions/setup/`: `pnpm install --frozen-lockfile`, pnpm store cached on the lockfile hash.
- Accepted risk: like every `pull_request` workflow, the PR policy checks run the pull request's own copy of `tools/ci/` and `commitlint.config.mjs`, so a PR could weaken its own policy checks. The owner reviews every change to these files; the run has a read-only token and no secrets.

| Workflow | File | Triggers | Jobs |
| --- | --- | --- | --- |
| CI | `ci.yml` | PR to `dev` or `main`; push to `dev` (warms the cache, re-checks the squashed result) | `lint`, `typecheck`, `test`, `tooling`, `rls`, `security` |
| PR policy | `pr-policy.yml` | PR to `dev` or `main`: opened, edited, synchronize, reopened | `base-branch`, `pr-title`, `commits` |
| CodeQL | `codeql.yml` | PR and push to `dev` or `main`; weekly schedule | `codeql (actions)`, `codeql (javascript-typescript)` |
| Release | `release-please.yml` | Push to `main` | release-please (see "Releases") |
| EAS preview | `eas-preview.yml` | Push to `dev` touching the app, native config, dependency and migration paths listed in the workflow (`paths` allowlist); `workflow_dispatch` | `staging` (GitHub Environment `staging`): `supabase link` + `supabase db push` to the staging project on every run (applies only pending migrations, idempotent, no EAS quota); then `tools/ci/eas-preview-scope.mjs` (CLI `tools/ci/check-eas-preview-scope.mjs`) reads `git diff --name-only <before>..<sha>` and runs `eas build --profile preview --platform android --non-interactive --no-wait` only when a build path changed (tests and Markdown ignored). A manual dispatch, or a push whose `before` commit is unusable, builds. A pending run cancelled by the concurrency group can drop changes from that diff, which is why migrations are never gated; a skipped build is harmless because the next app-path push builds the whole current tree |
| Production release | `release.yml` | Push of a tag `v*` | `production` (GitHub Environment `production`, owner approval required): full-history checkout, then fails before any migration or build unless the tag's commit is an ancestor of `origin/main` (`git merge-base --is-ancestor`); then `supabase link` + `supabase db push` to the production project, then `eas build --profile production --platform android --non-interactive --no-wait`; store submission (`eas submit`) only when `vars.STORE_SUBMIT_ENABLED == 'true'` |
| Back-merge | `back-merge.yml` | Push of a tag `v*` | `back-merge`: opens a PR `main` → `dev` with `RELEASE_PLEASE_TOKEN` unless `dev` already contains `main`; the owner merges it with a merge commit |

- The deployment workflows follow the rules above (pinned SHAs, `permissions: {}` with `contents: read` only where checkout needs it, checkout with `persist-credentials: false`, timeouts) and their concurrency groups never cancel a running job, which could stop a migration halfway. They run the Supabase CLI and `eas-cli` locked by the lockfile (`pnpm exec`). Builds are Android only: iOS builds stay off until `vars.IOS_BUILDS_ENABLED == 'true'`, and both repository variables are unset.
- Secrets and variables, per GitHub Environment (`staging` and `production`): secrets `EXPO_TOKEN` (Expo robot access token), `SUPABASE_ACCESS_TOKEN`, `SUPABASE_DB_PASSWORD` (of that environment's project); variable `SUPABASE_PROJECT_REF`. `RELEASE_PLEASE_TOKEN` stays a repository secret. `SENTRY_AUTH_TOKEN` is an EAS secret, not a GitHub one: source maps are uploaded by the EAS build.
- Environment protection: `staging` deploys from the branch `dev` only; `production` deploys from tags `v*` only and requires the owner's approval, with "Prevent self-review" off (the owner is the only reviewer).

| Required check | Workflow | Verifies |
| --- | --- | --- |
| `lint` | CI | ESLint (zero warnings) + Prettier check |
| `typecheck` | CI | `tsc --noEmit` |
| `test` | CI | Jest with coverage thresholds |
| `tooling` | CI | `pnpm test:tooling` |
| `rls` | CI | `pnpm exec supabase db start` (database only, Supabase CLI locked by the lockfile), `pnpm test:rls`, then checks that the committed database types match the migrations (`pnpm db:types`, then `git diff --exit-code`), then stop |

Target state: after F-04 is merged into `dev`, the owner adds the eleven checks above as required status checks (source GitHub Actions) to `protect-main-dev` for both `dev` and `main`, plus the rule "Require code scanning results" (CodeQL: security alerts High or higher, other alerts Errors). Until then the checks run but do not block a merge. The E2E suite becomes a release PR requirement from R-01.

### Releases

release-please (`release-please.yml`) runs on push to `main`. Config: `release-please-config.json` + `.release-please-manifest.json`, release type `node`, tags `vX.Y.Z` without component, `bump-minor-pre-major`, `CHANGELOG.md`; the version is also written into `app.config.ts` through a marker.

1. A release PR from `dev` to `main` is merged with a merge commit.
2. release-please opens or updates `chore(main): release X.Y.Z` on `main`. Hotfixes squashed into `main` feed the same PR.
3. Merging the release-please PR creates the tag `vX.Y.Z` and the GitHub release.
4. After each release or hotfix (a hotfix ships through the next release-please tag), `back-merge.yml` opens a PR from `main` to `dev` on the tag; the owner merges it with a merge commit, so they never diverge.

- `chore` and `docs` commits alone produce no release.
- First release: there is no `v0.1.0` tag, so its changelog covers the whole history of `main`; `chore` and `docs` entries are hidden by default.
- Token: a fine-grained personal access token scoped to this repository only (Contents, Pull requests, Issues: read and write), stored as the Actions secret `RELEASE_PLEASE_TOKEN` (see "Repository settings (owner)"). A PR created with `GITHUB_TOKEN` would not trigger the required checks, and its tag would not trigger `release.yml` and `back-merge.yml`. With the owner's token the release commits keep the single author.
- The release flow needs merge commits on `main` and `dev` and PR-title squash commits; the ruleset and merge settings it depends on are listed in "Repository settings (owner)".

### Repository settings (owner)

GitHub settings that no file in the repository can enforce. The owner applies them once, in this order:

1. Security: enable Dependabot alerts (Settings → Advanced Security). Alerts only, no Dependabot PRs.
2. Actions (Settings → Actions → General):
   - enable "Require actions to be pinned to a full-length commit SHA";
   - optionally, choose the policy that allows only selected actions: tick "Allow actions created by GitHub" (covers `actions/*` and `github/*`, so the CodeQL action) and list `pnpm/action-setup@*, googleapis/release-please-action@*` as the specified actions;
   - require approval to run workflows for all outside contributors (the repository is public).
3. Now, before the next merge into `dev`: Pull requests (Settings → General): set the default squash commit message to "Pull request title" (title = PR title, body blank) and disable "Allow rebase merging". The current default uses the commit message for a single-commit PR, which bypasses the checked PR title, and a `* <message>` list body can exceed commitlint's `body-max-line-length` (100). 4. After F-04 is merged into `dev`: add the eleven required checks (source GitHub Actions) and "Require code scanning results" to `protect-main-dev`, for both `dev` and `main` (see "CI workflows and required checks").

   - Ruleset: `protect-main-dev` requires linear history, which blocks the merge commits of release PRs and back-merges. Remove `required_linear_history`, remove `rebase` from the allowed merge methods, and split the ruleset per branch with the merge methods of the branching table: `dev` allows squash and merge (merge only for back-merges from `main`), `main` allows merge, plus squash for hotfixes and the release-please PR. Both rulesets keep the required checks and the code scanning rule of step 4.
   - Secrets: store `RELEASE_PLEASE_TOKEN` as an Actions secret (see "Releases").
   - Tag ruleset (Settings → Rules → Rulesets → New tag ruleset): `protect-release-tags`, enforcement active, target tags matching `v*`; rules "Restrict creations", "Restrict updates", "Restrict deletions" and "Block force pushes"; bypass list: the Repository admin role only (the owner). release-please creates the tags with the owner's token `RELEASE_PLEASE_TOKEN`, so it bypasses the ruleset; nobody else can create, move or delete a `v*` tag, which together with the `main` ancestor check of `release.yml` keeps production deployments on reviewed commits.

    ```sh
    pnpm exec supabase functions deploy delete-account --project-ref <staging-ref>
    pnpm exec supabase functions deploy delete-account --project-ref <prod-ref>
    ```

    `supabase/config.toml` applies `verify_jwt = true`; never pass `--no-verify-jwt`. `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` are provided by the platform: no secret to set. Local check before the first deploy: `pnpm exec supabase start`, then `pnpm exec supabase functions serve`; a POST without a token to `http://127.0.0.1:54321/functions/v1/delete-account` answers 401. Post-deploy check, per project: a POST without a token to `https://<project-ref>.supabase.co/functions/v1/delete-account` answers 401; then, on a build pointing at the project, a throwaway email account signed in deletes itself: the deleted state shows, and the user is gone from Authentication → Users. A `session-expired` with a fresh session means the gateway's `verify_jwt` does not accept the project's JWTs (asymmetric signing keys); an `unknown` reported with the code `server-misconfigured` or `deletion-failed` points at the keys (legacy keys disabled). The owner then decides the fix (for example `verify_jwt` off for this function, `getUser` staying the real check), recorded as an Update of ADR-0018.

## 11. Evolution paths

- **Web version**: Next.js app in a pnpm + Turborepo monorepo. `src/core/` moves to `packages/core` as is; the web app implements its own screens and a web `platform` layer (ADR-0006), e.g. a `LocaleAdapter` over `navigator.languages` and the `languagechange` event (ADR-0011).
- **Dedicated backend**: if Edge Functions are not enough (shared catalog cache, scheduled notifications), Next.js API routes or a dedicated service implement the same repository interfaces over HTTP; Postgres and Supabase Auth stay. A shared server-side catalog cache would also pool the provider's per-IP limits and keep user IPs away from the provider (§6, §9); it is written only by that trusted server (ADR-0009).
- **Fallback providers** (ADR-0013): Tenrai has no SLA and can be discontinued at any time; sustained failures reach Sentry (§3). The fallback is AniList if authorized (C-09 "AniList adapter (pending authorization)"), else a self-hosted Jikan (C-10 "Self-hosted Jikan"), which is one env value (§10). AniList: GraphQL, good manhwa/manhua coverage, its own namespace `anilist` unless C-09 decides a mapping to MAL ids (the AniList cross-reference is deferred to that item); free under $150 per month of revenue and a commercial licence above, so any monetization triggers a review, and the app name must not contain "AniList".
- **More providers**: MangaUpdates (chapter releases) as a new `CatalogProvider` adapter, held to the same contract suite (§3).

- Each project's `testMatch` is built from one list of root-relative patterns, and `jest.config.mjs` fails when a test file matches no project or more than one. No path segment of a pattern starts with a brace group or another glob special character: on Windows Jest turns the slash before it into a backslash that escapes it and the pattern matches nothing (`src\{ui,core}`), so folder alternatives are spelled out one pattern each (`tools/jest/jest-config-globs.test.mjs`).
- Determinism:
  - `TZ=UTC` is set at the top of `jest.config.mjs`, so workers inherit it.
  - Fake timers are on by default; the shared setup (`test/core/fixed-clock.ts`) resets the clock to `Date.UTC(2026, 0, 1)` before every test, so a test that moves the clock cannot leak into the next.
  - Fake timers also fake `performance.now()`, the monotonic clock of the catalog http client (§6): it starts at 0 at each install, so in every test, moves only when the timers advance and is untouched by `jest.setSystemTime` (`test/core/determinism.test.ts`). Caveat for the `mobile` project: after `jest.useRealTimers()`, React Native's Jest setup stubs `performance.now` with `Date.now`, which is not monotonic.
  - Mocks are restored after each test.
  - Test order is randomized within each file by the global Jest `randomize` option; the seed is printed on each run.
  - Unexpected `console.error` / `console.warn` calls are recorded and fail the test in `afterEach` (throwing inside the console call could be swallowed, e.g. by MSW).
  - The three Jest projects share these rules: `test/core/setup.ts`, `test/core/setup-dom.ts` and `test/mobile/setup.ts` all use `fixed-clock.ts` and `fail-on-console.ts`, and the last two `no-network.ts`.
- `testTimeout` is 60 s, set at the Jest root because Jest 29 reads it only there: the first test of a file that renders a lazily required React Native component (`ScrollView`, the router) loads and instruments it inside the test body, up to about 35 s on a cold cache (every CI run), past the 5 s default; a hung test still fails at 60 s.
- Coverage is collected from `app/` and `src/` (tests, fixtures, mocks, declarations and tool configs such as `tailwind.config.ts` excluded); untested files count as 0 %. Thresholds: global 70 % lines, `src/core/` 90 % lines and branches. Jest errors when a threshold path matches no file, so the `src/core/` threshold group is declared with the first source file in `src/core/`.
- Core tests are split between `core` and `core-dom` by extension (`.ts` / `.tsx`), not by a per-file `@jest-environment` docblock, which would keep the `core` setup: its `msw/node` server does not load under jsdom (browser export conditions resolve `msw/node` to nothing, and jsdom lacks the fetch globals MSW needs). F-06 added `core-dom` and `@testing-library/react` with the first core hook, the i18n provider and `useTranslation`.
- Missing translations are caught by three checks, each covering a case the others miss (ADR-0011):
  - parity: the checker `test/core/i18n-catalog-parity.ts`, applied to the real catalogs by `src/core/i18n/catalogs.test.ts`, requires `fr.json` to have exactly the keys of `en.json`, the same `{{placeholders}}` and every plural category of `Intl.PluralRules` for its language. It is the only check for a key in `en.json` but not in `fr.json`: that key resolves through the `en` fallback, so typecheck and the runtime handler never see it;
  - typecheck: keys are typed from `en.json`, so a key absent from it fails;
  - runtime: `onMissingKey` reports a key found in no catalog (built at run time or cast). `renderWithProviders` / `providersFor` (`test/mobile/render-with-providers.tsx`) render routes and features in `I18nProvider` with the real catalogs, English by default, and an `onMissingKey` that fails the test (it logs a `console.error`, which the console check turns into a failure; a throw would abort the render and leak listeners into the next test). The composition root reports them through the `ErrorReporter` (console in development, Sentry in release), and an unexpected `console.warn` fails a test rendering the root layout.
