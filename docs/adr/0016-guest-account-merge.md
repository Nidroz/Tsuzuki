# ADR-0016: Guest to account library merge

- Status: Accepted
- Date: 2026-10-31, revised 2026-11-01 (the open question resolved: B1)

## Context

A-04 implements FR-22 ("on first sign-in, guest data is merged into the account") under BR-08: each local entry is upserted, on conflict the most recent `updated_at` wins, and the local guest store is cleared after a successful merge. Constraints:

- Guest timestamps are client values: `updatedAt` is the device time of the entry's last change (BR-09), normalized by `timestampSchema` to the `Date#toISOString` form (L-02). Every stored guest entry has passed `libraryEntrySchema`, so it fits the database limits (ADR-0009, update).
- Schema v1 lets the database set a signed-in user's timestamps: `created_at` and `updated_at` default to `now()` on insert, a `before update` trigger stamps `now()`, and `authenticated` has no insert or update privilege on either column (`ARCHITECTURE.md` §5). A row the client writes therefore takes the write time, not the time of the change it carries.
- The account store (A-03) is created for one user id, filters its requests on that id on top of RLS, and checks before every call that the client's session is still that user's (the session guard), with an accepted residual window of one session storage read.
- `ARCHITECTURE.md` §4, §5 and §8 sketched a `security invoker` Postgres function followed by `guest.clear()`, "to be finalized in A-04".
- The main risks are losing the guest's only copy of an entry (a failed or interrupted merge, an entry changed while the merge runs), writing guest entries into another user's account (a session change during the merge), and letting a client choose the time of its writes outside the merge.

Options considered:

- **(a) Conditional client writes under RLS, merged rows at the server time** (the first design of this ADR, built first): inserts `on conflict do nothing` and updates filtered on `user_id`, the key and `updated_at <` the guest time, under the existing grants, in rounds that read the keys again after a concurrent write; no migration. Rejected by the owner: the database stamps its own time on every row it writes, so a merged row loses the time of the guest change and BR-08 fails across devices ("Resolution of the open question", below).
- **(b) A column grant on `updated_at` to `authenticated`** (the B1 first sketched in the open question): the trigger keeps a client-written value capped at `now()`, and the conditional writes send the guest time. Rejected: every regular write (`save`, the library writer's `+1`) could then set its own `updated_at`, while the owner allows a client time on the merge path only.
- **(c) A transaction-local setting honored by the trigger** (the B2 sketch: a `security invoker` RPC sets a variable, and the trigger keeps the client time while it is set): the guard is an implicit channel between a function and a trigger, which any later code setting that variable reopens (and a variable read from the request, such as a header, would be set by the client itself); a privilege is explicit and pinned by pgTAP. Rejected.
- **(d) An Edge Function with the service role**: it bypasses RLS, so the user scoping becomes the function's own code anyway, with a privileged key on the path of every merge, a second runtime and a deployment step. Rejected.
- **(e) Plain client upserts after comparing with a read**: an account change from another device landing between the read and the upsert would be overwritten. Rejected.
- **(f) B1 as the owner constrained it**: one `security definer` RPC writes each guest entry with its own time through a private rule, and the timestamp trigger keeps an explicitly written `updated_at`, capped at `now()`, which only roles holding the column privilege can write; every API write keeps the server time. Chosen by the owner.

## Decision

### Rule

BR-08 per guest entry: it is inserted when the account has no entry of its key; it replaces the account values only when its time is strictly later than the account row's `updated_at`; otherwise the account copy, newer or as recent, is kept and nothing is written. The time of a guest entry is its own `updatedAt`, capped at the server's `now()` ("Account side").

- `src/core/domain/guest-merge.ts`, pure: `guestMergeDecision(guestUpdatedAt, accountUpdatedAt | null)` returns one of `GUEST_MERGE_DECISIONS`: `insert` (the account has no entry of the key), `replace` (the guest `updatedAt` is strictly later) or `keep` (the account copy is newer or equal). It is the reference statement of the rule: the database function applies the same rule at the write, and the in-memory fake (`createFakeAccountLibraryRepository`) uses it; production code does not call it. `isSameLibraryEntry(a, b)` is the field by field equality the guest store removes by: the key (`compareMediaKeys`), the snapshot (`isSameMediaSnapshot`) and every other field, `createdAt` and `updatedAt` included.
- Equal timestamps keep the account copy: deterministic, no write, and a retry stays a no-op.
- Both sides are compared in the `Date#toISOString` form (milliseconds, UTC) on the client. The server compares its microsecond `updated_at` with the guest millisecond value (`stored.updated_at < guest`), which agrees with the client comparison of the truncated value: for a millisecond value `g`, `trunc(a) < g` exactly when `a < g`, since truncation keeps the order (pinned by pgTAP `050-guest-merge`).

### Interfaces

`src/core/repositories/library-repository.ts` (the doc comments there hold the full contracts, the timing of merged entries included):

```ts
export interface GuestLibraryRepository extends LibraryRepository {
  removeUnchanged(entries: readonly LibraryEntry[]): Promise<void>;   // after a successful merge (BR-08)
  clear(): Promise<void>;                                             // the sign-out purge (FR-25, A-06)
}

export interface AccountLibraryRepository extends LibraryRepository {
  mergeGuestEntries(entries: readonly LibraryEntry[]): Promise<void>; // BR-08, FR-22
}
```

`createSupabaseLibraryRepository` returns an `AccountLibraryRepository`.

### Account side

Database, migration `supabase/migrations/20261101182502_guest_merge_client_time.sql`:

- Timestamp trigger: `private.set_library_entry_updated_at()` (`security invoker`, `search_path = ''`, execute revoked from `public`, `anon` and `authenticated`) replaces `private.set_updated_at` on `library_entries` only (`profiles` keep it), and the trigger `library_entries_set_updated_at` now fires `before insert or update`. An update leaving `updated_at` unchanged gets `now()`: that is every API write, since `anon` and `authenticated` hold no privilege on the column, so a client can neither set nor change it (a direct attempt fails with `42501`). A value set explicitly is kept, capped with `least(…, now())`, and so is an inserted one (its `now()` default unless given). Only a role holding the column privilege can set it: the merge function's owner and the trusted server roles (`service_role`, in Edge Functions only).
- The rule of a client write carrying its own time: `private.write_client_library_entry(entry jsonb) returns boolean`, `security invoker`, `search_path = ''`, execute revoked from `public`, `anon` and `authenticated`, in schema `private`, which the API does not expose. The user is `auth.uid()`, never an input (`42501` without one); the time is `least(entry updated_at, now())`, a null or infinite one raising `22023`. It inserts the entry, or, on a conflict on `(user_id, id_namespace, media_kind, external_id)`, updates the values and the time only `where stored.updated_at < excluded.updated_at`; it never updates the key, `user_id`, `id` or `created_at`. It returns `true` when written, `false` when kept. The caller validates the shape of `entry`; any other key is ignored.
- The exposed function: `public.merge_guest_library_entries(entries jsonb)` returns one row per entry, in input order: `(id_namespace, media_kind, external_id, user_id, outcome)`, `outcome` `written` or `kept`. `security definer`, owner `postgres` (it writes `updated_at`, which no API role may), `search_path = ''` and fully qualified names; execute revoked from `public`, `anon` and `authenticated`, then granted to `authenticated` (`service_role` keeps Supabase's default). Definer rights bypass RLS, so the scoping is the function's own: `auth.uid()` (`42501` without one) in every write and in the conflict key, never a user id from the input. The input is validated whole before any write, each failure raising `22023` with a fixed message holding no value: a JSON array of at most 100 elements (`max_entries`), each an object holding exactly the 15 writable columns and `updated_at` (never `user_id`, `id` or `created_at`), `updated_at` a string of the RFC 3339 form the client sends (checked before any cast, so a BC date, `infinity` or a literal such as `epoch` or `now` is refused; migration `*_guest_merge_time_format.sql`, also enforced by `private.write_client_library_entry` with a lower bound of the year 1, so A-05 inherits it), no key twice (compared as the table types them). Each element then goes through `private.write_client_library_entry`. One call is one transaction: a validation, constraint or cast error rejects the call, and nothing of the batch is written.

Client: `mergeGuestEntries(requests, entries)` lives in `src/core/repositories/supabase/library-merge.ts`, called by the account store. It builds on the request helpers shared with the store in `library-requests.ts` (`createLibraryRequests`: the session guard, the request timeout `LIBRARY_REQUEST_TIMEOUT_MS`, the error mapping and reporting) and on the write payload of `library-row.ts` (`toLibraryRowPayload`, to which it adds the entry's `updatedAt` as `updated_at`).

- Input: every entry is validated with `libraryEntrySchema`; an invalid entry, or two entries of one key, reject with a `RangeError` without any value, and nothing is sent. An empty list resolves without a request.
- Batches of `GUEST_MERGE_BATCH_SIZE` (100, which must not exceed the function's `max_entries`: a larger batch is refused with `22023`), one after the other, each one call `client.rpc('merge_guest_library_entries', { entries })` behind the session guard and under the request's single timeout timer (a session read that does not answer in time rejects with `network`, and nothing is sent). A failed batch stops the merge; the batches before it stay written.
- The answer is parsed with Zod (the key, `user_id`, the outcome): a row of another user (the A-03 residual window: the token changed between the guard and the request) rejects with `signed-out`, not reported, and confirms nothing; an answer that does not parse, or does not hold each key of the batch exactly once, rejects with `unknown`, reported.
- Failures map as in A-03 (`network`, `signed-out`, `rejected`, a refusal of the function included, `unknown`; `invalid-row` is not used) and are reported as in A-03 (`rejected` and `unknown`), with the operation `merge`.
- A merged entry keeps its own `updatedAt`, capped at the server's `now()`; an inserted entry takes the server's `createdAt` (the merge time), a replaced one keeps its `createdAt`.

### Reuse by A-05 (offline write replay)

`private.write_client_library_entry` is the one rule for a client write that carries the time of its change, so A-05 can replay queued writes of a signed-in user with their own times through it: a new `security definer` wrapper with the same guards as the merge function (`auth.uid()` only, `search_path = ''`, the shape validated before any write, a bounded input, execute granted to `authenticated` only, pgTAP for each), never a column grant. The rule then holds in one place: the client time capped at the server's `now()`, a strictly later time wins, an equal one keeps the stored copy. It covers inserts and replacements only: a replayed removal carries no time against which a later change can win (no tombstone), which A-05 decides. Regular online writes keep the server time.

### Guest side

`removeUnchanged(entries)` replaces the `clear()` of the earlier sketch: one synchronous read, change and write that removes each stored entry equal field by field to one of `entries` (`isSameLibraryEntry`), timestamps included; it writes nothing when no stored entry matches, and deletes the stored key when no entry remains. An entry added or changed after the merge listed the store stays and is merged next time, so nothing this version can read leaves the device that the account did not receive or already held newer. The exception is the accepted L-02 rule: a stored entry this version cannot parse is dropped on every read, so the merge never sends it and the removal's write deletes it ("a damaged store loses what could not be read": it could not be merged either); the envelope-version rule (`ARCHITECTURE.md` §4 "Guest store") keeps a newer version from writing, under the same key, entries an older reader rejects. `clear()` remains, for the sign-out purge.

### When it runs

Each time a signed-in session starts in the app process (a launch with a stored session, a sign in, a switch to another user), and when the user taps Try again after a failure; the run reads the guest store and calls the account only when it holds entries. A token refresh keeps the user id and starts nothing. This covers FR-22's first sign-in, a later sign-in after guest use, and a retry on the next launch after a failure or a killed app. Owner: `SessionLibraryContextProvider`, which runs `mergeGuestLibrary` (`src/core/hooks/guest-merge.ts`) once per account instance and once per retry, and exposes the merge status (`idle`, `checking`, `merging`, `failed`) and the retry through `useGuestMerge()`. A run whose account instance is no longer the committed one is stale: it changes no state and removes nothing. Runs never overlap: a run starts once the previous run of the provider settled, since a stale run of the same user (signed out and in again) still passes the session guard, and its later batches could otherwise write back an entry deleted meanwhile.

### Pending writes flushed first

Switching away from the guest library retires its library writer, which flushes its pending coalesced writes (`+1`, BR-09). `LibraryContextProvider` reports each retired writer's flush to its `onRetired` prop (`RetiredLibrary { repository, flushed }`), and the merge waits for every flush reported so far, except the pending library's, which never settles, before it reads the guest store.

### What the user sees

- While the guest store is read: the library loading state (the pending library, from the first render of the account instance).
- While the entries are merged: the library and favorites tabs show a spinner and "Adding the titles saved on this device to your account…" instead of their content, the detail's library section a spinner labelled with that sentence, and the library is the pending library, so no library action can write while the merge runs (an Add computed on a stale view would otherwise overwrite a merged entry).
- After success: the account library.
- On failure: the library stays the pending library until a retry succeeds, so no library action can compute a write on an account library lacking a guest entry (an Add or a `+1` there would make the account copy newer, and the next merge would keep it and remove the guest copy, its progress and notes lost). The library and favorites tabs show an error state (`library.merge.failedTitle`, `library.merge.failed`) with Try again, and the detail's library section the failure with Try again, without Add or the favorite toggle. The guest store is kept, and the merge runs again on Try again, the next launch or the next sign in. Offline at launch with guest entries, this is what the library shows until a retry succeeds (an automatic retry on reconnect belongs to A-05).
- The texts are translated in English and French.

### Safety

- One account store instance per user id, with the session guard before every call; the database takes the user from the token only, never from the request body; the `user_id` of every answered row checked.
- The account library is given to the tree only once its merge succeeded: no library action reads or writes it before.
- A merge whose session ended (sign out, another user) never removes guest entries; the next session's merge handles them.
- Any failure, the app being killed included, leaves the guest store intact.
- Failures that are not a `LibraryRemoteError` (a guest store failure, an input `RangeError`) are reported with `{ source: 'guest-merge' }`, stale runs included; the account store reports its own.

## Resolution of the open question (owner, 2026-11-01)

The first design left merged rows with the server's merge time as `updated_at`, which broke BR-08 in two cases that B1 now fixes:

- Two devices: with guest data on two devices (for example a phone and a tablet used without an account), the first device to sign in wrote its entries at the merge time, so for a media in both stores the second device's entry lost even when its change was more recent: the newer progress was discarded.
- One device: a guest change made after a merge listed the store but before that entry's write landed lost at the next merge to the row stamped at the merge time. In the app this needs a sign out while a merge request is in flight and a change to that entry as a guest before it lands: the library is pending during a merge, and the retired guest writer is flushed before the store is read.

Faithful BR-08 needs the guest `updatedAt` on merged rows. The owner chose B1, constrained to the merge path: a client-supplied time is honored only by the guest merge, capped at the server's `now()`; regular writes keep the server time through the trigger, and a regular client update cannot set `updated_at`. The merged row now carries the time of the guest change itself, so in both cases the most recent change wins whatever the order of the merges (pgTAP `050`, the shared contract, the route test of a newer guest change replacing a merged copy).

## Consequences

- Maintainability: two migrations (`*_guest_merge_client_time.sql`: the timestamp trigger of `library_entries`, the private rule and the exposed function; `*_guest_merge_time_format.sql`: both functions replaced to require the RFC 3339 time form, after review), with the regenerated `database.types.ts`. The client merge is one call per batch: no key read, no rounds, no conditional writes (`GUEST_MERGE_MAX_ROUNDS`, `GUEST_MERGE_INSERT_BATCH_SIZE`, the `LibraryFailure` `unresolved` and `toLibraryRowValues` are gone; `LibraryOperation` gains `merge`). The rule exists in SQL (`private.write_client_library_entry`), in the domain (`guestMergeDecision`, the reference the fake uses) and in the PostgREST fake (`merge-function.ts`): the shared contract runs against the account store over the fake and against the in-memory fake, and pgTAP pins the real function, so a drift between them fails a suite. `GUEST_MERGE_BATCH_SIZE` and the function's `max_entries` must stay in step; each names the other in a comment. The guest store gains one method. `ARCHITECTURE.md` §4, §5, §8, §9 and §12 describe this design, and no longer say that the guest library stays untouched while a user is signed in: merged entries leave it.
- Data: each batch is atomic, and the merge is idempotent and safe to retry: a failure after some batches leaves them written and the guest store whole, and the next run keeps what was written (the same time, an equal one keeps). A replace that changes the progress logs one `progress_events` row (the `after update of progress` trigger), like any update, dated at the merge; inserts log none. The schema v1 comment "logging an insert or a guest merge would invent history" assumed a merge that never logs; a replace records a progress change the user made on the device. An inserted row's `created_at` is the merge time, so it can be later than its `updated_at` (a guest change made before the sign in); no rule or view orders by `createdAt`.
- Device clock skew (residual limits): a guest change is timed by the device clock. A clock ahead of the server is capped at the `now()` of the call that writes the entry: it can win over an account change made less than the skew after the guest change. A retry of such an entry, after a failed batch, caps it again at the retry's later `now()`: within the skew, it can then replace an account change made between the two calls. A clock behind makes a guest change lose to an account change made before it: that only penalizes that user's own data, since the merge reaches the caller's own rows only.
- Security: one exposed function, `security definer` because it writes a column no API role may write; the reasoning is the function's own scoping, since definer rights bypass RLS: the user is `auth.uid()` only, never an input (an element naming `user_id`, `id` or `created_at` is refused), every write and its conflict key hold `auth.uid()`, the input is bounded and validated before any write, the validation errors (`22023`, `42501`) carry fixed messages with no value, while a cast or constraint error (`22P02`, `22007`, `22008`, `23502`, `23514`) can quote the caller's own input back to the caller only, and the client keeps its code alone, `search_path = ''`, execute granted to `authenticated` only (pgTAP `010` fails on any other function an API role may execute, `050` covers cross-user, `anon`, no user and validation). The private rule is not exposed and is executable by its owner only. Every other write keeps the server time: `anon` and `authenticated` hold no privilege on `updated_at`, which pgTAP `030` and `060` assert, so a future grant of that column to `authenticated`, which would let every regular write set it, fails them. A user can backdate only their own rows (insert an entry with a past time, or delete one and merge it again), which only orders their own library and decides their own BR-08 conflicts. Trusted server roles (`service_role` in Edge Functions, `postgres`) can set any past time, capped, as they can already write any row. The client never sends a user id, checks the `user_id` of every answered row and stays behind the session guard, as in A-03: a row of another user (the residual window) is never confirmed, so the guest entries stay on the device. Entries are never logged or put in an error or a report tag. The merge depends on the session and the guest store only, never on a route or link parameter, so opening a link adds no write of its own (`CONTRIBUTING.md` §7).
- Performance: one call per 100 entries, each one transaction of per-entry inserts on the unique key. A first sign-in with a few hundred guest entries is a few calls, whatever the account holds. The library stays on the pending state while the merge runs, so the merge's duration is the user's wait: each call has the timeout, the session guard's read included, which `send` runs under the request's timer for every account store call (one session read per request, each page of `list()` included).
- Product: A-06's sign-out purge must not delete the guest library while a merge is pending or has failed; the status is exposed by `useGuestMerge()`. The E2E flow of the merge against a backend is deferred to R-01, with the sign-in flow.
- Future web app: the rule, the account merge and the hook stay in `src/core/`, platform-agnostic, and the database function serves any client of the API. A web guest store implements `removeUnchanged` over its own storage with the same single read, change and write (`localStorage` is synchronous).

## Update (2026-11-02)

Precisions from the A-04 review, and what A-05 (offline write queue and replay, ADR-0017) changes in the merge. The text above is kept as accepted; where it differs, this section applies.

- Idempotence, qualified. "The merge is idempotent and safe to retry ... the next run keeps what was written" ("Consequences", Data) holds in values, not in time: with a device clock ahead of the server, an entry was written at the first call's `now()`, and a retry caps it again at its own, later `now()`, so it is written again, with the same values and that later time (as "Device clock skew" and the `mergeGuestEntries` contract already state). The same qualification applies to the comment "a retry of a merge is a no-op" in `src/core/hooks/guest-merge.ts`, corrected in A-05: a retry reaches the same values, and writes again only the entries whose time was ahead of the server.
- Account side, the migrations. The account side uses two migrations: `supabase/migrations/20261101182502_guest_merge_client_time.sql` (the timestamp trigger of `library_entries`, `private.write_client_library_entry` and `public.merge_guest_library_entries`) and `supabase/migrations/20261101223143_guest_merge_time_format.sql` (both functions replaced to require the RFC 3339 time form).
- Account side, the private rule. `private.write_client_library_entry` itself requires `updated_at` to be a string of the RFC 3339 form, checked before any cast, then a finite time no earlier than the year 1 in UTC (`0001-01-01 00:00:00+00`), each failure raising `22023` with a fixed message. This is enforced by the rule, not only by its caller, so every caller inherits it.
- Reuse by A-05. The replay inherits the same requirements: every client time it sends goes through `private.write_client_library_entry` (RFC 3339 form before any cast, the year-1 lower bound), and the new `private.remove_client_library_entry` applies the same checks to the time of a removal. ADR-0017 records how the rule was reused: the `security definer` wrapper `public.replay_library_writes(expected_user_id uuid, writes jsonb)`, with the merge's guards plus an `expected_user_id` guard, writes each queued save through `private.write_client_library_entry` and each queued removal through `private.remove_client_library_entry`, which deletes the stored row only when it is strictly older than the removal's capped time (no tombstone). The owner's B1 rule now reads: a client-supplied time is honored only by the guest merge and by the replay of writes the server has not confirmed, capped at the server's `now()`; regular writes keep the server time. pgTAP `010-privileges` lists both functions as the only ones `authenticated` executes.
- Stale merge run. A run now gets an `AbortSignal`, aborted when its account is no longer the committed one, and passes it to `mergeGuestEntries(entries, { signal })`, which checks it before each batch: an aborted merge rejects with a `LibraryRemoteError` `signed-out` and sends no further batch (a batch already sent completes). A stale run of the same user no longer sends its later batches until it ends; the next run still waits for it to settle.
- Automatic retry. A failed merge is retried automatically when the device reconnects (TanStack `onlineManager` following `expo-network`, ADR-0017), besides Try again, the next launch and the next sign in. An offline launch with guest entries recovers without a tap.
- Accepted residual: a guest entry the account refuses on every attempt. Such an entry (`rejected`) is only reachable with a schema drift between `libraryEntrySchema` and the database, which the database-limits tests (`src/core/domain/database-limits.test.ts`) and pgTAP pin. It keeps the account library pending on that device after every retry, reconnect and launch. The way out is to sign out, then an app update fixing the drift. There is no automatic skip: skipping the entry would remove nothing from the device, but would show an account library lacking a guest entry, on which an Add or a `+1` would compute a write that the next merge keeps over the guest copy, which "What the user sees" forbids.

## Update (2026-11-04)

From the A-04 review, done in A-10. The text above and the Update of 2026-11-02 are kept as accepted; where they differ, this section applies.

- A failed removal after a successful merge no longer fails the run. When `mergeGuestEntries` succeeded and `removeUnchanged` then fails, the run ends as merged: the status is `idle` and the account library is shown. The failure is reported with `{ source: 'guest-merge' }`, holding no entry, key or user id. Before, that case showed the merge error, whose text (`library.merge.failed`) says the titles could not be added although they were, kept the library pending, and offered a Try again that only removed entries: that misleading state is gone.
- Why it is safe: the account then holds every listed entry or a newer copy. The guest store keeps those entries; the next session's merge (a launch with the stored session, or the next sign in) sends them again, where BR-08 keeps the account copy (an equal or older time keeps it), and then removes them from the device. A sign out while `idle` clears the guest store (ADR-0018, sign out step 4). An Add or a `+1` made meanwhile on the account library makes the account copy newer, which the next merge keeps: the guest copy it then removes was already merged, so nothing is lost, unlike the failure case of "What the user sees", where the account may lack a guest entry.
- Two qualifications, each within a residual already accepted:
  - an entry whose time was ahead of the server is written again by the next merge, capped at that call's later `now()` (the Update of 2026-11-02, "Idempotence, qualified"); within the clock skew it can then replace a change the user made to that entry meanwhile on this device ("Device clock skew"), which the pending library prevented before this Update;
  - an entry the user removed from the account library meanwhile is inserted again by the next merge (no tombstone, ADR-0017 "Database"); the user can remove it again.
- "What the user sees" and "Safety" are otherwise unchanged: a failure before the merge succeeded (the guest store read, the merge itself) still keeps the pending library and shows `library.merge.failed` with Try again.

### Precisions from the implementation

- The run (`GuestMergeRun`, `src/core/hooks/guest-merge.ts`) gains `onCleanupFailed(error)`. `mergeGuestLibrary` calls it with the error of a `removeUnchanged` that rejected after a successful merge, then resolves `merged`; it is never called after a failed guest store read or a failed merge, which still reject the run.
- `SessionLibraryContextProvider` passes an `onCleanupFailed` that reports the error with `{ source: 'guest-merge' }` and no tag, through the same reporter and source as the merge's other failures that are not a `LibraryRemoteError`. Nothing is shown: the status concludes `idle` and the account library is shown.
- `docs/ARCHITECTURE.md` §4 "Library switch" and §8 "Guest merge" record it.

## Update (2026-11-11)

From the security review (R-04, `docs/security-review.md`). The text above and the earlier Updates are kept as accepted; where they differ, this section applies.

### Error codes of a merge call

"Consequences", Security lists the cast and constraint codes a merge call can return as `22P02`, `22007`, `22008`, `23502`, `23514`. The list is an example, not exhaustive: probes also give `22009` (an offset out of range) and `22003` (an integer out of range), and the entry cap below adds `TZ001`. The claim stands: besides the fixed `22023` and `42501`, a cast or constraint error the input checks let through quotes only the caller's own input, back to the caller; `TZ001` carries a fixed message; the client keeps the code alone (`library-error-mapper.ts`). The same list applies to the replay (ADR-0017 Update of 2026-11-11).

### Input bounded by bytes

The 100-entry bound did not bound the size of a call: the column limits apply only after the whole payload is parsed and cast. Migration `supabase/migrations/20261111143207_library_input_byte_bounds.sql` replaces `public.merge_guest_library_entries` with the same signature, owner, security mode, `search_path` and grants, and one more check, right after the count and before any per-element check or cast: `octet_length(entries::text)` at most `max_input_bytes`, 100 × (28,049 + 2) = 2,805,100 bytes, else `22023` with the fixed message `entries are too large`. 28,049 bytes is one entry at its worst case in jsonb text (every column at the largest value the constraints accept, each code point at its largest escaped form, an enum label at 63 bytes; the table is in the migration), 2 bytes the array punctuation per element. jsonb text is canonical, so the bound does not depend on how the client formatted its body, and no valid batch of the client is refused (a maximal valid entry is 27,837 bytes). PostgREST has already parsed the body when the function runs: the bound limits the validation, the casts and the writes, not that parse. pgTAP `072-library-input-size`.

### Merge at the entry cap

`library_entries` holds at most 10,000 rows per user since migration `20261111143330_per_user_library_caps.sql` (`private.enforce_library_entry_cap`, `docs/ARCHITECTURE.md` §5 "Per-user caps"). The insert of a new key past the cap raises `TZ001`, also under `private.write_client_library_entry`, so:

- a merge batch holding a new key while the account holds 10,000 entries is refused whole (one transaction); the batches before it stay written; a batch of keys the account already holds still merges (pgTAP `090-library-entry-cap`);
- the account store maps the `TZ001` answer (PostgREST answers it with 400) to `LibraryRemoteError('library-full')`, not reported;
- the run fails; `SessionLibraryContextProvider` keeps the failure reason, and `useGuestMerge()` gives `{ status: 'failed', failure: 'library-full', retry }` (`GUEST_MERGE_FAILURES`: `library-full`, `other`; `guestMergeFailureOf`);
- the guest entries stay on the device, as for any failure ("Safety"); the user is told why, in English and French (`library.merge.full`, with the cap: the titles stay on this device; remove titles from the library on another device then try again, or sign out to use them here), on the library and favorites tabs and in the detail's library section;
- the library stays the pending library until a retry succeeds ("What the user sees"): every retry, reconnect, launch and sign in fails the same way while the account is full. The way out is to remove titles on another device, or to sign out: the merge being `failed`, the sign out keeps the guest library (ADR-0018), which shows again. A way out on the device itself is backlog item R-09.

### Cleanup failure reported as a fixed error

`GuestMergeRun.onCleanupFailed` takes no argument any more: `mergeGuestLibrary` calls `onCleanupFailed()` without the error of the failed `removeUnchanged`, since a storage error could quote stored content. `SessionLibraryContextProvider` reports a fixed `LibraryCleanupError('guest-merge-cleanup')` (`src/core/errors/library-report-errors.ts`, a fixed message, no cause) with `{ source: 'guest-merge' }`. This replaces "reports the error" of the Update of 2026-11-04 ("Precisions from the implementation"). The merge's other failures that are not a `LibraryRemoteError` are still reported with the caught error (a guest store failure or a `RangeError`, value-free by construction today; R-09).
