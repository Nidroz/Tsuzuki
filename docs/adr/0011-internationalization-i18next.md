# ADR-0011: Internationalization with i18next in the core

- Status: Accepted
- Date: 2026-09-30

## Context

F-06 adds English and French: device language detection through a platform adapter, English fallback, and a setting that overrides the device language (picker in F-07, persistence in F-09). Constraints:

- `src/core/` stays platform-agnostic and shareable with a future Next.js app (ADR-0006), so the translation engine, catalogs and language rules cannot depend on React Native or Expo.
- `src/ui/` never calls i18n: routes and features translate and pass labels as props, which keeps `ui` independent of `core` (`ARCHITECTURE.md` §2).
- A missing key must fail a test, and formatting must never depend on the machine locale, so tests are deterministic.
- TypeScript is strict: translation keys should be checked at compile time, not only at runtime.
- French plural rules differ from English (0 is singular, and `Intl.PluralRules('fr')` has a `many` category), so plural selection must follow CLDR, not a hand-written one/other rule.
- The device language list comes from the OS and is untrusted input (`CONTRIBUTING.md` §5: parsed with Zod at the boundary).
- A language switch must show the new language in the very render that receives it, without mutating shared state during render (a discarded concurrent render must leave nothing switched).

Options considered, engine:

- **i18next**: mature, MIT, no dependencies. Runs unchanged in React Native and Next.js, typed keys through `CustomTypeOptions`, plurals through `Intl.PluralRules`, fallback language, missing key handler, nested keys and interpolation built in.
- **Small custom engine on `Intl`**: no dependency, but plurals, interpolation, typed nested keys, fallback and missing key reporting would all be written and maintained here.
- **FormatJS / react-intl**: ICU message syntax and strong formatting, but heavier, more verbose catalogs, and typed keys need extra tooling.

Options considered, React binding:

- **react-i18next**: the usual binding, with `Trans` for rich text (inline links or emphasis inside a translation). Adds three transitive packages (`html-parse-stringify`, `use-sync-external-store`, `@babel/runtime`). Its `useTranslation` caches `t` per language and store revision, not per instance, so with one instance per language (below) it would keep a stale `t` and a stale missing key handler.
- **Own React context in `src/core/i18n/`**: a few lines (provider, context, hook), `t` taken from each new instance. No `Trans`.

## Decision

- **Library**: `i18next` 26, no React binding library. i18next is imported only inside `src/core/i18n/`; lint bans `i18next` and `react-i18next` everywhere else, so the engine can be replaced by rewriting that folder and the binding cannot be added outside it.
- **Module** `src/core/i18n/` (no React Native, no Expo). Public API in `index.ts`, imported as `@core/i18n/index` (like `@ui/index`); `createI18n`, `resources` and the device tag Zod schema are internal, and their tests import their modules directly. Lint enforces the barrel (`i18nInternals` in `tools/eslint/layers.mjs`, built like `uiInternals`) in routes and features, production and test code, and in `src/platform/`, type imports included: any other `@core/i18n/...` specifier (`@core/i18n` alone included) and any relative path into `src/core/i18n/` (the barrel included) is rejected, in static imports, re-exports, `import()` and jest module calls. `src/platform/` imports the barrel as types only. The rest of `src/core/` and `test/` are not restricted. The library ban and the barrel rule both cite this ADR in their lint messages.
  - `en.json`, `fr.json`: a single `translation` namespace, keys nested by feature. `en.json` is the source of the key set.
  - `languages.ts`: supported languages `en` and `fr`, fallback `en`, preference `system | en | fr`, default `system`.
  - `device-language-tags.ts`: Zod schema for the device tags; a non-array gives an empty list, invalid entries are dropped.
  - `resolve-language.ts`: pure `resolveLanguage(preference, deviceTags: unknown)`. An explicit preference wins; `system` takes the first device tag whose primary subtag is supported; otherwise `en`.
  - `locale-adapter.ts`: `LocaleAdapter { useDeviceLanguageTags(): readonly string[] }`. It is a hook so the tags follow OS language changes: `expo-localization` exposes change notifications only through its reactive `useLocales()` hook (its listener is internal). A web app implements it with `navigator.languages` and the `languagechange` event.
  - `create-i18n.ts`: creates a new i18next instance per call, with no global singleton; synchronous init with the bundled resources, fallback `en`. An optional `onMissingKey` callback receives each key found in no catalog of the chain (active language, then `en`); a key present only in `en.json` resolves through the fallback and is not reported.
  - `format.ts`: `formatNumber` and `formatDate` take a required language; they never use the machine locale.
  - `I18nProvider.tsx`, `i18n-context.ts`, `use-translation.ts`: the module's own React context. The provider creates, with `useMemo`, one never-mutated instance per `[language, onMissingKey]` and takes `t` from `instance.getFixedT(language, 'translation')`, so the render that receives a new language already translates with it: no stale frame (a `changeLanguage` in an effect) and no shared state mutated during render (a `changeLanguage` in render). `onMissingKey` must be stable (module level or memoized): a new function creates a new instance. `useTranslation()` returns `{ t, language, formatNumber, formatDate }`, the formatters bound to the active language; the value keeps its identity until the instance changes, and the hook throws outside `I18nProvider`.
  - `i18next.d.ts`: keys typed from `en.json` with `strictKeyChecks`, so an unknown key fails typecheck.
- **Platform**: `src/platform/locale.ts` implements `LocaleAdapter` with `expo-localization`, which works in Expo Go with no config plugin for detection. The config plugin that lists the app languages in the OS per-app language setting is deferred to F-10.
- **Composition root**: `app/_layout.tsx` holds the language preference (default `system`) like the theme preference, until the settings picker (F-07) and persistence (F-09). It resolves the language from the device tags and wraps the tree in `I18nProvider`. In development it warns on missing keys, and warns once if `Intl.PluralRules` is unavailable: i18next would otherwise fall back silently to a one/other rule, wrong for French 0. Hermes support is to be checked on a device.
- **Screens**: routes and features translate with `useTranslation` from `@core/i18n/index` and pass strings, or label functions such as `PaginationLabels.page(n)`, to `src/ui/` primitives. The i18n hook lives with its module in `src/core/i18n/`; `src/core/hooks/` stays for data hooks over the repository and `CatalogProvider` interfaces.
- **No hard-coded text** in production files of `app/` and `src/features/`, enforced by lint (`TEXT_GUARDS` in `tools/eslint/text-guards.mjs`; their test code, `*.test.ts(x)`, `__tests__/` and `__fixtures__/`, gets a separate layer entry with the same import bans and style guards, without the text guards). Text is a string or template literal containing a letter of any script (`\p{L}`). It is rejected as JSX text or a string literal child; in text props (`label`, `title`, `placeholder`, `message`, `description`, `text`, `hint`, `error`, `aria-label`, `aria-valuetext`, and names ending in `Label`, `Hint`, `Title`, `Text`, `Message`, `Placeholder`, `Description`) and the same keys of objects held by a prop, given or spread (`action={{ label }}`, `accessibilityActions={[{ label }]}`); as any value of a `labels` / `*Labels` object, label functions with an expression body included; in the navigation keys `title`, `headerTitle`, `headerBackTitle`, `tabBarLabel`, `tabBarAccessibilityLabel`, `drawerLabel` anywhere in the file, even as another call's data (`track({ title: 'opened' })`); and in `Alert.alert` / `Alert.prompt` arguments and the text keys of their objects (button `text`). It is found directly or through at most 3 nested wrappers (`MAX_NESTING`): `?:` branches, `&&`, `||`, `??`, `+`, templates, array elements (children `{['Hi', t('a')]}`, array-valued props), `as` / `satisfies` and arrow bodies. An object key is matched from the nearest prop or alert call through at most 6 intermediate nodes (`MAX_OBJECT_PATH`) of objects, arrays, spreads, conditionals, logical operands and type assertions; a function or a call ends the path, so a text key inside a callback or a call argument (`onPress={() => track({ label: 'save_button' })}`, `action={makeAction({ label: 'retry_action' })}`) is that code's data and is not reported. Beyond a syntax check: a string stored in a variable first, a label function with a block body, a key computed at run time, a literal behind more than 3 wrappers, an object key more than 6 nodes deep. Cases: `tools/eslint/layers-text-cases.mjs` with the probes of `tools/eslint/layers-text-probes.mjs`; the library ban in `tools/eslint/layers-i18n-cases.mjs`, the barrel rule in `tools/eslint/layers-i18n-barrel-cases.mjs`.
- **Missing key safety net**, three checks, each covering a case the others miss:
  - parity test: the checker `test/core/i18n-catalog-parity.ts`, applied to the real catalogs by `src/core/i18n/catalogs.test.ts`, requires `fr.json` to have exactly the keys of `en.json`, the same `{{placeholders}}`, and every plural category of `Intl.PluralRules(language)` (French: `_one`, `_many`, `_other`). It is the only check for a key in `en.json` but not in `fr.json`, which resolves through the fallback;
  - typecheck: typed keys reject a key absent from `en.json`;
  - runtime: `onMissingKey` reports a key found in no catalog (a key built at run time or cast). Component and route tests render inside the test helper `test/mobile/render-with-providers.tsx`: `I18nProvider` with the real catalogs, English by default, and an `onMissingKey` that fails the test through the console check of ADR-0010. The composition root turns it into a development warning, and an unexpected `console.warn` fails a test rendering the root layout.
- **Tests**: the i18n provider and hook are the first core hook, so the core hook test setup of ADR-0010 (`@testing-library/react` in jsdom) arrives in F-06 as a Jest project `core-dom`: core `.tsx` tests run in jsdom with browser export conditions, with the fixed clock, the console check and network globals that throw; core `.ts` tests stay in the Node project `core`, whose `msw/node` server does not load under jsdom (`ARCHITECTURE.md` §12).
- **Zod** is added as a dependency in F-06: the device language tags are the first external input parsed at a boundary.

## Consequences

- Maintainability: plurals, interpolation, fallback and typed keys come from a maintained library; our code is the language rules, the provider, the context and the formatters. The binding is a provider and a hook over `getFixedT`, tested with the module. The engine is confined to one folder behind `useTranslation`, so replacing it touches `src/core/i18n/` only. Adding a language means a new catalog, an entry in `languages.ts` and plural keys that the parity test checks.
- Rich text: there is no `Trans`. A translation with inline markup, if ever needed, gets a small component in `src/core/i18n/` or a binding library then (new ADR).
- Security: the device tags are parsed with Zod before use. Translations are rendered as text, never as markup. Runtime dependencies added: `i18next` (no dependencies) and `zod` (no dependencies), both MIT, and `expo-localization` (Expo SDK 57, one transitive package, `rtl-detect`). Dropping react-i18next avoids its three transitive packages.
- Performance: catalogs are bundled and initialized synchronously, so the first render is already translated, with no loading state and no network. A language switch creates a new instance, cheap with in-memory catalogs, and re-renders every consumer once. The catalogs are small; splitting them by namespace can come later if they grow.
- Determinism: one instance per provider and language means no shared state between tests (test order is randomized), and formatters with a required language make output independent of the machine locale.
- Web app: `src/core/i18n/` moves to `packages/core` unchanged, binding included; the web app provides its own `LocaleAdapter` and can create one instance per request on the server, which a global singleton would not allow.
- Plural correctness depends on `Intl.PluralRules` in the JavaScript engine; the development warning makes a missing implementation visible instead of silently wrong.
- A text lint rule based on syntax cannot catch every hard-coded string; review covers strings built in variables, label functions with a block body, keys computed at run time, and literals beyond the selector bounds (more than 3 wrappers, object keys more than 6 nodes deep). The bounds keep the selectors finite. The opposite trade-off: a navigation key is reported wherever it is written, even in another call's data such as an analytics event.
- The i18n barrel rule reads the specifier text: a folder literally named `core/i18n` under `app/` or a feature, imported relatively, is a known false positive, as for `uiInternals`.
