# Security review (MASVS L1)

Backlog item R-04, 2026-11-11. The baseline is OWASP MASVS L1 (`SPEC.md`, `CONTRIBUTING.md` §7). This review goes through the MASVS v2 controls one by one for the app, its Supabase project (migrations, RLS, the `delete-account` Edge Function) and the CI. `docs/ARCHITECTURE.md` §9 holds the threat model this checklist points to; the follow-ups are backlog item R-09.

The L1 profile covers the STORAGE, CRYPTO, AUTH, NETWORK, PLATFORM and CODE controls; RESILIENCE belongs to the R profile and PRIVACY to the P profile. The privacy controls are reviewed anyway, since `SPEC.md` requires GDPR compliance.

Statuses: **Met**; **Accepted** (not met, with the reason recorded); **Not applicable** (the app does not use what the control is about, or the control is outside the L1 profile); **Open** (with its backlog item).

## Residuals accepted

Recorded in `docs/ARCHITECTURE.md` §9 with their mitigations; those decided by R-04:

- An offline launch whose stored session has an expired access token reads as signed out (auth-js reports no session until a refresh answers), so a marked user is purged although the session may come back. Only a user whose sign out started, having confirmed any unsynced discard, is marked: purging them matches what they asked and loses nothing unsynced; the session coming back only refetches. The auth repository is not changed to tell such a session apart.
- Gone purge coverage: a session whose access token expired while the app was closed or in the background ends without a purge. Once the token expired, no server answer tells a deleted account from a revoked session, so a launch check cannot help; an Edge Function keeping the ids of deleted users would conflict with erasure.
- The `session_not_found` race: auth-js removes whatever session is stored when `getUser(jwt)` answers `session_not_found`, so an account switch between the check's session read and that answer could end the new session. Narrow, and nothing is lost (that session's queue is kept); a second auth client for that check alone would add an auth surface for a rare case.
- The Sentry notes scrubber's limits: an `=` value stops at a raw `&`; an unquoted value stops at its line end; a note holding its own quote followed by white space, `,`, `;`, `}`, `]`, `)` or `&` ends early; percent-encoded keys are not found; over-scrubs (a key such as `footnote`, an unclosed quote redacted to the end of the text).
- A guest merge refused at the entry cap keeps the guest entries on the device and the library pending until a retry succeeds (a way out on the device is R-09).
- The ADR-0020 residuals, once wired (a persistent secure store failure on Android, a false `key-mismatch` after a kill, the plaintext file kept one more launch).

Earlier residuals stay as recorded: deletion without re-authentication (ADR-0018), backdating one's own rows (ADR-0016), device clock skew (ADR-0016, ADR-0017), the catalog provider's IP logging (ADR-0013), native crash events outside `beforeSend` (§9).
