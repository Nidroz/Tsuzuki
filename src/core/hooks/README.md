# src/core/hooks

React hooks over the repository and `CatalogProvider` interfaces, consumed by feature screens: TanStack Query hooks (the paged catalog lists `useSearch`, `useTopMedia` and `useCurrentSeason` over `usePagedCatalogList`, `useMediaDetail`, `useGenres`, the library entry `useLibraryEntry` and its actions `useLibraryEntryActions`, the library list `useLibraryList`, the auth actions of `use-auth-mutations.ts`), the session `useAuthSession` and the hooks of local data (`useRecentSearches`).
Each injected dependency reaches them through its own React context, given by the composition root: `CatalogContextProvider` (`useCatalogProvider`), `RecentSearchesContextProvider` (`useRecentSearches`), `LibraryContextProvider` (`useLibraryContext`, read by the library hooks; its repository chosen from the session by `SessionLibraryContextProvider`, which also gives `useGuestMerge`) and `AuthContextProvider` (`useAuthContext`, read by the auth hooks, and `useAuthSession`); each hook throws outside its provider.
They depend only on interfaces, never on Supabase or a catalog provider directly. Hooks are imported by file (`@core/hooks/use-search`): there is no barrel.
`src/core/` never imports React Native, Expo modules or NativeWind.

## Library writes

`LibraryContextProvider({ repository, onRetired?, subscribeToForeground?, children })`, inside the query client provider, gives the hooks `{ repository, writer, scope }`: the active `LibraryRepository`, a `LibraryWriter` over it (`library-writer.ts`, plain TypeScript over the `QueryClient`) and their cache scope, a `LibraryScope` (`src/core/query/keys.ts`) taken from a module counter, one per writer, built together in one `useMemo` per (query client, repository). Every library query key holds the scope (`['library', scope]` for the list, `['library', scope, namespace, kind, externalId]` for an entry), so a new repository moves every hook to keys of the new library in the same render, which have no data yet: the previous library never shows, not even for one frame. When the repository or the query client changes, and on unmount, the effect cleanup calls the old writer's `flushAll()`, so the pending coalesced writes go to the repository they were made for, and removes the old scope's queries once the commit is over and again once the flush settled (a flushed write that succeeded set its entry again). The removal checks that the value is no longer current (a ref set by the effect setup, cleared by the cleanup, read in a microtask): the extra cleanup StrictMode runs on the live value at mount flushes and reports it, but never removes the live scope (ADR-0017). An apply still waiting for its query cancel at that moment finds its entry removed and rejects as not loaded; its error is not shown on the next library. Each retired value is reported to `onRetired({ repository, flushed })`, in the commit that retires it: its repository and the promise of that `flushAll()` (never rejects). `onRetired` is read through a ref set during the commit, not an effect dependency, so a new function never retires the live value. With `subscribeToForeground` (the core `ForegroundSubscription` of `foreground.ts`; `src/platform/app-state.ts` on mobile, passed by the composition root), going to the background calls the live writer's `flushAll()`: the coalesced `+1` writes leave at once, those of the account library reaching its write-ahead queue, so a killed app loses none of them.

`SessionLibraryContextProvider({ guest, accountRepositoryFor, reporter, subscribeToForeground?, children })` (A-03, A-04, A-05), inside `AuthContextProvider`, renders `LibraryContextProvider` with the repository of the session (`useAuthSession`): the `GuestLibraryRepository` `guest` signed out, the `OfflineAccountLibraryRepository` `accountRepositoryFor(userId)` signed in (`createOfflineAccountLibraries`, ADR-0017) (memoized on the user id: a token refresh keeps the instance, another user or a new sign in gets a new one), and `PENDING_LIBRARY_REPOSITORY` while the session loads, whose calls never settle, so the library screens show their loading state instead of the wrong library. Screens use the hooks only and never know which repository is active.

### Guest merge

Each account instance gets the guest library merged into it as it becomes the session's (BR-08, FR-22, ADR-0016): at a launch with a stored session, a sign in, a switch to another user, and again on `retry()` after a failure; a token refresh keeps the instance and starts nothing. Until the merge of the current instance succeeded, the library is `PENDING_LIBRARY_REPOSITORY`, after a failure too: the merge phase is derived from the instance, so its very first render is already `checking`, the account library never shows before the merge, and no write reaches it meanwhile. No library action can then compute a write on an account library lacking a guest entry (an Add or a `+1` there would write an account copy newer than the guest one, which the next merge keeps before removing the guest copy).

- `mergeGuestLibrary({ guest, account, settleWrites, isCurrent, signal, onMerging, onCleanupFailed })` (`guest-merge.ts`, plain TypeScript) runs once: it waits for `settleWrites()`, lists the guest store (`empty`: nothing sent), calls `onMerging()`, `account.mergeGuestEntries(entries)`, then `guest.removeUnchanged(entries)` with exactly the listed entries (`merged`). It checks `isCurrent()` after each wait and returns `stale` without a further call once the session changed: a stale run never removes a guest entry. A rejection of a step up to the merge rejects the run, and nothing is removed after a failed merge. A rejected `removeUnchanged` still ends the run `merged` and goes to `onCleanupFailed(error)` (A-10): the account holds every listed entry or a newer copy, and the next merge sends the entries left on the device again (kept, BR-08) and removes them.
- The provider passes `settleWrites`: the previous run of the provider, settled whatever its outcome, so two runs never overlap (a stale run of the same user signed in again still passes the account store's session guard), and every flush reported by `onRetired` and not settled yet (the guest writer retired in the commit that starts the run included, as the run starts in an effect, after the child cleanups), except the pending library's, which never settles. `isCurrent` compares the run's account instance with the session's, set during the commit, and is false once unmounted.
- Each run gets an `AbortSignal`, passed through `mergeGuestLibrary` to `account.mergeGuestEntries(entries, { signal })`, and aborted once its account is no longer the committed one (checked in a microtask after the commit, so a cleanup of the committed account never aborts it): a stale run sends no further batch. A failed merge is retried automatically when the device reconnects (TanStack's `onlineManager`), as by `retry()`. Merging the same entries again keeps their values (BR-08): each is kept, or, its time ahead of the server, written again with the same values at its later capped time (ADR-0016 Update).
- `useGuestMerge()` (`use-guest-merge.ts`, `GuestMergeContext` in `guest-merge-context.ts`) gives `{ status, retry }`, `status` one of `GUEST_MERGE_STATUSES`: `checking` (the guest store read), `merging` (its entries sent), `failed` (the guest store kept, the library still pending: the screens show the failure with Try again instead of the library), `idle` otherwise (signed out, the session loading, or the merge concluded). `retry()` starts a new run from `failed` only; in any other status, a retry tap is ignored. It throws outside the provider.
- A failed current run sets `failed`; a stale run changes no state. A failure that is not a `LibraryRemoteError` (the account store reports those itself) goes to `reporter.captureError(error, { source: 'guest-merge' })`, a stale run's too; no entry, key or user id is ever put in a report. A failed removal of the merged guest entries is not a failed run: the merge is done (`idle`, the account library shown) and the error goes to the same report, never shown.

### Replay of the account library

`LibraryReplayDriver` (`LibraryReplayDriver.tsx`, ADR-0017 D10), rendered by `SessionLibraryContextProvider` inside its `LibraryContextProvider`, replays the queued writes of the account instance whose merge is done, only while it is the live library of that provider: never before the merge, never for a retired instance. A run (`replayQueuedWrites({ signal })`) starts when the instance becomes live, on reconnect (`onlineManager`), on a return to the foreground, and when the instance notifies a write left in the queue (`subscribeToQueuedWrites`); the triggers of one synchronous step start one run, and the account library joins a run in flight itself. After a run with `confirmed > 0` (kept writes included), the live scope `['library', scope]` is invalidated, non-exact, so the list and the entries refetch the server state. The run's `AbortController` is aborted when the instance stops being live (sign out, another user, unmount). A run never throws into React: one that rejects goes to `reporter.captureError(error, { source: 'library-replay' })`.

- `useLibraryEntry(key, { media })`: the entry query (`queryKeys.library.entry(scope, key)`, `STALE_TIMES.library`), read through the writer. With the catalog's `media`, the entry is shown with the fresh snapshot (`withMediaSnapshot`): display only, viewing writes nothing. The snapshot is built in `select` whether the media is in the library or not, so a `media` no snapshot can hold fails the query with a `LibrarySnapshotError` in both cases (the detail shows its unsupported message, without Add or the heart).
- `useLibraryEntryActions(key, { media })`: `add`, `remove`, `setStatus`, `setProgress`, `incrementProgress`, `setScore`, `setNotes` (blank text clears the notes) apply the domain rules (BR-01 to BR-04, BR-07, BR-09) and, with `media`, first refresh the snapshot (`refreshMediaSnapshot`): the snapshot is written with a user action only. Fire and forget; `error` holds the last failure, tied to the key values and the scope it belongs to (a recycled list row never shows another entry's error, a failure of the previous library never shows on the next one), until the next action or `dismissError`.
- `useLibraryList(options, { showAdult, layoutKey, favoritesOnly? }): { query, view }`: the `['library', scope]` list query, read through the writer (`list()`: optimistic entries shown, entry queries seeded), filtered, sorted and grouped in `select` (`buildLibraryView`, plus every entry by `libraryEntryId`), covers re-checked against the provider's `imageHosts`; an option or adult setting change never refetches. `view` keeps the layout last shown (`keepLibraryLayout`) while `layoutKey`, the options, the setting and the scope stay the same: a changed row stays in its group and position with its new values, a removed one disappears, a new one goes to the top of its group. A new `layoutKey` (the screen gaining focus), option or library (a new scope) lays the library out again.
- `createLibraryWriter({ queryClient, repository, scope, now? })` builds every key it reads, sets, cancels or invalidates with its `scope`; its per-key state is keyed by the scope-free `mediaKeyId(key)`. The writer applies each change optimistically (after cancelling the entry's fetch in flight), skips no-op changes (BR-09), debounces `+1` taps for `PROGRESS_WRITE_COALESCE_MS` into one write of the latest entry, and runs the repository calls of one key one after the other. A read first writes the pending change of its key, so a refetch never returns an older state. Each change also updates the cached list data (`library-list-data.ts`). A success shows the stored entry in the entry and list data (unless a newer change came) and invalidates the `['library', scope]` list query only (`exact`); a failure rejects the action and refetches the entry. The newer changes of that key, computed from the failed change's optimistic entry, fail with it, never sent: a write started before the failure settled and still chained behind it rejects its applies with the same error (each failed write is recorded on the key state, and a write compares it with the one it started after, A-10), and the pending coalesced change is dropped, its timer cleared; a write started after the failure is sent. The key states and their serial chain live in `library-writer-state.ts` (`createKeyStates`). `createInspectableLibraryWriter(options)` returns `{ writer, activeKeyCount }`, for the writer tests only: `activeKeyCount()` counts the key states the writer keeps, 0 once every call settled; `createLibraryWriter` returns the writer alone, and `LibraryWriter` has no test-only method.

### Stuck writes

`useLibrarySyncIssues()` (`use-library-sync-issues.ts`, ADR-0017 "Stuck writes", A-10) gives `{ stuckCount, retrying, retry, discard }` for the notice of the library and favorites tabs (`LibrarySyncNotice`, `src/features/library/`). It is active only while the live library of the nearest `LibraryContextProvider` is the session's account instance (`useSessionLibrary().account`), which it is once its guest merge is done; signed out, while the session loads or while the merge has not succeeded, `stuckCount` is 0 and the actions do nothing, and the account instance is never read. `stuckCount` is `stuckWriteCount()` read with `useSyncExternalStore` over `subscribeToSyncState`. `retry()` calls `retryStuckWrites()`, one retry per instance at a time (a tap while it runs is ignored), `retrying` true until it settled; after a run with `confirmed > 0` the live scope `['library', scope]` is invalidated, non-exact, as the replay driver does. `discard()`, called once the user confirmed, calls `discardStuckWrites()`, invalidates the live scope when it removed writes, so the views show the server state, and returns how many it removed. Neither throws into React: a retry that rejects, or a discard whose storage failed (it then returns 0), goes to the reporter of `DevicePurgeContextProvider` with `{ source: 'library-sync-issues' }` (`LIBRARY_SYNC_ISSUES_REPORT_SOURCE`), never with a write, a key or a user id. It throws outside `SessionLibraryContextProvider`, `LibraryContextProvider`, `DevicePurgeContextProvider` or the query client provider.

## Auth

`AuthContextProvider({ repository, captcha, children })`, inside the query client provider, gives the hooks the `AuthRepository`, the `CaptchaTokenProvider` (`noCaptcha` until A-08) and the session state, subscribed with `onAuthStateChange` in an effect.

- `useAuthSession()`: `{ status: 'loading' | 'signed-out' | 'signed-in', session }`, `loading` until the repository first reports the session, the same object while the user id stays the same (a token refresh re-renders nothing). The session holds the user id only.
- `use-auth-mutations.ts`: one `useMutation` per action (`useSignUp`, `useResendConfirmation`, `useSignIn`, `useRequestPasswordReset`, `useCompleteEmailLink`, `useCompletePasswordReset`, `useSignInWithProvider`), with `networkMode: 'always'` and `gcTime: 0`: the variables hold passwords, so a mutation never pauses offline and is dropped once unobserved. The four protected calls ask the captcha provider for a token first and pass `{ captchaToken }` only when there is one. `useCompletePasswordReset` exchanges the link code once, then sets the password; a retry after a failed update sets the password only; its `failedStep` (`exchange` or `update`, null without an error) tells which step failed, so a screen treats any failed exchange as a spent link. `useSignInWithProvider` takes an `OAuthProvider` and resolves the session, or null when the user closed the browser or declined consent; it asks no captcha (ADR-0015). Rejections are `AuthError`s.
- `useOAuthProviders()`: the providers this build can sign in with (`AuthRepository.oauthProviders`), in display order; empty until A-09.

## Sign out, account deletion and device purge

Both end the session on the device and purge its user data (FR-24, FR-25, ADR-0018); a user the auth server reports gone, and a purge that did not complete, are purged by `DevicePurgeDriver` (ADR-0018, update of 2026-11-04). They read the session's libraries and the device purge wiring, so they run inside every provider of the composition root.

- `session-library-context.ts`: `useSessionLibrary()` gives `{ account, userId, guest, accountRepositoryFor }` from `SessionLibraryContextProvider`: the `OfflineAccountLibraryRepository` of the user signed in whatever the merge phase (null signed out or while the session loads) and its user id (null exactly when `account` is), the `GuestLibraryRepository`, and the factory the provider was given, a new instance of a user id per call. It throws outside the provider. `PENDING_LIBRARY_REPOSITORY` lives in `pending-library.ts`, re-exported by the provider.
- `use-latest.ts`: `useLatest(value)`, a ref holding `value` as of the last commit, read by an async callback after an await to act on the latest value, never on the one of the render that started it.
- `device-purge.ts` (plain TypeScript): `purgeDeviceUserData(input)` deletes a user's data in order: the account copy and queue of `input.account`'s user (`purgeDeviceData`), then, with `deviceWide` only, the guest library unless kept, the recent searches, every query of the cache (mutations untouched), the persisted cache document, and last advances the purge generation. Each step is independent: a failure is reported as a `DevicePurgeError` of its step (fixed message, no cause) and the next steps still run; it never rejects and resolves the steps that failed, in order. `keepsGuestLibrary(status)`: the guest library is kept while the merge is `checking`, `merging` or `failed`, cleared once `idle` (BR-08).
- `device-purge-markers.ts`: `guardDevicePurgeMarkers(repository, reporter)` wraps the `DevicePurgeMarkerRepository` (`device-purge-pending` in the app storage) so that a failing `list`, `add` or `remove` is reported (`{ source: 'device-purge-marker', tags: { operation } }`, fixed message, no cause, no user id) and never thrown (`list` then reads no marker); `settle(userId, failed)` removes the marker when the `account-library` step succeeded, else rewrites it with `clearGuestLibrary` and `deviceWide` false, so the next launch retries that step only.
- `device-purge-context.ts`: `DevicePurgeContext` and its `DevicePurgeValue` `{ removePersistedCache, reporter, markers, generation, advanceGeneration }`; `useLibrarySyncIssues` reports its failures to the same reporter.
- `DevicePurgeContextProvider({ removePersistedCache, reporter, markers, children })`, inside the query client provider, `AuthContextProvider`, `RecentSearchesContextProvider` and `SessionLibraryContextProvider`: gives the persisted cache removal (the persister's `removeClient`), the reporter, the guarded markers and the purge generation, starting at 0, and renders `DevicePurgeDriver`.
- `use-device-purge.ts`: `useDevicePurge()` binds `purgeDeviceUserData` to the query client, the recent searches, the session's guest library and the provider, and takes `{ account, clearGuestLibrary, deviceWide }` (`account` any object with `purgeDeviceData`); `usePurgeGeneration()`, the number of device-wide purges so far: a screen keyed with it (the search route) remounts with its state gone; `useDevicePurgeContext()`. Each throws outside its providers.
- `DevicePurgeDriver.tsx` (renders nothing), ready once the session is known and the persisted query cache restored (`useIsRestoring()`), so no purge runs before a restore that would put purged queries back. Launch: once ready, once per mount (one per app process in the composition root), each marker is read: the session's user is unmarked (that sign out did not complete, the data stays); every other marked user is purged with the recorded `clearGuestLibrary` and `deviceWide`. After the launch, a marked user who becomes the session's user is unmarked (signed in again: their sign out did not stand), unless their purge is queued or running; a launch purge then checks the session as it starts and as it settles, and unmarks instead of purging or rewriting while that user is signed in. A launch without a session cannot tell a signed out user from a stored session not confirmed yet (an expired token refreshed offline: auth-js reports no session and keeps it stored): it purges. Gone: from the moment it is ready, `AuthRepository.onUserGone` is subscribed; a user X reported is marked (`clearGuestLibrary` by the guest library rule when X is the session's user, else false; `deviceWide` true), signed out when X is the session's user (a rejection is reported as `{ source: 'device-purge-driver', tags: { step: 'sign-out', reason } }`, except the `unknown` the repository reports itself, and the purge goes on), then purged. Each purge takes X's documents through a new instance from `accountRepositoryFor(X)` (created inside the `account-library` step), runs the device-wide steps only when no other user is signed in at that moment, then settles X's marker. Purges run one after the other; a user reported again while their purge is queued or running gets no second one, a repeat after it purges X's documents again (none left). A session that ends without a report (a refused refresh of a revoked session, an expired token, offline) purges nothing: the queue waits for that user's next sign in (ADR-0017). Every per-user step takes X's id only; no report holds a user id.
- `sign-out-failure.ts`: `reportSignOutFailure(reporter, source, error)`, the report of a local sign out that rejected after a deletion or a gone report, shared by `useDeleteAccount` and the driver.
- `use-sign-out.ts`: `useSignOut()`, a mutation taking `{ discardUnsynced? }` and resolving `{ status: 'signed-out' }` or `{ status: 'unsynced', count }`. With an account instance: the live writer is flushed and the queued writes replayed within `SIGN_OUT_SYNC_TIMEOUT_MS` (10 s), a failed step reported as a `SignOutSyncError`; writes still queued or held, without `discardUnsynced`, resolve `unsynced` and nothing else is done; otherwise whether the guest library is kept is read, the user's marker is written (`deviceWide` true), then `signOut()` (a rejection removes the marker and rejects, nothing purged), then the purge, the queue included, and the marker is settled.
- `use-delete-account.ts`: `useDeleteAccount()`, a mutation without variables: no account instance rejects `session-expired`, the device offline rejects `offline`, nothing sent; then `deleteAccount()` (a rejection rejects, nothing purged, still signed in), the purge with the queued writes (no marker before it: the purge comes before the local sign out; after it, the marker settled from the failed steps, so a failed `account-library` step leaves the user marked with both flags false for the next launch), then the local `signOut()`, whose rejection is reported (an `AuthError` `unknown` by the auth repository only), not shown, and the mutation still resolves.
