# src/core/hooks

React hooks over the repository and `CatalogProvider` interfaces, consumed by feature screens: TanStack Query hooks (the paged catalog lists `useSearch`, `useTopMedia` and `useCurrentSeason` over `usePagedCatalogList`, `useMediaDetail`, `useGenres`, the library entry `useLibraryEntry` and its actions `useLibraryEntryActions`, the library list `useLibraryList`, the auth actions of `use-auth-mutations.ts`), the session `useAuthSession` and the hooks of local data (`useRecentSearches`).
Each injected dependency reaches them through its own React context, given by the composition root: `CatalogContextProvider` (`useCatalogProvider`), `RecentSearchesContextProvider` (`useRecentSearches`), `LibraryContextProvider` (`useLibraryContext`, read by the library hooks; its repository chosen from the session by `SessionLibraryContextProvider`, which also gives `useGuestMerge`) and `AuthContextProvider` (`useAuthContext`, read by the auth hooks, and `useAuthSession`); each hook throws outside its provider.
They depend only on interfaces, never on Supabase or a catalog provider directly. Hooks are imported by file (`@core/hooks/use-search`): there is no barrel.
`src/core/` never imports React Native, Expo modules or NativeWind.

## Library writes

`LibraryContextProvider({ repository, onRetired?, children })`, inside the query client provider, gives the hooks `{ repository, writer, scope }`: the active `LibraryRepository`, a `LibraryWriter` over it (`library-writer.ts`, plain TypeScript over the `QueryClient`) and their cache scope, a `LibraryScope` (`src/core/query/keys.ts`) taken from a module counter, one per writer, built together in one `useMemo` per (query client, repository). Every library query key holds the scope (`['library', scope]` for the list, `['library', scope, namespace, kind, externalId]` for an entry), so a new repository moves every hook to keys of the new library in the same render, which have no data yet: the previous library never shows, not even for one frame. When the repository or the query client changes, and on unmount, the effect cleanup removes the old scope's queries at once, calls the old writer's `flushAll()`, so the pending coalesced writes go to the repository they were made for, and removes the old scope's queries again once it settled (a flushed write that succeeded set its entry again). An apply still waiting for its query cancel at that moment finds its entry removed and rejects as not loaded; its error is not shown on the next library. Each retired value is reported to `onRetired({ repository, flushed })`, in the commit that retires it: its repository and the promise of that `flushAll()` (never rejects). `onRetired` is read through a ref set during the commit, not an effect dependency, so a new function never retires the live value.

`SessionLibraryContextProvider({ guest, accountRepositoryFor, reporter, children })` (A-03, A-04), inside `AuthContextProvider`, renders `LibraryContextProvider` with the repository of the session (`useAuthSession`): the `GuestLibraryRepository` `guest` signed out, the `AccountLibraryRepository` `accountRepositoryFor(userId)` signed in (memoized on the user id: a token refresh keeps the instance, another user or a new sign in gets a new one), and `PENDING_LIBRARY_REPOSITORY` while the session loads, whose calls never settle, so the library screens show their loading state instead of the wrong library. Screens use the hooks only and never know which repository is active.

### Guest merge

Each account instance gets the guest library merged into it as it becomes the session's (BR-08, FR-22, ADR-0016): at a launch with a stored session, a sign in, a switch to another user, and again on `retry()` after a failure; a token refresh keeps the instance and starts nothing. Until the merge of the current instance concluded, the library is `PENDING_LIBRARY_REPOSITORY`: the merge phase is derived from the instance, so its very first render is already `checking`, the account library never shows before the merge, and no write reaches it meanwhile.

- `mergeGuestLibrary({ guest, account, settleWrites, isCurrent, onMerging })` (`guest-merge.ts`, plain TypeScript) runs once: it waits for `settleWrites()`, lists the guest store (`empty`: nothing sent), calls `onMerging()`, `account.mergeGuestEntries(entries)`, then `guest.removeUnchanged(entries)` with exactly the listed entries (`merged`). It checks `isCurrent()` after each wait and returns `stale` without a further call once the session changed: a stale run never removes a guest entry. A rejection of any step rejects the run, and nothing is removed after a failed merge.
- The provider passes `settleWrites`: every flush reported by `onRetired` and not settled yet (the guest writer retired in the commit that starts the run included, as the run starts in an effect, after the child cleanups), except the pending library's, which never settles. `isCurrent` compares the run's account instance with the session's, set during the commit, and is false once unmounted.
- `useGuestMerge()` (`use-guest-merge.ts`, `GuestMergeContext` in `guest-merge-context.ts`) gives `{ status, retry }`, `status` one of `GUEST_MERGE_STATUSES`: `checking` (the guest store read), `merging` (its entries sent), `failed` (the account library shown, the guest store kept), `idle` otherwise (signed out, the session loading, or the merge concluded). `retry()` starts a new run from `failed` only; in any other status, a retry tap is ignored. It throws outside the provider.
- A failed current run sets `failed`; a stale run changes no state. A failure that is not a `LibraryRemoteError` (the account store reports those itself) goes to `reporter.captureError(error, { source: 'guest-merge' })`, a stale run's too; no entry, key or user id is ever put in a report.

- `useLibraryEntry(key, { media })`: the entry query (`queryKeys.library.entry(scope, key)`, `STALE_TIMES.library`), read through the writer. With the catalog's `media`, the entry is shown with the fresh snapshot (`withMediaSnapshot`): display only, viewing writes nothing. The snapshot is built in `select` whether the media is in the library or not, so a `media` no snapshot can hold fails the query with a `LibrarySnapshotError` in both cases (the detail shows its unsupported message, without Add or the heart).
- `useLibraryEntryActions(key, { media })`: `add`, `remove`, `setStatus`, `setProgress`, `incrementProgress`, `setScore`, `setNotes` (blank text clears the notes) apply the domain rules (BR-01 to BR-04, BR-07, BR-09) and, with `media`, first refresh the snapshot (`refreshMediaSnapshot`): the snapshot is written with a user action only. Fire and forget; `error` holds the last failure, tied to the key values and the scope it belongs to (a recycled list row never shows another entry's error, a failure of the previous library never shows on the next one), until the next action or `dismissError`.
- `useLibraryList(options, { showAdult, layoutKey, favoritesOnly? }): { query, view }`: the `['library', scope]` list query, read through the writer (`list()`: optimistic entries shown, entry queries seeded), filtered, sorted and grouped in `select` (`buildLibraryView`, plus every entry by `libraryEntryId`), covers re-checked against the provider's `imageHosts`; an option or adult setting change never refetches. `view` keeps the layout last shown (`keepLibraryLayout`) while `layoutKey`, the options, the setting and the scope stay the same: a changed row stays in its group and position with its new values, a removed one disappears, a new one goes to the top of its group. A new `layoutKey` (the screen gaining focus), option or library (a new scope) lays the library out again.
- `createLibraryWriter({ queryClient, repository, scope, now? })` builds every key it reads, sets, cancels or invalidates with its `scope`; its per-key state is keyed by the scope-free `mediaKeyId(key)`. The writer applies each change optimistically (after cancelling the entry's fetch in flight), skips no-op changes (BR-09), debounces `+1` taps for `PROGRESS_WRITE_COALESCE_MS` into one write of the latest entry, and runs the repository calls of one key one after the other. A read first writes the pending change of its key, so a refetch never returns an older state. Each change also updates the cached list data (`library-list-data.ts`). A success shows the stored entry in the entry and list data (unless a newer change came) and invalidates the `['library', scope]` list query only (`exact`); a failure rejects the action and refetches the entry.

## Auth

`AuthContextProvider({ repository, captcha, children })`, inside the query client provider, gives the hooks the `AuthRepository`, the `CaptchaTokenProvider` (`noCaptcha` until A-08) and the session state, subscribed with `onAuthStateChange` in an effect.

- `useAuthSession()`: `{ status: 'loading' | 'signed-out' | 'signed-in', session }`, `loading` until the repository first reports the session, the same object while the user id stays the same (a token refresh re-renders nothing). The session holds the user id only.
- `use-auth-mutations.ts`: one `useMutation` per action (`useSignUp`, `useResendConfirmation`, `useSignIn`, `useRequestPasswordReset`, `useCompleteEmailLink`, `useCompletePasswordReset`, `useSignInWithProvider`, `useSignOut`), with `networkMode: 'always'` and `gcTime: 0`: the variables hold passwords, so a mutation never pauses offline and is dropped once unobserved. The four protected calls ask the captcha provider for a token first and pass `{ captchaToken }` only when there is one. `useCompletePasswordReset` exchanges the link code once, then sets the password; a retry after a failed update sets the password only; its `failedStep` (`exchange` or `update`, null without an error) tells which step failed, so a screen treats any failed exchange as a spent link. `useSignInWithProvider` takes an `OAuthProvider` and resolves the session, or null when the user closed the browser or declined consent; it asks no captcha (ADR-0015). Rejections are `AuthError`s.
- `useOAuthProviders()`: the providers this build can sign in with (`AuthRepository.oauthProviders`), in display order; empty until A-09.
